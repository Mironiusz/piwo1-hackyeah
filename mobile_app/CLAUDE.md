# CLAUDE.md

Agent rules for this repository. HackYeah 2026, challenge "Kraków bez barier": **EnableMe** (walking routes in Kraków rated against the user's needs, facts about barriers and amenities, community reports and votes; see README.md and docs/ARCHITECTURE.md) - an OpenHarmony app (ArkTS + ArkUI, Stage model) in `accessway/`, API 20, built and run on Linux with the Oniro toolchain. The screens follow the team mock-ups "Widoki MVP: makiety"; product rules come from the piwo1-hackyeah repository.

## Communication

- Talk to the user in Polish. Everything committed to the repo (code, README, docs, AI_WORKFLOW.md) is in English - the jury requires English.
- When something is unclear, say so and ask instead of guessing. Flag potential bugs you notice.
- After each change: what changed, why, decisions taken, risks noticed, what is still unknown.

## Git

- Never run `git commit` or `git push` - the human commits. `git add` / `git rebase` only on explicit request.
- The jury looks at commit history to see progress, so suggest committing after each working step.

## Toolchain (see README.md)

- All commands go through the `Makefile`: `make build`, `make run`, `make lint`, `make logs`, `make screenshot`, `make doctor`.
- CLI: `source scripts/env.sh && oniro <cmd>` (wrapper around `@oniroproject/oniro-app`, pinned in `scripts/env.sh`).
- Do not hand-edit `signingConfigs` in `accessway/build-profile.json5`, `accessway/local.properties` or `accessway/signatures/` - they are machine-specific and regenerated by `make sign` / `make setup`.
- Emulator installation from scratch (Linux, Windows, without KVM): `docs/setup/EMULATOR_SETUP.md` in the root of the repository.
- Keep `compileSdkVersion` / `compatibleSdkVersion` at 20 unless the user decides otherwise (challenge requires API 20+ and declaring 20 as minimum).

## Code

- ArkTS strict rules apply (no `any`, no untyped object literals, explicit interfaces/classes). Prefer `@ohos.*` / `@kit.*` platform APIs - real platform usage is 20% of the score.
- Small, readable components; reasonable error handling for API errors, timeouts and missing data.
- Screens get data only through the `Repository` interface (`accessway/entry/src/main/ets/data/Repository.ets`); do not guess API contracts, ask instead.
- Request only the permissions the feature needs (`module.json5` `requestPermissions`, with reasons).
- No secrets, keys or personal data in the repo.
- Add/maintain tests in `accessway/entry/src/test` (local unit, `make test`) for key scenarios.

## Deliverables checklist (challenge requirements)

1. Public repository; README with reproducible setup/build/install/launch.
2. Working `.hap` (signed) - attach to the submission / release, not to git.
3. Short recorded demo (emulator is fine).
4. `docs/ARCHITECTURE.md` - concise architecture and implementation description.
5. `AI_WORKFLOW.md` - update it whenever an AI tool, important prompt or decision is used.
6. If the app gets AI features: model, inference flow, data handling, limitations, validation, privacy (EnableMe has none today).
