## Scenarios: input, flow, expected state after the run

1. First start. Input: a clean server with Docker, the repository checked out, the environment file filled in from the templates. Flow: the user runs the start command, then the revisions command with consent, then the loading program, then restarts the routing service. State after: the page answers at the public link, `/api/` reaches the one backend process, `/tiles/krakow.pmtiles` answers byte ranges, a reload of any view path returns the page of the application, and routing plans a route.
2. Partial deployment before the whole demo works. Input: the routing data are not loaded yet. Flow: the user runs the start command. State after: the page, the tiles once loaded and the backend answer at the link; the routing service waits for the pointer `current`; a route request gets the plain message of M10. The task is not done yet (requirement 10).
3. Restart. Input: the demo running with loaded data. Flow: the server is rebooted, or one service is restarted. State after: all services come back on their own with the same database, routing data and tile archive, without loading again (requirement 3).
4. A vote without an account through the proxy. Input: a person at 203.0.113.7 votes. Flow: the proxy passes the request to the backend with the address of the person. State after: the backend stores the hash of M9; neither the proxy log nor the backend log holds the IP address or the User-Agent (requirement 6).
5. Emptying the database. Input: the demo with data. Flow: the user runs the command of `docs/deployment/hosted_demo.md`, section Emptying the database. State after: the database volume is empty and the next start begins from scenario 1.
