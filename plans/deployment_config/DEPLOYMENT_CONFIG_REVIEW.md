# Review: Deployment configuration of the MVP demo

## Implementation run of 2026-10-04

### Deviations from the plan

O-1. The pulled routing image of D-1 lacks the start script of the routing service. `ghcr.io/mironiusz/valhalla-a11y:3.9.0-a11y.1` was created at 2026-10-04T00:00:45Z, before commit `d8227b9` added `COPY start_routing_service.py valhalla_overrides.json /opt/enableme/` and the `CMD` that runs it to `valhalla/Dockerfile`; the image has `CMD ["/bin/bash"]` and no `/opt/enableme`, so F-3 and F-4 do not hold together and the build of the backend image stopped at `valhalla_build_config > /opt/enableme/valhalla_config_template.json`. The patches and the rest of `valhalla/Dockerfile` did not change between the build of the tag and that commit. Kuba decided on 2026-10-04, against a thin layer over the pulled tag and against publishing a new tag with `.github/workflows/valhalla-image.yml`, to build `valhalla/Dockerfile` instead: `routing` is built from `valhalla/` as `enableme-routing:local`, and the backend image is built `FROM` that image through the build context `routing` of `additional_contexts`, so D-1 is replaced and a first start on the server includes the build of Valhalla, 11 min 33 s in the spike.

O-2. Compose 2.29.2 refuses the build context `service:routing` of `additional_contexts` with "failed to get build context routing: stat .../deploy/service:routing". The backend takes the routing image through `routing: docker-image://enableme-routing:local` instead, so `enableme-routing:local` has to exist before the backend is built: `docs/deployment/hosted_demo.md`, section Starting the demo, runs `build routing` before `up -d --build`. Agent decision at C:40, without asking: the only form the Compose version of D-13 accepts, with no change of what the images hold.

O-3. The check of AC-8 found that an appended X-Forwarded-For lets a person choose the address the backend hashes. A throwaway container of the backend image, run with the alias `backend` and the uvicorn settings of `api/__main__.py`, answered a request through the proxy carrying `X-Forwarded-For: 203.0.113.9` with `203.0.113.9`: the peer the proxy saw was the gateway of the network `enableme_edge`, inside the subnet D-15 makes trusted, so uvicorn skipped it and took the forged entry. Kuba decided on 2026-10-04, against appending and trusting only the address of the proxy container, that the proxy overwrites the header: `deploy/nginx.conf` sets `proxy_set_header X-Forwarded-For $remote_addr;` in place of `$proxy_add_x_forwarded_for` of D-9. The same check then answered `172.22.0.1`, the peer, for the forged request too. This departs from the word "appends" of D-16 of `plans/community_facts_api/COMMUNITY_FACTS_API_PLAN.md`; the backend side of D-16 does not change.

O-4. nginx resolves the name `backend` once at its start, so a backend container recreated with another address would leave the proxy answering 502 until a restart of the proxy. `deploy/nginx.conf` adds `resolver 127.0.0.11 valid=10s ipv6=off;` and passes `/api/` through the variable `$backend_upstream`, which makes nginx resolve the name again every 10 seconds; the check of O-3, where the throwaway container got a new address, was answered without restarting the proxy. Agent decision at C:40, without asking: a defect of D-9 found while running it, fixed inside the file D-9 decides, with no change of a contract.

O-5. The access log of the proxy names the path after `try_files`, so a view path is logged as `/index.html`. This holds PRD FR-6, which allows at most the path, and it leaves the log less useful for telling one view from another. Agent decision at C:40, without asking: nginx has no variable of the original path without its query string, and `$request_uri` would log the query string, which FR-6 keeps out.

O-6. `error_log /dev/stderr emerg;` of D-9 keeps every error line that names a client out of the log, and with it the cause of an upstream failure: a 502 shows only as the status in the access log, and its reason is read from the log of `backend`. Agent decision at C:40, without asking: the trade-off D-9 chose for PRD FR-6, recorded here after the review asked for it.

O-7. `docker compose down` removes the network `enableme_edge`, and the next start gave it another subnet, `172.21.0.0/16` in place of `172.22.0.0/16`, so the value D-15 writes into `API_TRUSTED_PROXY_ADDRESSES` goes stale and the backend stops trusting the proxy. A start with `up`, a restart after a fix and a reboot of the server keep the network. `docs/deployment/hosted_demo.md`, section Emptying the database, the only step that runs `down`, now repeats the step of D-15 after the next start. Agent decision at C:40, without asking: the smallest change that keeps D-15; pinning a subnet in the repository was rejected in D-15.

O-8. The import of AC-3 ran in the container `loader` and ended after 380 seconds with `OSM import outcome=failed cause=OsmReadError: Cannot read complete source elements`. A one-off script outside the repository, run in a throwaway container of the backend image, read the same `malopolskie-latest.osm.pbf` with `osmium.FileProcessor(path).with_locations().with_areas()` as `data/osm_reader.py` function `fetch_osm_elements` does: it read 24 100 926 nodes, 287 144 ways and 170 068 areas, and `osmium.geom.WKBFactory.create_multipolygon` then raised `RuntimeError: invalid area (area_id=27125993)` for the area of relation 13562996. `fetch_osm_elements` turns every `RuntimeError` into `OsmReadError`, so one broken multipolygon of OpenStreetMap stops the whole import. This is a defect of the importer of `plans_finished/osm_importer/` on real data, not of the configuration; the disk had 82 GB free. Kuba decided on 2026-10-04 to diagnose it with a time limit and hand it to Mateusz, the owner of the importer, without fixing `data/osm_reader.py` in this task. Until it is fixed, no routing data exist on the demo and every route ends with the message that a route cannot be planned right now.
