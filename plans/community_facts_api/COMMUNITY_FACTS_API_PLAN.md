## Decisions

D-1. Keep the approved boundary: API/service implementation belongs to this initiative; data operations are delivered by `plans/community_facts/` and actor resolution by `accounts`. Do not create alternative account or community-data implementations to hide missing dependencies. Agent decision at C:40, without asking: this follows the approved scope, the split the user decided on 2026-10-04 and the ban on guessing contracts.

D-2. New HTTP operations are synchronous FastAPI routes, so synchronous SQLAlchemy work runs in the framework's thread pool. `api/facts.py` owns the six public fact routes and `api/moderation.py` the three moderator routes. Their route names are the nine operation headings in the contract, independent of the Python function names. Registration is through `apply_fact_routes(app)` and `apply_moderation_routes(app)` called from `api.app.build_app`. Agent decision at C:40, without asking: all delivered database calls are synchronous and the route split follows the existing contract.

D-3. `api/fact_models.py` owns the strict request models `FactAreaRequest`, `NearbyFactsRequest`, `CreateFactRequest` and `CastVoteRequest`, configured like the route models of F-31. Responses follow the route idiom: plain dict bodies built in `api/fact_body.py`, which reuses `build_fact_body` and gains `build_flagged_fact_body(FlaggedFactView)`, `build_area_facts_body` and `build_nearby_facts_body`. No Pydantic response model and no second Fact builder is added. Pydantic performs shape validation, while cross-field domain rules stay in service. Agent decision at C:40, without asking: F-30 and F-31 show an existing builder and idiom, and a parallel one would break DRY.

D-4. `service/fact_rules.py` owns `InvalidFactInputError`, `FactCreationInput` and `resolve_fact_creation_input`, validates the ordered area corners, the stairs-only step count, barrier-only geozones and permitted radii, and normalizes descriptions. `build_fact_idempotency_key(UUID)` computes SHA-256 of ASCII `create_fact:` plus the canonical lowercase UUID, as the target schema requires. A canonical creation input is compared to the saved content, not to its author, timestamp or current status. Agent decision at C:40, without asking: normalization and stable key semantics are already decided.

D-5. `service/community_facts.py` owns read/write orchestration and the domain failures `FactNotFoundError`, `IdempotencyKeyReusedError`, `VoteTooSoonError`, `FactNotFlaggableError` and `FactNotFlaggedError`. It builds views using the existing `FactView` and `resolve_fact_status`; the API adapter exposes no status sums or person fields. Stored votes are grouped by fact in one pass, not filtered once per returned fact. The exact data calls and result types remain Q-4 and are not invented in this plan. Agent decision at C:40, without asking: orchestration, one evaluator and omission of protected data follow the architecture and contract.

D-6. Area/detail/nearby/moderator reads use `fetch_read_only_snapshot(fetch_api_engine())` so facts and votes come from one snapshot. Writes use a caller-owned transaction from `fetch_api_engine().begin()` and construct the successful response view before leaving it; failure rolls back and no response is returned before commit. Reads take no per-fact engine or connection. Agent decision at C:40, without asking: this reuses the delivered engine and prevents mixed fact/vote states.

D-7. Optional-token operations depend on `api.sessions.fetch_request_session` and moderator operations on `api.sessions.fetch_moderator_actor` (F-19). An authenticated voter supplies `AccountActor.account_id`; an anonymous voter supplies only the 32 bytes of D-11. The data layer receives no Request, IP or User-Agent. A write that fails on `fk_vote_account` raises `service.session_tokens.SessionExpiredError` (F-20). Session registration stays where `apply_account_routes` installs it, which already covers every route (F-33). Agent decision at C:40, without asking: this follows the delivered consumer contract.

D-8. `api/fact_errors.py` installs domain-to-contract handlers through `apply_fact_error_handlers(app)`. Most failures reuse `build_error_response`. `build_error_response` gains a keyword `repeat_allowed_at: datetime | None = None`, written as the contracted ISO 8601 value with milliseconds and offset only for `vote_too_soon`, following the existing pattern of `fields` and `points` (F-7); existing callers stay unchanged and no second error envelope is introduced. Unexpected errors retain the existing sanitized diagnostic path. Agent decision at C:40, without asking: F-7 shows the established pattern for a code-specific error field.

D-9. Compute the next voting boundary in `service/fact_rules.py` through `build_repeat_allowed_at(cast_on: date)`: add one calendar day as a date, combine with local midnight and the configured Europe/Warsaw ZoneInfo. This is calendar arithmetic, not addition of 24 hours to an aware instant. A conflict must supply the stored conflicting vote day, so waiting through midnight cannot produce a stale next-vote time from request-entry time. Preserve the stored offset pair through `build_offset_instant` on writes and `build_local_datetime` on reads. Agent decision at C:40, without asking: the daily limit and offset standard decide this behavior.

D-10. Retrying a save first respects public visibility, then compares normalized saved content. The operation returns the original fact on an identical retry and writes the author confirmation only for a newly inserted fact. The new-fact insertion, author confirmation and view belong to one transaction. The final conflict protection stays in the delivered data operation and database constraint, not in a preliminary service lookup. Agent decision at C:40, without asking: this follows PRD FR-2 and FR-6 and the idempotency standard.

D-11. `service/anonymous_voters.py` owns `AnonymousVoterInput` (an `ipaddress` address and the User-Agent text, both excluded from its representation), `InvalidAnonymousVoterInputError` raised without any input in its message, the constant `ANONYMOUS_VOTER_HASH_DOMAIN = b"enableme-anonymous-voter:v1"` and `build_anonymous_voter_hash(voter: AnonymousVoterInput, key: bytes) -> bytes`. The hash is HMAC-SHA256 under the key of D-15 over the domain followed by two fields, each a 4-byte big-endian length and its UTF-8 bytes: the canonical address, then the User-Agent. The canonical address is `ipaddress.ip_address(host)`, an IPv4-mapped IPv6 address reduced to its IPv4 address, written in compressed form. `api/fact_identity.py` owns `fetch_anonymous_voter_input(request: Request) -> AnonymousVoterInput`: it takes the address from `request.client.host` as uvicorn resolved it under D-16 and the User-Agent under D-17, logs neither, and raises `InvalidAnonymousVoterInputError` when the request has no client or its host is not an IP address, which ends in the existing sanitized `internal_error` path because it is a transport fault, not an input of the person. Agent decision at C:40, without asking, for the framing, the canonical address and the transport-fault path: they make the identity deterministic and cannot add an identifying input.

D-12. Preserve the already agreed vote wait of at most 120 seconds (F-21). On the vote transaction, use the existing `data.engine.APPLY_STATEMENT_TIMEOUT_SQL` to set a local 120000 ms statement budget before the fact-lock query, then restore `API_STATEMENT_TIMEOUT_MS` after that query. The data handoff must identify the lock operation and must capture the vote instant after the wait, so a wait through midnight applies the day of the actual write. All other request statements keep the existing 5000 ms limit. The proxy handoff of D-16 records the maximum wait. No write retries after an uncertain commit; the client reconciles a save through its same key and retries a vote through the agreed daily-limit behavior. A timeout rolls back and uses the existing safe `internal_error` contract. Agent decision at C:40, without asking: the 120-second vote agreement already exists; the narrow transaction-local setting preserves it without raising the limit for all API reads or inventing a new failure code.

D-13. There is no new schema revision, periodic job, external HTTP call, dependency or status cache. The two configuration entries of D-15 and D-16 use the existing settings, facade and empty-marker templates, with matching standard records and tests. Machine-specific or secret values never enter these artifacts. Agent decision at C:40, without asking: none of those additions is required by the approved scope.

D-14. Group tests by the existing layer boundary. API integration replaces service calls and session dependencies; service scenarios replace the agreed data seam; critical checks run the real data operations on the local database and prove offset preservation and atomic writes. Do not seed durable fact/vote rows through a service-account connection and then assume DELETE cleanup. The exact transaction-injection or local owner-cleanup fixture is part of Q-4. Agent decision at C:40, without asking: F-17 and the testing standard require this boundary.

D-15. The anonymous-voter hash is keyed by a separate secret `VOTER_HASH_KEY`: a `SecretStr` of at least `VOTER_HASH_KEY_MIN_LENGTH = 32` characters kept in `.env`, declared like `SESSION_SIGNING_KEY` (F-9) and read lazily by `fetch_voter_hash_key() -> bytes` in `service/anonymous_voters.py` through the facade, as `fetch_session_signing_key` does. The key stays the same for the whole demo; changing it gives every anonymous person a new identity. Decided by the user on 2026-10-04, answering Q-1, after the run in which rotating the session key would let one person count twice.

D-16. The person's address reaches the service through uvicorn's own proxy handling. A new `.env.local` entry `API_TRUSTED_PROXY_ADDRESSES` holds a comma-separated list of IP addresses or CIDR networks of the proxy; empty means no proxy is trusted and the raw peer is the person's address, which is the local case. `Settings` validates it with `apply_trusted_proxy_validation`, refusing an asterisk and any entry that is neither `ipaddress.ip_address` nor `ipaddress.ip_network`, because uvicorn would silently keep a malformed entry (F-32). `api/__main__.py` passes `proxy_headers=True` and `forwarded_allow_ips=API_TRUSTED_PROXY_ADDRESSES` explicitly, so uvicorn never falls back to `FORWARDED_ALLOW_IPS` or `127.0.0.1` (F-8). The producer side handed to `plans/deployment_config/`: the proxy appends the TCP peer address to X-Forwarded-For on every request it passes to the backend, its read timeout towards the backend allows the 120 seconds of D-12, and the server's `.env.local` sets `API_TRUSTED_PROXY_ADDRESSES` to the proxy's address or network, a value that never enters the repository. Decided by the user on 2026-10-04, answering Q-2.

D-17. A missing or empty User-Agent is the empty text, and repeated User-Agent headers are joined in received order with `, `, as `request.headers.getlist("user-agent")` gives them. Nothing is refused and the contract does not change; people without a User-Agent behind one address share one identity, the same accepted limitation as identical pairs. Decided by the user on 2026-10-04, answering Q-3, for the missing and empty cases; the joining of repeated headers is an Agent decision at C:40, without asking, because it keeps the identity deterministic without a refusal.

D-18. Move `PointBody` from `api/route.py` to a new `api/point_body.py`, imported by `api/route.py` and `api/fact_models.py`, without changing it. Agent decision at C:40, without asking: the contract has one point object (F-31), and a second model or an import from the route module would duplicate or misplace it.

D-19. This initiative is archived on its own final ready verdict; it no longer waits for the archiving of `plans/community_facts/`. Agent decision at C:40, without asking: the user's split makes this task the whole scope of its initiative, which is the unit of archiving.

## Risks

R-1. The data-operation contract is missing, so the service signatures and fixture boundary cannot yet be finalized. Treat Q-4 as a real dependency, not an opportunity to invent fallback queries or alternate result types.

R-2. The live local schema and query cost are unverified. Models and revision SQL establish the target, not the state of a server; do not label S-0 or critical acceptance passed until a run proves them.

R-3. IP + User-Agent collisions and changed-pair identities are accepted prototype limitations, and D-17 adds the empty User-Agent to them. At the demo venue many people share one public address and the same browser or app version, so they share one anonymous identity: after one of them votes on a fact, the next is refused with `vote_too_soon` until midnight. A changed `VOTER_HASH_KEY` creates a different identity for everyone.

R-4. D-16 trusts exactly the configured proxy. A list that is too wide lets a client choose its own address through X-Forwarded-For; a list that misses the proxy, or a proxy that does not append the header, makes every anonymous person one identity per User-Agent. The hosted demo has to be checked with two different addresses before the demo.

R-5. Full vote-history reads have unbounded row volume even though the area result is capped. Group once, avoid N+1 queries and measure the delivered data method. If it requires a bounded status projection, agree it with Kuba and preserve the latest-confirmation date as well as the five-person window.

R-6. The agreed fact-lock wait requires a narrow extension of the current 5-second statement ceiling. The exact lock call belongs to the data handoff, and the proxy must support the recorded wait. Pool occupancy remains bounded by the existing pool settings; a pool timeout is a safe failure, not a reason to create more engines.

R-7. Account deletion and moderation can race with a vote/save. The service must use the agreed locked data outcomes and translate account detachment without treating it as anonymous or returning a partially committed view.

R-8. Kuber and Adrian's confirmation of the contract amendments and the team handoff remain outstanding. Do not resolve these by silently altering requests, permissions or identifying inputs.

R-9. The importer side of the publication race is delivered (F-21, F-29), but AC-14 still needs the locking vote write of Kuba's data layer and a real run of a publication against a waiting vote; do not claim it passed with a substitute importer or vote write.

R-10. The HarmonyOS client gives up after 15 seconds (F-23), while a vote may wait up to 120 seconds during a publication (D-12). Such a vote can commit after the client has shown a failure, and a retry on the same day is refused with `vote_too_soon`, which is the agreed daily-limit behavior but needs a clear message in the client.
