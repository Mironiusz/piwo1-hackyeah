## Decisions

D-1. Two stages in one plan. Stage A is S-1 - S-6, documents only, implemented at once (PRD FR-3). Stage B is S-7 - S-12, the package `db/`. Agent decision at C:40, without asking: it follows from FR-3 of the PRD. Changed on 2026-10-04 by Kuba during the implementation (D-14): stage B no longer waits for the code of `backend_skeleton`, because the package brings its own local database, its own Alembic configuration and its own connection for the tests.

D-2. The calendar day of a vote is the stored generated column `cast_on date GENERATED ALWAYS AS ((cast_at AT TIME ZONE 'Europe/Warsaw')::date) STORED`, and the vote limit is the two constraints `UX_vote_account_day UNIQUE (fact_id, account_id, cast_on)` and `UX_vote_hash_day UNIQUE (fact_id, voter_hash, cast_on)`. A vote of an account has a null hash and a vote without an account a null account, so with the default distinct nulls each constraint compares only its own kind of person, and a vote whose account was deleted takes part in neither (F-18). `STORED` is written out, because a virtual generated column cannot carry a unique index. The zone literal stands once, in the DDL; the code that computes `repeat_allowed_at` takes the zone from the configuration (F-16). `PK_vote` stays on `id`, because `voter_hash` and `account_id` are nullable. Decided by Kuba on 2026-10-04 in this phase, against two unique indexes on an expression with the literal twice and no stored day.

D-3. `CK_vote_voter_hash_sha256 CHECK (octet_length(voter_hash) = 32)` on `vote`, named after `CK_fact_idempotency_key_sha256`; a null hash passes it. Decided by Kuba on 2026-10-04 (shape, question 7); the name is an agent decision at C:40, without asking.

D-4. Version 13 of `docs/product/specification.md` and the documents that follow it carry exactly the texts of S-1 - S-4. The wording is proposed by the agent; the interface texts keep their keys, `vote.own.saved` says the next vote is possible the next day, which stays true whenever the own vote is shown, and `vote.too_soon` takes the placeholder `{day}` in place of `{moment}`, because the moment is now always a midnight. Agent decision at C:40, without asking: Kuba decided that the version rewrites these documents and left the wording to the version (shape, question 8).

D-5. The name of the service account reaches the revision from the environment entry `DB_SERVICE_ACCOUNT_NAME`, the same entry from which the script of the image of `db/` creates that account. `db/accessibility_db/migrations/env.py` reads it directly from the environment, with the described exception of `alembic/env.py` (F-12), stops with the name of the key when it is missing, and passes it as `context.config.attributes["service_account_name"]`. The revision gives it to the database only as a parameter of `set_config('accessibility_db.service_account_name', :service_account_name, true)` and quotes it as an identifier inside each grant with `format('%I', current_setting('accessibility_db.service_account_name'))` (F-11, F-19). On the server the same entry stands in the one environment file of the demo, so the step of applying the revisions needs no argument at the call besides the consent (F-13, D-15). Proposed by the agent at the request of Kuba on 2026-10-04 that it works with the deployment, against the name typed as `alembic -x` at every application. Changed on 2026-10-04 by Kuba during the implementation (D-14): the file is the environment of the package, not `alembic/env.py` of `backend_skeleton`, and the setting is named after the package, because Kuba refused the prefix `piwo1`.

D-6. The grants are four statements, one per row of the table Rights of the service account, each on the named tables only. No `ALTER DEFAULT PRIVILEGES` and no `ON ALL TABLES`: the rights differ per table, and a grant on all tables would also reach `alembic_version`, on which the service account gets nothing. Identity columns need no grant on their sequences (F-19). Agent decision at C:40, without asking: it follows from "exactly these rights" of `docs/product/schema.md` and F-10.

D-8. The shared model is SQLAlchemy declarative mapping, because the pair of an instant is mapped through `composite()` (F-16), in the package `accessibility_db` of `db/`: `accessibility_db/closed_lists.py` with the six closed lists as `enum.StrEnum`, and `accessibility_db/tables.py` with the seven mapped classes. A composite cannot carry the name of its own column and SQLAlchemy keeps an attribute for every column of a composite (F-25), so each pair is one public attribute named after its instant column, with its two columns under private keys starting with an underscore, the closest SQLAlchemy comes to no attribute for the offset alone; a nullable pair passes `return_none_on` explicitly, because the automatic one of SQLAlchemy 2.1 does not apply to an explicitly named composite class (F-25). `geography` is a `UserDefinedType` written and read as EWKT text through `ST_GeogFromText` and `ST_AsEWKT`, so no GeoAlchemy2 dependency is added. The package pins SQLAlchemy 2.1.3, psycopg 3.3.6 and Alembic 1.20.0 (F-17). Agent decision at C:40, without asking, for the form. Changed on 2026-10-04 by Kuba during the implementation (D-14): the model was planned in `data/` of the backend, and Kuba decided it is a library of its own, `db/` with the import name `accessibility_db`, which the import and the backend install.
