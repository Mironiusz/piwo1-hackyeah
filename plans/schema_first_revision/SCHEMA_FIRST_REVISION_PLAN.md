## Decisions

D-1. Two stages in one plan. Stage A is S-1 - S-6, documents only, implemented at once (PRD FR-3). Stage B is S-7 - S-13 and starts only when the code of `backend_skeleton` is merged into the branch of this initiative, because the revision, the model and the tests stand on its `data/engine.py`, `alembic/env.py`, `pyproject.toml` pins and critical-test hook (F-9, F-12, F-14). Agent decision at C:40, without asking: it follows from FR-3 of the PRD and from the trigger of the shape.

D-2. The calendar day of a vote is the stored generated column `cast_on date GENERATED ALWAYS AS ((cast_at AT TIME ZONE 'Europe/Warsaw')::date) STORED`, and the vote limit is the two constraints `UX_vote_account_day UNIQUE (fact_id, account_id, cast_on)` and `UX_vote_hash_day UNIQUE (fact_id, voter_hash, cast_on)`. A vote of an account has a null hash and a vote without an account a null account, so with the default distinct nulls each constraint compares only its own kind of person, and a vote whose account was deleted takes part in neither (F-18). `STORED` is written out, because a virtual generated column cannot carry a unique index. The zone literal stands once, in the DDL; the code that computes `repeat_allowed_at` takes the zone from the configuration (F-16). `PK_vote` stays on `id`, because `voter_hash` and `account_id` are nullable. Decided by Kuba on 2026-10-04 in this phase, against two unique indexes on an expression with the literal twice and no stored day.

D-3. `CK_vote_voter_hash_sha256 CHECK (octet_length(voter_hash) = 32)` on `vote`, named after `CK_fact_idempotency_key_sha256`; a null hash passes it. Decided by Kuba on 2026-10-04 (shape, question 7); the name is an agent decision at C:40, without asking.

D-4. Version 13 of `docs/product/specification.md` and the documents that follow it carry exactly the texts of S-1 - S-4. The wording is proposed by the agent; the interface texts keep their keys, `vote.own.saved` says the next vote is possible the next day, which stays true whenever the own vote is shown, and `vote.too_soon` takes the placeholder `{day}` in place of `{moment}`, because the moment is now always a midnight. Agent decision at C:40, without asking: Kuba decided that the version rewrites these documents and left the wording to the version (shape, question 8).

D-5. The name of the service account reaches the revision from the environment entry `DB_SERVICE_ACCOUNT_NAME`, the same entry from which the script of the local setup creates that account. `alembic/env.py` reads it directly from the environment, in the same way and with the same described exception as the address of the schema owner (F-12), stops Alembic with the name of the key when it is missing, and passes it as `config.attributes["service_account_name"]`. The revision gives it to the database only as a parameter of `set_config('piwo1.service_account_name', :service_account_name, true)` and quotes it as an identifier inside each grant with `format('%I', current_setting('piwo1.service_account_name'))` (F-11, F-19). On the server the same entry stands in the one environment file of the demo, so the step of applying the revisions needs no argument typed at the call besides the consent (F-13). Proposed by the agent at the request of Kuba on 2026-10-04 that it works with the deployment, against the name typed as `alembic -x` at every application and against a plan left open until `backend_skeleton` names the entry; `backend_skeleton` names the entry this way (steps of a human).

D-6. The grants are four statements, one per row of the table Rights of the service account, each on the named tables only. No `ALTER DEFAULT PRIVILEGES` and no `ON ALL TABLES`: the rights differ per table, and a grant on all tables would also reach `alembic_version`, on which the service account gets nothing. Identity columns need no grant on their sequences (F-19). Agent decision at C:40, without asking: it follows from "exactly these rights" of `docs/product/schema.md` and F-10.

D-7. The revision is `alembic/versions/0001_target_schema.py` with `revision = "0001"` and `down_revision = None`, so the order of the chain is visible from the file names (F-10). It holds `CREATE_TARGET_SCHEMA_SQL: tuple[str, ...]`, every statement of the `sql` blocks of `docs/product/schema.md` version 13 in the order of the document, verbatim, without the final semicolon; `SET_SERVICE_ACCOUNT_NAME_SQL: str`; and `GRANT_SERVICE_ACCOUNT_SQL: tuple[str, ...]`. Agent decision at C:40, without asking.

D-8. The shared model is SQLAlchemy declarative mapping, because the pair of an instant is mapped through `composite()` (F-16). It lives in the data layer, the only layer that touches the database (F-9), in two files: `data/closed_lists.py` with the six closed lists as `enum.StrEnum`, and `data/tables.py` with the seven mapped classes. The service layer imports them along the direction input, rules, data. A nullable pair is annotated `Mapped[OffsetInstant | None]`, which needs SQLAlchemy 2.1 (F-17). `geography` is a `UserDefinedType` written and read as EWKT text through `ST_GeogFromText` and `ST_AsEWKT`, so no GeoAlchemy2 dependency is added. The queries of the consumers stay `<VERB>_<WHAT>_SQL` constants; the model gives them typed rows, for example through `select(Vote).from_statement(text(...))`. Agent decision at C:40, without asking: it follows from F-9, F-11 and F-16 and from the "minimal model of the tables" of the shape.

D-9. The critical tests run against the local database brought to the head of the chain by the documented command, connect only through `build_engine(statement_timeout_ms=5000)` as the service account, and roll back every write: each test runs in a transaction of the fixture `service_connection`, and each expected refusal in a savepoint. They therefore write no durable seed and need no cleanup fixture (F-14). Decided by Kuba on 2026-10-04 in this phase, against a session fixture applying the chain as the schema owner.

D-10. A refusal is asserted by the name of the constraint the database reports, `exc.orig.diag.constraint_name`, in lower case (F-18), not by the error class alone, so a test cannot pass on another constraint. The objects test compares names in lower case and leaves out what an extension owns (`pg_depend.deptype = 'e'`), `alembic_version`, and the not-null constraints PostgreSQL 18 keeps in `pg_constraint` with `contype = 'n'`. Agent decision at C:40, without asking.

D-11. The match of the revision with the target schema is proven twice: a test without a database compares `CREATE_TARGET_SCHEMA_SQL` statement by statement with the `sql` blocks of `docs/product/schema.md`, whitespace collapsed, and a critical test compares the stored objects with the names those statements create. The line by line review of AC-13 of the fact schema PRD therefore reduces to the grants and the docstring. Agent decision at C:40, without asking.

D-12. The naming registry gets the section Names in the database with every extension, domain, table, constraint and index the revision creates, as `docs/product/schema.md` writes it and as it is stored, and the setting `piwo1.service_account_name`; the sections File names, Function names and Names of query constants get the names this plan creates. Columns are not listed: `docs/product/schema.md` is their place. Agent decision at C:40, without asking: FR-9 and F-21.

D-13. No pair of documents of the code unit is written for `data/`, because the model holds no domain rule (F-23); the docstrings of the modules carry what they map and why. Agent decision at C:40, without asking.

## Risks

- The DDL with PostGIS and on PostgreSQL 18 has never run: F-18 and F-19 ran on PostgreSQL 15 without PostGIS (F-20). A defect found in S-13 needs another version of the specification approved by Kuba before the revision can match it, and recreating the local database after every edit of the applied revision (`docs/standards/standard_database.md`, Form of schema changes).
- If `backend_skeleton` names the entry of the service account otherwise or pins SQLAlchemy 2.0, S-7 stops; with SQLAlchemy 2.0 a null flag would read as an `OffsetInstant` of nulls (F-17).
- The zone literal of `cast_on` and the business zone of the configuration can drift apart; `community_facts` then names a `repeat_allowed_at` the database does not keep. Both are Europe/Warsaw today.
- `cast_on` is computed with the zone rules of the database at the write; a change of those rules later does not recompute stored days. Irrelevant for a demo deleted on 4 October 2026.
- The test of D-11 reads `docs/product/schema.md` by its layout: statements in `sql` blocks, each ending with a semicolon at the end of a line. A change of that layout breaks the test, not the schema.
- The critical tests need the local database at the head of the chain; on a database left at another state they fail on the objects test first, which says what is missing.
- Stage A and the work of Kuber and Adrian edit the same documents of the frontend; a merge conflict there is resolved by keeping the calendar day.
