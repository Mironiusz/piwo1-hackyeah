## Decisions

D-1. The key is the column `idempotency_key bytea NULL` of `fact`, holding the SHA-256 hash of the UTF-8 text `create_fact:` followed by the `idempotency_key` of the request in its canonical form, 36 lowercase characters with hyphens. It meets the convention of the idempotency standard (F-6): the column has its name, the value is a SHA-256 hash, and the hashed fields are the operation type and the identity of the operation, which for a save is the key the client generates once per approved summary and repeats with every attempt (F-5), not a value generated anew on every attempt. The content of the request is not hashed: with the content in the key, the same key with another content would give another key and a second fact, while the contract refuses it with `409` (F-5). Decided by the user on 2026-10-04 in this phase, against the UUID stored as sent with a deviation from the standard recorded. Agent decision at C:40, without asking: the separator `:` and the canonical form, so that the same UUID written in capitals by one client and in small letters by another gives one key.

D-2. The constraint `CK_fact_saved_report_has_idempotency_key CHECK ((idempotency_key IS NOT NULL) = (osm_element_id IS NULL AND NOT is_sample))` makes the stored data refuse both a report or a geozone without a key and a key on a fact from OpenStreetMap, a converted fact or sample data. By F-8 the right side is true exactly for the facts saved through `create_fact`, so the constraint states which facts carry a key and which do not (AC-2 of the PRD). The name follows `CK_fact_openstreetmap_has_identity` (F-9). Agent decision at C:40, without asking: a check of integrity the database standard requires (F-10), and the PRD asks for both halves of the rule.

D-3. The uniqueness is the constraint `UX_fact_idempotency_key UNIQUE (idempotency_key)`, not a partial unique index. Facts without a key never collide, because NULLS DISTINCT is the default (F-12), and the work package of D-11 can write the save as `INSERT ... ON CONFLICT ON CONSTRAINT UX_fact_idempotency_key DO NOTHING RETURNING id`, as the standard asks (F-6): a returned row is a new fact, and no row is a repetition. The key is never cleared and no one deletes a fact, so the duplicate is the permanent kind (F-6). Agent decision at C:40, without asking: the form the standard names, and the name follows `UX_fact_osm_identity`.

D-4. The constraint `CK_fact_idempotency_key_sha256 CHECK (octet_length(idempotency_key) = 32)` refuses a value that is not a SHA-256 hash. `voter_hash` has no such check (F-9) and keeps it that way, because FR-1 of the PRD forbids any other change of the target schema; the difference is reported to the user. Agent decision at C:40, without asking: a value correctness condition the database standard requires (F-10).

D-5. No column holds the content of the save or a hash of it. The fact row holds every content field of the request (F-7), so on a repetition the code reads the fact by the key and compares the request with it, normalized the way the contract normalizes it (an empty description is `null`), and answers `200` with that fact or `409 idempotency_key_reused`. That comparison is code of the work package of D-11, not of this task. Agent decision at C:40, without asking: a column that duplicates data the row already holds would be a second source of the same truth (F-10, a column only for what the row does not hold).
