## Current state

- No backend code exists: there is no `api/`, `service/`, `data/`, `worker/` or `backend/` directory in the repository, and `tests/` holds only architecture tests (checked by the agent on 2026-10-03 and again on 2026-10-04; `plans/mvp/MVP_PLAN.md` F-3). Since commit `e6d9a67` the root holds `valhalla/`, the build definition of the image of the routing service.
- The backend is Python 3.13 with FastAPI on PostgreSQL with PostGIS, and the Python profile of the standards stays in force (`plans/mvp/MVP_PLAN.md` D-1).
- The standards already fix the outline of the backend. The service has an input layer, a rules layer and a data layer with a one-way dependency (`docs/standards/standard_architecture.md`, section Layer boundary). The layer directories `api`, `service`, `data` and `worker` sit in the repository root (`docs/standards/standard_naming.md`, section File names). The worker is a second entry point of the same image, not a separate service; it has one registry of periodic tasks in the rules layer and a database lock for every task (`docs/standards/standard_worker.md`, sections One process, one task registry and Locks).
- The backend that answers the address search runs as exactly one process, because the cache and the rate gate of the search live in its memory (`plans_finished/geocoding/GEOCODING_PLAN.md` D-15).
- The route graph is built in the memory of that process when it starts and rebuilt there when the instant of the copy in use changes (`plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-3, in force as D-9 of `plans/mvp/MVP_PLAN.md`). `plans/valhalla_routing/` decided on 2026-10-04 to replace that graph with one Valhalla service run by the project, and D-9 of `plans/mvp/MVP_PLAN.md` now points to it. Its needs for item 3: the backend learns the instant of the copy the routing data the service serves was built from, and refuses a route while it differs from the copy in use; it holds the graph of the route with the fewest barriers, about 630 MB, in the one backend process, built at start and rebuilt when the copy changes; and the import run needs the tools of the image of the engine to build the routing data before it deletes the downloaded file. Its needs for item 4: one service of the image built by `valhalla/Dockerfile` on the internal network with no port of the host, at most 2.5 GB of memory, about 60 MB of routing data for walking and about 700 MB with public transport, and a build that needs about 2.1 GB and 3.9 GB of memory with public transport (`plans/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-3, D-7, D-14).
- The import and refresh run is an administrative run started by a member of the team, never by request handling and never on a schedule, with a database lock that skips a second trigger; the form of its trigger and the machine it runs on are left to Q-11 (`plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-11). One run took 297 - 377 seconds with a peak of 980 MB of memory on the machine of the agent's session, and the downloaded file of 202 232 967 bytes is deleted after the run (F-11, D-14 there).
- The periodic task of the worker clears `voter_hash` 30 days after `cast_at` (`docs/product/schema.md`, section Who writes what). The specification says the hash "is deleted 30 days after the vote" (`docs/product/specification.md`, line 197), and AC-4 of `plans_finished/fact_schema/FACT_SCHEMA_PRD.md` says "No identifier of a vote exists 30 days after the vote was cast, while the vote still counts."
- The demo runs on a server of the user in a data centre, with 16 GB of memory and 16 cores, reached at its IP address over plain HTTP; everything of the demo runs in Docker containers orchestrated by Docker Compose, started with one command and an environment file kept on the server, with a PostgreSQL instance of its own (`plans/deployment/DEPLOYMENT_PLAN.md`, plan closed on 2026-10-04, Scope of changes, step 3, the new text of D-10). That text hands Q-11 the placement of the backend process, the worker, PostgreSQL with PostGIS, the static frontend and the Valhalla service, and whether the import runs on the server or on a team machine. D-10 of `plans/mvp/MVP_PLAN.md` still names the virtual private server of the db person (checked by the agent on 2026-10-04).
- On the server the schema revisions are applied by hand with consent given at call time, and the separate loading program - the OpenStreetMap copy, the tile archive and the sample reports - is run by hand after them; the start command does neither (`plans/deployment/DEPLOYMENT_PLAN.md` D-4 and Scope of changes, step 5, sections 6 and 7).
- The page, the programming interface and the map tiles are served from one host (`plans_finished/frontend_stack/FRONTEND_STACK_PLAN.md` D-3, in force as D-6 of `plans/mvp/MVP_PLAN.md`).

## Scenarios: input, flow, expected state after the run

1. Closing Q-11. Input: the plan of this initiative is closed. Flow: Q-11 of `plans/mvp/MVP_PLAN.md` becomes a decision that names this initiative, and D-12 there hands the implementation of the operations to the work packages. State after: the MVP plan has no open question and can be given its work packages; the work package of D-7 and the task `DEPLOYMENT_CONFIG` know where the files of the skeleton go and which services run on the server.
2. Refresh of the copy. Input: the copy in use has the instant T1 and the Valhalla service serves routing data of T1; a member of the team triggers the import and refresh run by hand. Flow: the run writes the copy T2 with its reconciliation in one transaction and builds the routing data of T2 with the tools of the image of the service; the service is pointed at the new data. State after: from the moment T2 is the copy in use until the service serves the routing data of T2, every route request ends with `routing_unavailable` (`plans/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-3); afterwards routes come from T2 and the graph of the route with the fewest barriers is rebuilt from T2; no route ever combines two copies. How short that gap is made is decided in phase B of `plan-prd`.
3. First start on the server. Input: the start command runs on a server where no schema revision has been applied and no copy is loaded, as the order of `plans/deployment/DEPLOYMENT_PLAN.md` D-4 and Scope of changes, step 5, has it. Flow: the backend process starts and finds no copy in use. State after: the process keeps running, so that the revisions and the loading can follow, and a route request ends with `routing_unavailable` until the copy is loaded and the service serves its routing data. Agent decision at C:40, without asking: it follows from that order of steps.
4. Vote without an account. Input: a person without an account confirms a fact at 10:00 on 4 October 2026. Flow: the vote stores the hash of M9; no task of the app clears it. State after: the hash exists until the demo and all its data are deleted on 4 October 2026, and the specification, `docs/product/schema.md` and AC-12 of `plans/mvp/MVP_PRD.md` say so.

## Challenging own assumptions

- Is Q-11 a shape at all, when almost every item of it is technical? Most items - how the process starts, the form of the trigger, the names of modules - are decisions of phase B of `plan-prd`, and the names follow `docs/standards/standard_naming.md`. The shape asks only about the scope, about the inputs that two sources describe differently, and about the rules that touch a blocking risk category.
- Did waiting for `plans/valhalla_routing/` move the critical path of the MVP plan? It could have, since Q-11 closes only with items 3 and 4 decided; that initiative decided on 2026-10-04, before this interview reached them, so no wait remains.
- Does "only decisions" leave the backend skeleton without an executor? Not without one, but without a date: the skeleton is built by a work package of `plans/mvp/`, and that plan has no work packages until it closes (`plans/mvp/MVP_PLAN.md`, sections Scope of changes and Rollout order are empty). The task `DEPLOYMENT_CONFIG`, which needs the skeleton, therefore waits for Q-11, for the closing of the MVP plan and for the first work package.
- Would a periodic task that clears the hash ever clear anything in the demo? No: the demo and all its data are deleted on 4 October 2026 (`CLAUDE.md`, section Target environment), so no vote reaches 30 days in it. This is the reason of the decision of question 5 not to clear it.
- Does the worker still have work without that task? It was the only periodic task Q-11 named, and no other is described in the specification. The import and refresh run is an administrative run, not a periodic task (`plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-11), though D-11 there gives a command of the worker entry point as an example of its trigger. Whether the demo runs a worker process at all is therefore a consequence for items 2 and 4, decided in phase B of `plan-prd`.
