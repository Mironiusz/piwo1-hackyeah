## Decisions

D-1. Engine and image. Every route is computed by one Valhalla service run by the project from an image of the project, built by `valhalla/Dockerfile` (F-26) from the official image `ghcr.io/valhalla/valhalla:3.9.0` with `valhalla/multimodal-exclusions.patch` and `valhalla/stop-accessibility.patch` applied, rebuilding `valhalla_service`, `valhalla_convert_transit` and `valhalla_build_tiles` with the CMake options `-DCMAKE_BUILD_TYPE=Release -DENABLE_SERVICES=ON -DENABLE_DATA_TOOLS=ON -DENABLE_TESTS=OFF -DENABLE_PYTHON_BINDINGS=OFF -DENABLE_CCACHE=OFF -DENABLE_SINGLE_FILES_WERROR=OFF -DENABLE_GEOTIFF=OFF` the spike built with (F-12, F-13); without `ENABLE_SERVICES` the service has no HTTP server, and the data tools need the OpenSSL headers (`plans/valhalla_routing/spike/VALHALLA_SPIKE_TIMELOG.md`, steps P2 and P5). The same service serves walking routes and, once O9 ships, routes with public transport. The service listens only on the internal network of the demo and publishes no port of the host. Decided by the user on 2026-10-04 in phase B, against a second service for public transport; the engine was decided by the user in the shape.

D-2. Network and routing data. The import run of `plans_finished/osm_data_source/` D-11, from the downloaded file and before D-14 there deletes it, writes a network file in PBF holding only the ways of the pedestrian network of M2, chosen by the same predicate that decides which ways the import stores, with every way tagged `foot=yes`; the tags `access`, `sac_scale`, `foot:*`, `*:conditional` and `smoothness=impassable` removed; `area=yes` removed except on `highway=pedestrian`; and only node tags that no costing of Valhalla reads as a barrier or an access restriction kept (F-6, F-7). The run then builds the routing data from that file with the tools of the image of D-1, with `mjolnir.include_platforms`, `mjolnir.keep_osm_node_ids` and `mjolnir.keep_all_osm_node_ids` set to true, and stores the network file and the routing data together with the instant of the copy they were built from. The downloaded file is still deleted, so D-14 there holds. Escalators stay one-way and pedestrian areas are routed along their outline, as Valhalla does. Agent decision at C:40, without asking: it answers both reasons of F-3 at once - the file is used before the import deletes it, and Valhalla routes only on the network M2 admits, never by its own access rules.

D-3. The copy in use. Every route request reads, in its one read-only transaction of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-3 and D-12, the instant of the copy in use, and compares it with the instant of the routing data the service serves; when they differ, the request ends with `routing_unavailable` and no route. A fresh copy is therefore served only after the import has built its routing data and the service has been restarted on it; a new vote, report or geozone needs neither, because it travels in the request (D-5). How the backend learns the instant of the served routing data, and how the service is pointed at new data, is for item 3 of `plans/backend_architecture/`. Agent decision at C:40, without asking: it follows from PRD FR-3, which forbids combining the ways of one copy with the facts of another.

D-4. Walking request. A walking route is a `POST /route` with `costing` `pedestrian` and these costing options: `type` `foot`, `max_hiking_difficulty` 6, `step_penalty` 0, `elevator_penalty` 0, `walkway_factor`, `sidewalk_factor`, `alley_factor` and `driveway_factor` 1.0, `use_living_streets` 0.5, `use_ferry` 0. The pedestrian type `wheelchair` is never sent, because it decides barriers by itself (F-7). Agent decision at C:40, without asking: these are the values the spike measured, neutral toward every barrier the rules of the project decide.

D-5. What the request avoids. The request carries the barriers M2 avoids - those of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-6, read as in D-12 there - as `exclude_locations`, every one with `radius` 0 and `minimum_reachability` 0: a barrier of a stretch at the middle of the longest segment of that stretch with `node_snap_tolerance` 0, and a barrier at an OpenStreetMap node at the coordinates of that node with `node_snap_tolerance` 1 (F-8). A geozone M2 avoids travels in `exclude_polygons` as the polygon of 32 vertices circumscribed about its circle, which covers at most 0.5% of its radius more than the circle. The service is configured with `service_limits.max_exclude_locations` 5000, `service_limits.max_exclude_polygons_length` 1000000 and `service_limits.max_exclude_polygons_vertices` 50000. A request carries only the barriers and geozones that lie within the corridor around the straight line from the start to the destination, wide on each side by a quarter of its length and at least 1000 m; the check of D-9 catches a route that leaves the corridor. A geozone whose circle holds the start or the destination is not sent, because Valhalla then answers no route at all (F-16); the route crosses it, and D-9 reports it as an unavoidable barrier. Agent decision at C:40, without asking: the semantics of the spike re-run of F-8, and the corridor keeps the request within the 5 seconds of PRD FR-4 at 0.25 ms per barrier.

D-6. Alternative. When the route keeps an unverified or disputed barrier of the profile that OpenStreetMap does not contradict, a second request adds those barriers to the excluded locations, and its route is the alternative when its path differs, with the reason of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-7. Agent decision at C:40, without asking: D-7 there, with the weight replaced by an exclusion.

D-7. Route with the fewest barriers. When Valhalla answers error 442 with every avoided barrier excluded, the rules layer finds the path with the fewest avoided barriers on its own graph of the stretches of the copy in use, built from the stored ordered nodes (F-5) with numpy and scipy as `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-14 pins them, with the weight of a stretch equal to the number of avoided barriers and covering geozones on it times 1 000 000 plus its length in metres. One more request then excludes every avoided barrier and geozone except those on that path, and its route is shown with `barrier_free_route_exists` false. The graph is a cache of the copy in use, built when the backend process starts and rebuilt when the instant of the copy changes, as D-3 there decides. When that request fails too, the result is `routing_unavailable`. Agent decision at C:40, without asking: approach B of F-10, the only one measured correct within 5 seconds.

D-8. Tie of a route to the stored stretches. Every route is traced with `POST /trace_attributes`, `shape_match` `edge_walk` and the same costing options as its request, reading for every edge its way identifier, its shape indices and the OpenStreetMap identifiers of its start and end node as the spike read them (F-11); on error 443 the trace is repeated once with `walk_or_snap`. Every edge maps by its way identifier and its two OpenStreetMap node identifiers to a stretch of the copy in use, and the segments, their states of M7, the list of M8 and the amenities within 50 m come from the stored facts as `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-5, D-9, D-10 and D-12 decide. An edge that maps to no stretch of the copy in use ends the request with `routing_unavailable`. The stretch between a chosen point and the point where the route joins the network stays a straight segment in the state no data, with unknown stairs (M2). Agent decision at C:40, without asking: F-11 with `keep_osm_node_ids` of D-2.

D-9. Check before a route is shown. After D-8, the stretches of the route are checked against every barrier and geozone the request had to avoid, read from the database for the whole route and not only for the corridor of D-5. A route that crosses one, other than those D-7 chose or the geozones of D-5 that hold the start or the destination, is requested once more with the crossed barriers added; if it still crosses one, the request ends with `routing_unavailable` and the event is logged at ERROR without coordinates. A route that crosses an unavoidable geozone of D-5 is shown with `barrier_free_route_exists` false and that geozone in `profile_barriers`. Agent decision at C:40, without asking: F-9 can produce a route that looks compliant while crossing a barrier, which would present a barrier as absent (M10).

D-10. Routing unavailable. A request ends with `routing_unavailable` and no route when Valhalla does not answer, answers after 2 seconds for one call, answers any error other than 442 on `/route` and 443 on `/trace_attributes`, or in the cases of D-3, D-7, D-8 and D-9; nothing is ever sent to a routing service outside the project. A request to Valhalla is never retried, except the trace of D-8 and the repeated request of D-9. Agent decision at C:40, without asking: three calls of 2 seconds at most, plus the reads, stay within the 5 seconds of PRD FR-4; it replaces `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-13.

D-11. Logs of the engine. Nothing Valhalla writes about a request holds a coordinate of it: the route work package sets the logging of the service so, and its tests show it on a route request whose start is a known coordinate, by searching the log of the service for that coordinate after the route. Agent decision at C:40, without asking: M2 forbids logging the current location, and what Valhalla 3.9.0 logs at its default level was not measured by the spike, so it is checked, not assumed.

D-12. Public transport, input for the initiative of O9. The routing data with public transport is built by the tools of the image of D-1 from the network file of D-2 and the three feeds of ZTP Kraków, after the rewrite of F-14; a route with public transport is `costing` `multimodal`, departs now in Europe/Warsaw, carries the pedestrian options of D-4 and the exclusions of D-5 for its walking legs and `transit.wheelchair` true, and every walking leg goes through D-8 and D-9. When the multimodal request answers no route, the walking route of D-4 - D-10 is shown with the statement that public transport was unavailable, as the PRD decides in its section Domain rules. A public transport leg is drawn between the coordinates of its boarding and alighting stops (F-16). The interface of that route is first written into `docs/product/api_contract.md` by that initiative (`plans/mvp/MVP_PLAN.md` D-12). Decided by the user in phase B on 2026-10-04 for the fallback and the executor; the rest is an agent decision at C:40, without asking, from F-12, F-14 and F-16.

D-13. Executors. The import work package of `plans/mvp/` builds D-2. The route work package of `plans/mvp/` builds the image of D-1, the configuration of the service of D-1 and D-5, and D-3 - D-11, with the tests of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-16, whose cases still hold, plus a test of D-9 in which Valhalla answers a route crossing an excluded barrier and the request ends with `routing_unavailable`. `plans/deployment_config/` runs the service of D-1 with its data.
