## Decisions

D-1. Preserve the existing public request, response, token renewal, error envelope and logging contract. Do not add a freshness endpoint variant, new error code or anonymous fallback for an invalid token. Adopted from F-2 and F-3. The exact shared session adapter and router-registration seam remain Q-4.

D-2. Read the greatest source-state instant in one read-only transaction using the shared service-account engine. Read only required columns, return a typed value retaining the instant/offset pair, and introduce no freshness cache. No-copy is a successful null date; a database error is the existing `internal_error` response, never a null date. Agent decision at C:40, without asking: F-2, F-4 and the database and architecture standards require truthful current metadata and do not justify a cache for this small read.

D-3. Convert the selected source instant to the Europe/Warsaw calendar day in service using zoneinfo. Define the third-layer presentation constant `OSM_COPY_DISPLAY_ZONE = ZoneInfo("Europe/Warsaw")` in `service/osm_copy.py`, implementing the fixed public rule in F-4. Do not truncate its UTC date, use the original source offset as the display zone or read download/publication time. The API serializes the resulting date as YYYY-MM-DD. The displayed day is independent of the machine zone and the configurable business zone used for server-stamped writes; this read adds no clock or timestamp write. Agent decision at C:40, without asking: the specification already fixes the presentation zone, while skeleton's valid-IANA business setting does not guarantee Warsaw. A named product-rule constant satisfies the third configuration layer without expanding another initiative's settings contract.

D-4. Consume the shared `accessibility_db` model and existing first revision. Add no schema object, grant, private connection factory or alternate SQLAlchemy model. Use the shared `fetch_current_osm_copy` contract approved in D-15 rather than defining two independently maintained current-copy selectors. Coordinate its implementation and file ownership with Mateusz under Q-3. Agent decision at C:40, without asking: F-5 - F-7 and F-12 identify the existing shared storage and overlap.

D-5. Compose synchronous service-layer operations; worker calls service, never importer worker code or data modules. Each provider owns its transaction and resource publication. Do not hold a transaction across download, tile or sample work, and do not add cross-step rollback, automatic retries or a persisted resume cursor. Full manual retry follows F-1. Agent decision at C:40, without asking: this preserves the approved scope and layer direction.

D-6. The common program command is `python -m worker.load_demo`, with `worker/load_demo.py` calling `service/demo_loading.py` through the skeleton's administrative wrapper. Keep `python -m worker.osm_import` as the importer's existing command. The user selected option A for Q-2 on 2026-10-04, approving separate commands for full loading or full manual retry and for an OpenStreetMap-only refresh. This does not authorize changes to the importer's entry point; the wrapper and service binding remain Q-3.

D-7. Execute OpenStreetMap, tiles, samples in that order and stop on the first unsuccessful required step. Mark later steps as not started and retain an overall incomplete result. The user selected option A for Q-1 on 2026-10-04: if OpenStreetMap succeeds and tiles fail, samples are not started and the published OpenStreetMap effects remain. Samples require the published OpenStreetMap prerequisite (F-15). Missing required provider integration must be reported rather than replaced with a successful placeholder.

D-8. Preserve provider outcomes, including unchanged source, busy import, committed database with incomplete pointer publication and unknown commit. A process exit status alone is insufficient to infer those states: the importer's existing command can classify a skipped import as an ordinary exit. Loader exit status is 0 only for complete three-step loading and 1 otherwise, with a typed per-step summary. The user selected option A for exit statuses on 2026-10-04: errors, refused admission and uncertain commits all return 1, while their distinct meanings remain explicit in the summary. For example, an acknowledged OpenStreetMap publication followed by a tile failure returns 1 and retains the committed OpenStreetMap effect. D-10 and D-11 require immediate refusal of a competing run; refused admission cannot count as completed loading. Exact provider mapping, result fields and exclusion completion rules remain Q-3 and Q-5.

D-9. Use the shared administrative run identifier and central logger. Log fixed step identifiers and safe outcome codes, never provider exception text, connection values or contributor records; caught exceptions retain a traceback through central sanitization. No second logging mechanism is added. Agent decision at C:40, without asking: F-10 and the logging standard already establish this infrastructure boundary.

D-10. Permit only one full `load_demo` run at a time. The user selected option A for full-flow concurrency on 2026-10-04: when the first run has completed OpenStreetMap and is loading tiles or samples, a second full run immediately refuses admission, reports that loading is already in progress and starts zero provider steps. It does not wait or retry automatically. Exclusion therefore covers the entire three-step flow rather than only the importer stage. D-11 settles the standalone-import interaction; the shared mechanism and abnormal-loss behavior remain Q-3 and Q-5. This decision does not allocate a lock key or modify Mateusz's entry point.

D-11. Full loading and a standalone OpenStreetMap import mutually exclude each other. The user selected option A for the standalone-import interaction on 2026-10-04: an import attempted while `load_demo` is loading tiles or samples refuses admission immediately, and `load_demo` attempted while a standalone import is active likewise starts no provider steps. The shared exclusion must cover the full admitted operation, not just its OpenStreetMap publication. The admitted loader's own importer service call is part of that same operation and must not compete with its outer guard or release it before tiles and samples finish. Record this as a required shared contract for skeleton and Mateusz to consume; their implementations and Mateusz's ownership remain unchanged by this planning edit. Exact guard attachment, validation, completion and loss behavior remain Q-3 and Q-5.

D-12. Consume the user-approved sample-provider handoff in F-19. Call `apply_sample_data()` synchronously after the successful tile step, with no outer database transaction. Both created and unchanged complete the sample effect. Preserve the provider's counts and stable identifiers, safe failure reason and commit state; an unknown commit remains unknown, and no sample failure implies rollback of earlier committed effects. The provider owns sample insertion, validation and retry safety. Adopted from the approved handoff, without redefining its contract here.

D-13. Use a separate finite execution budget for each required provider step, without an additional full-loader elapsed deadline. The user selected option A for timeout boundaries on 2026-10-04: if loading begins at 08:00 and OpenStreetMap completes at 08:58, the remaining steps receive their own budgets rather than sharing two minutes left from a 60-minute loader budget. Preserve the importer's existing 60-minute whole-import deadline and its nested publication and network limits. Tile and sample total execution budgets, their start points and safe expiration contracts must be concrete before plan closure; provider statement or inactivity timeouts alone do not establish a whole-step budget. Expiration follows D-7 and preserves confirmed or uncertain effects under D-8. Execution-budget expiration does not by itself prove outstanding work has stopped or permit exclusion release; completion and cleanup follow the shared contract still open in Q-5.

D-14. The caller owns admission through skeleton's `apply_import_exclusion` and passes the live `ImportLease` explicitly to the importer service operation. The user selected option A for the guard handoff on 2026-10-04. The importer consumes and validates the supplied lease, without reacquiring or closing the caller's guard. This approves the shared handoff direction, not the remaining importer signature or edits to Mateusz's initiative. Exact lease validation, remaining importer arguments/result and abnormal-loss enforcement still require the shared contracts in Q-3 and Q-5.

## Scope of changes

The verified shared touch points are the new public-operation router registration, the accounts-owned optional-session adapter, the current-copy selector also planned by the importer, the shared engine/configuration/logging/administrative launcher, the provider integrations, and the layer and local-critical-test gates. The copy-date read touches only `osm_copy` metadata and its existing unique source-state index; writes to imported network/facts and sample facts/votes remain inside their owners' service operations. No schema object or environment key is added by this draft. Changes needed beyond these agreed responsibilities return to the user rather than expanding implementation scope silently.

## Risks

- R-1. Shared backend and importer plans remain open. Their proposed callables are not delivery evidence; closing this plan without resolving the integration questions would guess contracts.
- R-2. An unchanged-copy outcome alone may not repair a failed routing pointer. The importer's recovery contract must establish this before a full retry can report success. This initiative does not implement recovery in Mateusz's place.
- R-3. A busy importer or uncertain commit cannot be inferred from a successful process exit. Per-step outcome mapping must preserve their meaning and exclude false full completion.
- R-4. D-10 and D-11 require shared exclusion between full loading and standalone imports across all three stages, but importer-only exclusion cannot provide it. Reacquiring exclusion inside an admitted loader can refuse its own importer step, while releasing the outer guard at importer completion can admit competing work too early. Guard attachment and completion/abnormal-loss rules remain Q-3 and Q-5. No new advisory-lock key is silently allocated.
- R-5. The proposed read module overlaps importer data access. Coordinate the shared selector and edit ownership before either initiative implements it; changes to its signature can affect both consumers.
- R-6. Existing skeleton configuration and local-setup proposals predate the delivered db package and use different environment names and paths. Consume the current db package and require the skeleton to settle its runtime integration rather than copying the old setup.
- R-7. No applied schema, query timing or end-to-end loading has been verified in this phase. Missing Python test dependencies and Node.js/npm currently limit configured checks; no test pass or performance measurement is claimed.
- R-8. Provider statement and read-inactivity limits do not establish a whole-step deadline. The now-closed sample plan and handoff fix statement waits but no total sample budget (F-20); tiles have no technical contract. A loader-side timer cannot safely invent cancellation or rollback semantics. The finite tile and sample budgets selected in D-13 therefore require agreed provider enforcement before implementation, including an explicit sample-provider contract supplement.
- R-9. D-16 deliberately creates and disposes of an engine for each freshness read, preserving service ownership without a new application-wide provider. This incurs connection setup on each request; validate its practical cost locally once the shared factory exists. No query duration or endpoint performance is claimed in this planning phase.
