# Shape: Sample reports and geozones for the demo

Document state: 2026-10-04, interview closed
Regulator: C:40

## Problem

The demo needs marked sample reports and geozones in Czyżyny, near Tauron Arena Kraków, so that the team can demonstrate community contributions and contradictory accessibility information without presenting invented observations as verified facts about a place. The initiative supplies these records and their step of the common loading program, as the existing seed and `MVP.md`, section Initiatives, require.

Mateusz prepares the data for the team members who demonstrate the application and for the common loading program owned by `osm_import`. Loading is triggered manually after schema revisions, independently of application startup (`docs/deployment/hosted_demo.md`, section Loading the data). People using the demo encounter the examples through the existing map, list and fact views.

## Scenarios: input, flow, expected state after the run

1. First loading. Input: the current schema, the imported OpenStreetMap copy and the required sample dataset. Flow: the operator manually starts the common program, which validates the examples and loads their required sample records. Expected state: all four examples are available, marked as samples, with the source and dates required by the specification and an unverified status derived from one fictional author confirmation of weight 0.5 each, as the user decided in Q-2.
2. Contradictory data. Input: S-1 lies on a stretch whose OpenStreetMap attribute explicitly contradicts its poor-surface report, and the report has fewer than 2 confirmation weight. Expected state: the user report remains visible with its status and sample mark, while the route assessment follows OpenStreetMap as M4 and M7 require. Those domain computations remain with their implementation initiatives.
3. Geozone. Input: S-4 is visible and not outdated or hidden, and the profile avoids poor surface. Flow: the existing routing operation evaluates a route through its radius. Expected state: the covered stretches are avoided under M2 and M5. A profile without that barrier does not acquire a new avoidance rule.
4. Repeat after partial loading. Input: samples were successfully loaded, a person later voted on or flagged an example, and another step of the common flow failed. Flow: the operator fixes the failure and manually starts the complete program again. Expected state: the four examples are not duplicated, no initial vote is counted twice, and the person's vote or moderation state and unrelated community contributions remain.
5. Invalid contradiction prerequisite. Input: the selected OpenStreetMap copy lacks the required explicit attribute or the selected report is too far from the pedestrian stretch. Flow: the sample step checks the data. Expected state: the common program receives a visible failure rather than a claim that the demo contradiction is ready; no accessibility conclusion is invented.

## Challenging own assumptions

- Is a seed already an executable plan? No. The initiative has no agreed sample dataset or loading interface, so implementation cannot begin by guessing them.
- Can simplified OSM-shaped data from the mobile mock establish a real contradiction? No. They are synthetic geometry, and M2 requires evidence from the imported source copy.
- Does marking a fact as sample make it confirmed? No. Status is derived from votes under M4; the sample mark is independent of reliability.
- Can the sample loader erase and recreate its rows to avoid duplicates? That would lose user votes or moderation state and contradict the repeat-safe loading behavior already agreed in `osm_import`.
- Does stage 4 prevent preparation now? No. `MVP.md`, section Order and critical path, distinguishes starting from documents from verifying integration after prerequisite delivery.
- Can the loader claim success before the frontend displays the sample mark? Loading and frontend presentation have separate owners. Full AC-17 still needs their joint runtime verification.
