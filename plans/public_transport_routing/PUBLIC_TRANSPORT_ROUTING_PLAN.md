# Plan: Routes with public transport, the optional feature O9

Document state: 2026-10-04, plan in progress

## Goal

Build what `PUBLIC_TRANSPORT_ROUTING_PRD.md` asks for, FR-1 - FR-11 with AC-1 - AC-13, in two stages. Stage 1 needs no code of `plans/route_planning/`: the interface in the contract and the other documents, the copy of the GTFS with the routing data of public transport, and the operation that gives the days of the feeds and whether the switch is shown. Stage 2 joins a route with public transport to `plan_route`: the multimodal request, its walking legs through the checks of `route_planning`, the public transport segment, the walking route when public transport is unavailable, and the alternative. Stage 2 is written into this plan once `plans/route_planning/ROUTE_PLANNING_PLAN.md` names the functions it reuses (D-1), and the plan stays in progress until then.

## Decisions

D-1. Two stages, and the plan stays in progress. Stage 1, S-1 - S-9 below, needs no code of `route_planning`. Stage 2 - the multimodal call, the walking legs through D-8 and D-9 of `VALHALLA_ROUTING_PLAN.md`, the public transport segment of a route, the walking route of PRD FR-4, the alternative, and `route_kind` in `api/route.py` - is written into this plan once `plans/route_planning/ROUTE_PLANNING_PLAN.md` names the functions of D-8, D-9, the walking route and the segment it builds, and the call site of `data/valhalla.py` that the multimodal request must share (F-21). Until then no code of this initiative is written. Decided by Rafał on 2026-10-04 in phase B, against closing stage 1 now with a second plan for stage 2, and against this plan naming the functions `route_planning` would have to expose.

D-2. Kind of route in `plan_route`. The request gets the optional field `route_kind`, `walking` or `public_transport`, `walking` when absent, so a client that does not send it keeps working and a dropped feature leaves nothing to remove from the request. The response gets `public_transport_unavailable`, `true` only when `route_kind` was `public_transport` and the answer is the walking route of PRD FR-4. A segment gets `public_transport`, `null` for a walking segment, and for a public transport segment `{ "vehicle": "tram", "line": "14", "boarding_stop": "Teatr Variété", "alighting_stop": "Cystersów", "departs_at": "2026-10-04T09:12:00.000+02:00", "source": "ztp_krakow_gtfs" }`, an example with stop names the spike reported (F-16), with `vehicle` `tram` or `bus`; such a segment has `state` `no_barrier`, empty `missing_attributes` and `is_marked_wheelchair_no` false, and its `line` runs straight from the boarding stop to the alighting stop (`VALHALLA_ROUTING_PLAN.md` D-12, F-16 there). The client lists each public transport segment as an item of the list of M8 in the order of the route. Agent decision at C:40, without asking: the smallest change of the operation that carries PRD FR-1, FR-3 and FR-4, approved with the rest of the contract by Rafał (PRD FR-7).

D-3. New operation `read_public_transport`, `GET /api/public-transport`, token optional, no request body, answering `{ "is_enabled": true, "feeds": [{ "feed": "GTFS_KRK_T", "published_on": "2026-10-02" }, { "feed": "GTFS_KRK_A", "published_on": "2026-10-02" }, { "feed": "GTFS_KRK_M", "published_on": "2026-10-02" }] }`. `is_enabled` says whether the client shows the switch (PRD FR-8, D-5); `feeds` are the three feeds of the copy in use with the day each was published (PRD FR-6, D-6), empty before the first complete copy. A `plan_route` with `route_kind` `public_transport` while `is_enabled` is false is refused with 409 `public_transport_disabled`. It is a new operation of its own, not a field of `read_osm_copy`, so that each operation has one initiative (`MVP.md`, section How the MVP is built), and `MVP.md` D-12 then counts seventeen operations. Agent decision at C:40, without asking.

D-4. The section Conventions of the contract names the names of stops and lines from the GTFS as a third kind of text in a language in a response, in Polish as the GTFS gives them. Decided by Rafał in the shape, question 4.

D-5. The switch is shown where the environment entry `PUBLIC_TRANSPORT_ENABLED` is `true`; it is optional, `false` when absent, and the team sets it in an environment only after AC-1 of the PRD has passed there, and back to `false` everywhere when the time box ends (PRD FR-8, FR-9). Whether a route with a tram works is a judgement of a person on a run, which the service cannot detect by itself. Agent decision at C:40, without asking.

D-6. The copy of the GTFS. `ROUTING_DATA_DIR/gtfs/<fetched_at epoch s>/` holds `GTFS_KRK_T.zip`, `GTFS_KRK_A.zip`, `GTFS_KRK_M.zip` and `feeds.json`, the day each feed was published; it is written into a temporary directory and renamed into place only when all three files were fetched with status 200, each is a valid zip holding `agency.txt`, `stops.txt`, `routes.txt`, `trips.txt`, `stop_times.txt` and `calendar_dates.txt`, and each response carried `Last-Modified`. The pointer `ROUTING_DATA_DIR/gtfs/current` names that directory and is written through a temporary file and a rename after it. The day a feed was published is the calendar day of its `Last-Modified` in Europe/Warsaw (F-14); a response without it makes the copy incomplete. The download URLs `https://gtfs.ztp.krakow.pl/GTFS_KRK_T.zip`, `GTFS_KRK_A.zip` and `GTFS_KRK_M.zip` are public addresses of the city's data, not of the target environment, and are a constant next to the code that fetches them (F-20). Decided by Rafał in phase B on 2026-10-04 for the day of a feed, against `feed_version` where it is a date and against no days on V-13; the rest is an agent decision at C:40, without asking, following the copy of OpenStreetMap (F-3).

D-7. Preparing a feed. Before the ingest, each feed is unpacked into its own directory of the input of the ingest, and three columns are rewritten, the other files copied unchanged: in `stops.txt`, `wheelchair_boarding` empty or 0 of a stop with a `parent_station` whose value is 1 or 2 takes that value, as the GTFS reference says a child stop inherits it, and otherwise becomes 1; in `trips.txt`, `wheelchair_accessible` empty or 0 becomes 1; in `routes.txt`, `route_type` 900 becomes 0. The value 2 is never changed (F-12, PRD domain rules). Agent decision at C:40, without asking: the rewrite of the spike, made safe for a child stop of a station marked 2, which the spike's rewrite would have made accessible.

D-8. Routing data with public transport. `ROUTING_DATA_DIR/transit/<state_at>_<fetched_at>/valhalla_tiles.tar` is built from `copies/<state_at>/network.osm.pbf` of the copy `current` names and the GTFS copy `gtfs/current` names, by `valhalla_build_config` with `mjolnir.include_platforms`, `mjolnir.keep_osm_node_ids` and `mjolnir.keep_all_osm_node_ids` true and the input and output directories of transit set, then `valhalla_build_timezones`, `valhalla_ingest_transit`, `valhalla_convert_transit`, `valhalla_build_tiles` and `valhalla_build_extract`, each with a timeout. The modification time of the tar is set to the instant of the copy, so the check of F-3 accepts it. The pointer `ROUTING_DATA_DIR/transit/current` names the directory and is written through a temporary file and a rename. A directory is never changed after its pointer is written. Agent decision at C:40, without asking: the build is one full build of the network with transit (F-11), kept out of `copies/` so that the files of a copy stay unchanged (F-3).

D-9. What the routing service serves. At start it serves `transit/<state_at>_<fetched_at>/valhalla_tiles.tar` when `transit/current` names a directory whose `<state_at>` equals the one `current` names, and `copies/<state_at>/valhalla_tiles.tar` otherwise, so a walking route always has data of the copy in use and a route with public transport never has data of another copy. The start of the service belongs to `route_planning` and `plans/deployment_config/` (F-5); this rule is written into `docs/deployment/hosted_demo.md`, section Loading the data, and handed to them in S-8. Agent decision at C:40, without asking.

D-10. The step of the loading program. The command `python -m worker.gtfs_import`, run after `python -m worker.osm_import` in the same one-off container of the backend image (F-4, F-6), with the modules `worker/gtfs_import.py` -> `service/gtfs_import.py` `apply_gtfs_import() -> int`, run through `apply_administrative_run` (F-2), -> `data/gtfs_source.py` `fetch_gtfs_feed(feed: str, target: Path, deadline: Deadline) -> FetchedFeed`, `data/gtfs_copy.py` `apply_gtfs_copy(...)`, `fetch_gtfs_copy() -> GtfsCopy | None`, `apply_gtfs_pointer(...)`, and `data/transit_build.py` `apply_transit_build(...)`, `apply_transit_pointer(...)`. The fetch uses the standard library HTTP client with a connection timeout of 30 s and a read inactivity timeout of 30 s, as the importer does (`OSM_IMPORTER_PLAN.md` D-18), and the whole run 30 minutes; nothing is retried, because a person runs the command again (F-21). A failed fetch keeps the last complete copy, and the build still runs from it when the copy of OpenStreetMap changed; with no complete GTFS copy at all nothing is built. The command ends with 0 when `transit/current` names the copy `current` names, and with 1 otherwise. Agent decision at C:40, without asking.

D-11. `ROUTING_DATA_DIR` and `PUBLIC_TRANSPORT_ENABLED` are added to `config/config.py`, `config/settings.py`, the templates and `docs/standards/standard_config.md`, section Environment entries, together (F-2); `ROUTING_DATA_DIR` is reused as it stands when `osm_importer` added it first. Agent decision at C:40, without asking.

D-12. The specification, the registry, `MVP.md`, `docs/deployment/hosted_demo.md` and `docs/product/views.md` are written by this initiative before `route_planning` writes the same files, and `route_planning` writes on top of them.
