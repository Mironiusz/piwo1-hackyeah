## Decisions

D-1. The search is answered by the public Nominatim instance of the OpenStreetMap Foundation at `https://nominatim.openstreetmap.org/search`. Decided by the user with the external API person on 2026-10-03, against the public Photon instance, a commercial provider with an API key and an own Nominatim instance (F-9, F-10).

D-2. The search is a read from an external system during request handling, so it is recorded as the explicit exception of `docs/standards/standard_architecture.md`, section Calls to external systems (F-14): without the outside answer the search request cannot be handled at all. It has one call site in the data layer and one seam in the rules layer, which the input layer calls, and the blocking outgoing call runs from request handling through a thread pool, as that section requires. The names of these modules and functions are decided in `plans/mvp/MVP_PLAN.md` together with the backend architecture (Q-10, F-21), following `docs/standards/standard_naming.md`, because naming them here would guess that architecture. Agent decision at C:40, without asking: it follows from the scope of the PRD and from the standard.

D-3. The text travels from the browser to the server only in the body of a POST request, never in the path or the query string of a URL, and the frontend never puts it into the address of the page. An access log of the HTTP server or of the hosting records the URL but not the body, so this keeps the text out of every such log (PRD FR-7). The path and the JSON shape of the request and the response are decided by `plans/api_contract/` under this constraint. Agent decision at C:40, without asking: the URL is the part of a request that every access log records.

D-4. Before the cache lookup and the outgoing request, the server normalizes the text: it trims it, collapses every run of whitespace into one space, and removes the standalone words "ul." and "ulica" in any letter case (F-5). Nothing else is rewritten. A text longer than 200 characters as received, checked before normalization, or empty after normalization is a caller error, answered without any outgoing request. Agent decision at C:40, without asking: these two prefixes are the only ones the check of F-5 showed to break the search, and the length limit keeps one request from carrying an arbitrary payload to the outside service.

D-5. The outgoing request is a GET of `/search` with exactly these parameters: `q` with the normalized text, `format=jsonv2`, `addressdetails=1`, `limit=10`, `countrycodes=pl`, `viewbox=19.7922355,50.1261338,20.2173455,49.9676668`, `bounded=1` and `accept-language=pl`, and with the header `User-Agent: piwo1-hackyeah (HackYeah 2026 accessibility prototype)`. It carries no cookie, no header forwarded from the request of the person - in particular nothing with the IP address of the person - and no identifier of an account (PRD FR-6). The viewbox is the bounding box of the administrative boundary of Kraków (F-1). Agent decision at C:40, without asking.

D-6. Only results whose `address.city` equals `Kraków` are kept, and a result without that field is dropped (F-3). The viewbox alone lets in Niepołomice and Wieliczka. Agent decision at C:40, without asking: dropping a result without the field can only lose a match, never set a point outside Kraków.

D-7. Each kept result becomes a match with three values: a label, the latitude from `lat` and the longitude from `lon`, in the order the service returned them. The label joins with ", " the parts that are present, in this order: `name`, when it is not empty and differs from `address.road`; `address.road`, followed by a space and `address.house_number` when the number is present; the first present of `address.quarter`, `address.suburb` and `address.city_district`; `address.postcode` followed by a space and `Kraków`, or `Kraków` alone when there is no postcode. From F-2 and F-7 this gives "Tauron Arena Kraków, Stanisława Lema 7, Czyżyny, 31-571 Kraków", "Lipska, Płaszów, 30-716 Kraków", "Biedronka, Kozłówka, Kraków" and "Floriańska 1, Stare Miasto, 31-019 Kraków". Nothing else from the response is passed on. Agent decision at C:40, without asking: the label of the service itself ends with the province, the postcode and the country, which a screen reader would read out for every item, while the district and the postcode are what tells two places of the same name apart (PRD FR-3).

D-8. Answers are kept in a cache in the memory of the server process. The key is the normalized text in case-folded form, and the value is the list of matches after D-6 and D-7, an empty list included, because nothing found is an answer. A failed search is never stored (PRD FR-8). An entry lives at most 24 hours, and the cache holds at most 1000 entries, dropping the oldest first. The cache is written with the standard library, without a new dependency. Agent decision at C:40, without asking: `docs/standards/standard_architecture.md` requires an explicit time to live (F-14), and the demo environment lives less than a day (F-19), so in practice an entry lives as long as the process, as the shape decided.

D-9. One gate for the whole process lets at most one outgoing request start per 1.1 seconds, and a search that does not get its turn within 3 seconds ends as unavailable without sending anything (PRD FR-9, AC-9). The 0.1 seconds above the limit of the policy absorbs the jitter of timing. Agent decision at C:40, without asking.

D-10. The outgoing request has a timeout of 5 seconds for the whole call and is not retried (F-14, F-16). The slowest of the 20 searches of F-8 took 1.54 seconds, and the person retries by submitting the search again. Agent decision at C:40, without asking.

D-11. A search ends in one of three outcomes: a non-empty list of matches; an empty list, meaning nothing found in Kraków; or the named exception of the integration, meaning the search is unavailable. That exception covers a timeout, a connection error, any status other than 200 - 403 for a blocked server address and 429 for an exceeded limit included - a body that is not the expected JSON, and no turn within the gate of D-9. The input layer turns it into a response distinct from an empty list, whose shape `plans/api_contract/` decides, and the frontend shows the search unavailable message for it (PRD FR-5). Agent decision at C:40, without asking: one named exception is enough, because the person gets the same message for every cause, and the cause goes to the log (D-12).

D-12. No log entry contains the text, the normalized text, the URL of the outgoing request, the response body or the coordinates of a match. The integration uses no helper of the HTTP client that puts the URL into an exception message, and the message of its own exception carries only the cause and the status code. An error entry carries the cause, the status code and the elapsed time (F-15). The request logging of the HTTP client is switched off for this call or kept above the INFO level, because httpx, for example, logs every request with its URL at INFO (F-12), and INFO is the default level of the project (F-17). The MVP work package proves it with a unit test that captures the log at the DEBUG level for each outcome of D-11 and asserts that the searched text appears in no record, formatted tracebacks included. Agent decision at C:40, without asking: it follows from PRD FR-7 and from the personal data rule of `docs/standards/standard_logging.md`.

D-13. The base address of the service, the User-Agent, the viewbox, the timeout and the limits of D-4, D-8 and D-9 are constants of the third configuration layer, next to the code of the integration: they are the same in every environment, used in one place, and none of them is a secret (F-17). No environment entry is added. Agent decision at C:40, without asking.

D-14. The results are OpenStreetMap data under the ODbL, which the response itself states in `licence` (F-2), so the OpenStreetMap attribution that `plans/mvp/MVP_PRD.md` FR-9 already requires on the map (F-22) also covers the search (PRD FR-9). Agent decision at C:40, without asking.

D-15. The cache of D-8 and the gate of D-9 live in the memory of one process, so the backend that answers the search runs as exactly one process in the demo environment. With N processes the outgoing rate could reach N requests per second, against the policy (F-10). This is handed to `plans/demo_environment/` as a constraint. Agent decision at C:40, without asking: it follows from the cache in memory decided in the shape and from the policy.

D-16. The MVP work package adds these tests under `docs/standards/standard_tests.md`, none of them using the real network (F-18): unit tests of the normalization of D-4, the filter of D-6, the label of D-7, the cache of D-8 - a hit, a miss, a failure not stored, an expired entry - the gate of D-9 and the classification of D-11 for every cause, with the transport of the HTTP client replaced by a fake; the log test of D-12; and an integration test of the search endpoint for a list, an empty list, the unavailable response and a caller error. One manual check follows the first deployment: a single search from the hosted service returns a list, which shows that the address of the hosting is not blocked. Agent decision at C:40, without asking.

## Risks

- The hosting may send outgoing requests from an address the public Nominatim instance already blocks. The search then ends as unavailable (D-11) for the whole demo, and only the map is left for giving a place. The manual check of D-16 finds it after the first deployment, not earlier, because the hosting is not chosen yet.
- The public instance is the single outside dependency of the search during the live demo, and it may be slow or down at 11:00 on 4 October 2026.
- If the hosting of `plans/demo_environment/` runs more than one process, for example by scaling automatically, D-15 breaks and the policy limit can be exceeded.
- A name combined with an address finds nothing (F-6). The person gets the nothing found message and can search for one of the two parts; the demo script should search for one of them.
- A house number unknown to OpenStreetMap falls back to the street (F-7). The label then has no number, so the person sees that the match is the street, not the house.
- The OpenStreetMap Foundation keeps the requests for an unknown time (F-11). The text reaches it without anything identifying the person (D-5), which the shape accepted.
- The description of the data sources in the Kraków submission has to name the public Nominatim instance next to OpenStreetMap; no such document exists in the repository yet.
- If `plans/mvp/` decides to show the place of an item in the list for a route (F-22) as a street address, it needs the opposite direction of the search for every item, which multiplies the requests against the limit of 1 per second; the PRD leaves it out and it needs its own decision.
