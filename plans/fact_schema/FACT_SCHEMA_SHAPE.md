# Shape: Domain model and database schema of facts and votes for the MVP

Document state: 2026-10-03, interview closed
Regulator: C:40

The request carries no regulator value, so the default C:40 applies; the agent named it in question 1 of the seed and the user did not change it.

## Problem

Every requirement of the MVP that touches a barrier or an amenity - reports, confirmations and denials, statuses, geozones, the OpenStreetMap facts, the segment states, accounts and moderation - reads or writes the same data, but nothing says yet what that data is: which things exist, what identifies each of them, and which states and transitions they have. Without it the programming interface (`plans/mvp/MVP_PLAN.md` Q-9) cannot name its resources and statuses, and the import, the route and the voting would each guess the shape of a fact on their own. `plans/mvp/MVP_PLAN.md` names Q-10 the start of the critical path Q-10 -> Q-9.

## Current state

- No product code and no database schema exist, and the repository keeps no schema dump (`docs/standards/README.md`, section Mapping, lists none). The backend is Python 3.13 with FastAPI on PostgreSQL with PostGIS (`plans/mvp/MVP_PLAN.md` D-1). The local database environment is still open (`plans/local_database/`, Q-4).
- `docs/standards/standard_database.md`: every schema change is an Alembic revision with raw SQL, reviewed "line by line" against "the DDL written in the product specification"; integrity constraints, uniqueness included, are required, because the backstop against duplicates must live in the database.
- `docs/standards/standard_time.md`: every point in time is stored as an instant with the zone offset in force at the moment of writing.
- What the specification, version 2, says the data holds (`docs/product/specification.md`):
  - M3 - a user report is a point with a type from the closed list, an optional description and, for stairs, an optional number of steps; a saved report is not edited by anyone.
  - M4 - every fact, OpenStreetMap facts included, gets confirmations and denials; weights 1 for an account and 0.5 without one, the author of a report included; the statuses unverified, confirmed, disputed and outdated derived from the sums; one vote per fact per account or per hashed identifier; a status never changes with time alone.
  - M5 - a geozone is a point with a radius from a list and a barrier type, judged with the mechanism of M4, not edited after saving.
  - M6 - the date of the OpenStreetMap copy in use is shown.
  - M9 - an account is a pseudonym and a password; a vote without an account keeps a one-way hash of the IP address with browser characteristics, deleted after 30 days; deleting an account removes the account, the pseudonym and the points, while reports and votes stay detached and keep their weight; nobody else sees anything about the author.
  - M10 - every fact shows its source, the date it was obtained or last confirmed and its status; sample data is marked as such.
  - M11 - anyone can flag a report, a geozone or a photo; a moderator, assigned by hand, can hide it, and hidden content disappears for everyone.
- Inputs settled in two closed shape interviews of 2026-10-03, quoted in `plans/mvp/MVP_PLAN.md` Q-10. From `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, section Domain rules: an OpenStreetMap fact keeps the identity of its OpenStreetMap element and its fact type; a fact missing from a fresh copy becomes a user fact with its votes when its confirmations outweigh its denials, and otherwise becomes outdated with the reason that it was removed in OpenStreetMap, its votes kept in its history; a returning fact on the same element with the same type is the same fact again with all its votes; an OpenStreetMap fact and a user fact of the same type at the same place are never merged. From `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_SHAPE.md`, section Domain rules: the mapping turns tags into present, absent or unknown for each barrier once, independently of the profile; OpenStreetMap contradicts a user report only through an opposite fact of the closed list or an explicit tag value on the passable side, never through a missing tag.
- Caveats on these inputs, from `plans/mvp/MVP_PLAN.md` Q-10: they enter the specification only in version 3, not written yet, and the rules of `plans/osm_data_source/` were given by the user on behalf of the import person, whose ruling is still to be confirmed.
- Two points handed to this initiative by `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`: whether a vote without an account keeps its weight after its 30-day identifier is deleted, and what counts as the same OpenStreetMap element when OpenStreetMap splits, joins or recreates a way.
- A defect reported to the user in `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_SHAPE.md`, section Out of scope, and not settled since: the M4 rule "disputed when neither rule applies" gives confirmed at the fourth step of scenario 3 of `plans/mvp/MVP_SHAPE.md` (confirmations 2.0, one denial), while that scenario and AC-6 of `plans/mvp/MVP_PRD.md` expect disputed.
- The Kraków submission closes at 11:00 on 4 October 2026 (`docs/hackathon/challenge_requirements.md`, Shared facts).

## Functional requirements

The model has to hold what these requirements of `plans/mvp/MVP_PRD.md` read and write:

1. FR-5 - a point report with its type, optional description and optional number of steps, never edited after saving, and the lookup of facts of the same type within about 15 m, OpenStreetMap facts included.
2. FR-6 and FR-7 - confirmations and denials of every fact with their weights, the vote limit of one person per fact and the window of the last k persons (question 5), and the statuses derived from them.
3. FR-8 - a geozone as a point with a radius and a barrier type, with votes and statuses like a point report.
4. FR-9 - the OpenStreetMap facts of the last fetched copy, and the date of that copy.
5. FR-10 and FR-11 - what is known about each barrier on each stretch of way, so that the route can derive the segment state and name the missing attributes.
6. FR-12 and FR-13 - accounts with a pseudonym and a password, contributions without an account with an identifier deleted after 30 days, and the detachment of contributions from a deleted account.
7. FR-14 - flags, the moderator role and hidden content.
8. FR-15 - the source, the date and the status of every fact, without anything about its author or the weights reaching other users.
9. FR-18 - the sample data mark.
10. The rules of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`: conversion, outdating with a reason, and the return of an OpenStreetMap fact with all its votes.
11. The first schema revision that creates this model, with its tests, in the form of `docs/standards/standard_database.md` (question 1).
12. The target schema written in `docs/product/schema.md`, which `docs/product/specification.md` declares part of itself, so that the revision is reviewed against it (question 2).

## Scenarios: input, flow, expected state after the run

The model has to be able to run these scenarios already decided elsewhere, without restating them: scenarios 3 and 5 of `plans/mvp/MVP_SHAPE.md` (status run, denying an OpenStreetMap fact) and scenarios 1 to 3 of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md` (conversion, outdating, return).

1. A vote without an account expires. Input: stairs at G. Flow: 1 October an anonymous report of stairs at G (0.5); 3 October three anonymous confirmations (2.0); 3 October 12:00 the browser of one of them, on the same network, tries to confirm G again; 31 October the identifier and the vote of the report's author expire; 2 November the three confirmations expire. Expected state: on 3 October G is confirmed and avoided by a wheelchair route, and the repeated confirmation is refused; on 31 October G is unverified with 1.5 and no longer avoided; on 2 November G is unverified with 0, and the report itself still exists. Decided by the user on 2026-10-03 (question 3).
2. Anonymous denials of an OpenStreetMap fact expire. Input: OpenStreetMap stairs at S. Flow: 1 October three anonymous denials (1.5) and one logged-in denial (2.5), and S is outdated; 31 October the three anonymous denials expire. Expected state on 31 October, with k of at least 4 (question 5): the denials weigh 1, below the sum of 2, so S prevails again and is on the map and the route. Decided by the user on 2026-10-03 (question 3), with this run shown before the confirmation.
3. A person votes again and changes their mind. The values x = 7 days and k = 5 are illustrative only, the real ones are configuration (question 5). Input: stairs at F. Flow: 1 October 10:00 account U reports stairs at F (1); 1 October 10:01 U confirms F again; 2 October anonymous A confirms (1.5); 3 October account B confirms (2.5); 8 October 10:00 U, seeing a ramp instead, denies F; 9 October anonymous C and account D deny F; 10 October anonymous E denies F. Expected state: on 1 October 10:01 the second vote of U is refused, because x days have not passed, and F is unverified with 1; on 3 October F is confirmed; on 8 October only the latest vote of U counts, so F has 1.5 of confirmations (A, B) and 1 of denials (U) and is disputed; on 10 October the window holds the latest votes of the five persons who voted most recently - U, C, D, E as denials and B as a confirmation, while A has fallen out of the window - so the denials weigh 3, reach 2 and outweigh the confirmation of 1, and F is outdated. Decided by the user on 2026-10-03 (question 5 and its follow-ups); the status at each step follows the rules of `docs/product/specification.md` M4 applied to the window.

## Challenging own assumptions

- Do OpenStreetMap facts have to be stored as facts at all, or could they be read from the OpenStreetMap copy when needed? They have to be stored: they carry votes, and a fact that disappears and returns keeps those votes (`plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, scenario 3), so its identity has to outlive any single copy.
- Is a geozone a separate thing or a kind of fact? `docs/product/specification.md` M5 gives it a barrier type and judges it "with the mechanism of M4", so it has votes and statuses like a point report and differs in its area. Recorded without asking as an answer found in the specification; how it is stored is phase B.
- Is the author's report also a vote? M4 says the weights apply "the author of the report included", and scenario 3 of `plans/mvp/MVP_SHAPE.md` starts at 0.5 after an anonymous report alone, so a report carries the author's confirmation, and the author votes on it again only under the vote limit of question 5. Recorded without asking as an answer found in the specification and the scenario.
- Is Q-10 really independent of the routing engine (Q-1)? The facts are tied to OpenStreetMap elements, and the route needs to know which facts lie on its segments. That holds whatever the engine is, as long as the route can be related to OpenStreetMap ways or to positions; how is a question of `plans/routing_engine/`, not of this model. To be checked against that initiative when it closes, not assumed.
- Does the window of k persons break the conversion of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`? No: the conversion compares confirmations and denials, and it now compares those in the window, the same sums the status uses. Its scenarios 1 and 3 keep their results as long as k is at least 3, because their votes come from different persons.
- Does a status that changes when anonymous votes expire break "Missing information is never presented as a confirmation of accessibility" (`docs/product/specification.md`, M10)? When anonymous denials of an OpenStreetMap barrier expire, the barrier returns (scenario 2), which is the safe direction. When anonymous confirmations of a user barrier expire, the barrier stays as unverified and, unless OpenStreetMap contradicts it, its segment stays red (M2), so a barrier never becomes a confirmation of accessibility by expiry.
- Is the status computed on every route a cost problem (blocking category query volume and cost)? The number of rows can be estimated: OpenStreetMap facts of Kraków in the order of tens of thousands, user facts in the demo in the order of tens, and at most k counted votes per fact. Whether statuses are derived on read or kept up to date on write is phase B, measured on the first import, not a product question. Agent decision at C:40, without asking.

## Domain rules or explicit TODO

- A vote without an account is deleted together with its identifier 30 days after it was cast, and from then on it counts for nothing: the sums, the statuses and the conversion of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md` count only the votes that still exist. A status can therefore change when an anonymous vote expires, in both directions (scenarios 1 and 2). Votes of an account never expire, also after the account is deleted (`docs/product/specification.md`, M9). Decided by the user on 2026-10-03 (question 3), against keeping the weight of an expired vote and against keeping the identifier as long as the vote; the agent showed beforehand that it contradicts the specification, and the user confirmed it together with the change below.
- This changes `docs/product/specification.md` in version 3: M4 ("A status does not change with time alone") and the section Out of scope ("Statuses that change with time alone") get the exception of an expired vote without an account, and M9 says that the vote is deleted with its identifier. Decided by the user on 2026-10-03 (question 3); the approval of the specification change itself stays with the user, as for the other rules of version 3.
- The report of an author without an account stays after the author's vote expires, as a fact without that vote: a report is content, the author's confirmation is a vote (section Challenging own assumptions), and `docs/product/specification.md` M9 keeps reports also after an account is deleted. Agent decision at C:40, without asking: a consequence of question 3.
- A person - an account, or a hashed identifier for a vote without an account - can vote on a fact again once x days have passed since their previous vote on that fact; an earlier vote is refused. Of the votes of one person on a fact only the latest counts, so a person can change their mind or refresh a confirmation, but never adds weight by voting again. This replaces "One person has one vote per fact" of `docs/product/specification.md` M4. Decided by the user on 2026-10-03 (question 5 and its follow-ups), against a vote that is final, against counting every vote of a person in the window, and against keeping one changeable vote per account without a limit.
- The status of a fact is derived from the latest votes of the k persons who voted on it most recently, with the weights and the thresholds of `docs/product/specification.md` M4 unchanged; older votes fall out of the window, so fresh votes decide. Decided by the user on 2026-10-03 (follow-ups to question 5).
- x and k are configuration values. The db person proposes them in phase A of the PRD of this initiative and the user approves them; until then the code works with default values held in configuration. Decided by the user on 2026-10-03 (follow-up to question 5), against fixing them in this shape. Two facts for the proposal, recorded without asking as arithmetic of the rules above: with k below 4, votes without an account alone can never reach the sum of 2 (3 x 0.5 = 1.5); and for a hashed identifier, an x of 30 days or more acts as 30, because the identifier and the vote are deleted after 30 days (question 3).
- The window and the vote limit apply to every fact, OpenStreetMap facts and geozones included, because `docs/product/specification.md` M4 applies its votes to every fact and M5 judges geozones with the same mechanism. So the sum of 2 at which denials overturn an OpenStreetMap fact, and the comparison of confirmations and denials in the conversion of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, are counted in the window. Agent decision at C:40, without asking: a consequence of the rules above.
- The author of a report is a person like any other: the report carries the author's vote, and the author can vote on their own report again after x days, a denial included. Agent decision at C:40, without asking: a consequence of the rules above and of section Challenging own assumptions.
- A vote cannot be withdrawn without casting another; the user's rule names only a new vote. Agent decision at C:40, without asking, taken from the answer to question 5, which replaced the offered option of withdrawing.
- Earlier votes of a person and votes outside the window are kept as history, as `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md` keeps the votes of an outdated fact in its history; they only stop counting. A vote without an account is still deleted after 30 days (question 3). Agent decision at C:40, without asking.
- This changes `docs/product/specification.md` in version 3 in M4 (one vote per fact), and `plans/mvp/MVP_PRD.md` in AC-6 ("A second confirmation of the same fact by the same account is refused" becomes refused within x days). AC-12 and scenarios 3 and 5 of `plans/mvp/MVP_SHAPE.md` keep their results as long as k is at least 4, because each of their votes comes from a different person. Agent decision at C:40, without asking, as a consequence; the approval of the changes stays with the user.
- A vote of a deleted account stays with its weight and keeps no link to any person, so a person who deletes an account and creates a new one can vote again on the same fact, and both votes count. Source: `docs/product/specification.md` M9 ("Reports and votes stay, detached from the person, and keep their weight") together with accounts without an email address, under which the system cannot tell one person with two accounts from two people anyway. Recorded without asking as an answer found in the specification (question 4).
- The identity of an OpenStreetMap fact is the type of its OpenStreetMap element (node or way), the identifier of that element and the fact type. When OpenStreetMap splits a way, the part that keeps the identifier keeps the fact with its votes and the other part gets a new fact without votes; when it joins ways or recreates one, the fact on an identifier that disappeared follows the conversion or outdating of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, which can leave a converted user fact next to an OpenStreetMap fact of the same barrier, never merged (`docs/product/specification.md`, M3). Decided by the user on 2026-10-03 (question 6), accepting these effects for the MVP, against carrying votes to a new element by matching its geometry. The risk is negligible in the MVP, where the import runs by hand and once before the demo, and is described in the plan from prototype to service, next to the regular refresh of `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`. This closes the TODO of that shape.
- A hidden fact is out of everything for everyone: it is not on the map or the list, does not affect the route or a segment state, does not take part in the duplicate check within about 15 m, and cannot be voted on. Its data and votes stay in the database, and a moderator can restore it, after which it counts again with the votes it still has; anonymous votes on it expire after 30 days as everywhere (question 3). Decided by the user on 2026-10-03 (question 7), against irreversible hiding and against hiding only from view, which would leave a red segment without a visible barrier against `docs/product/specification.md` M10. Restoring widens M11 ("can hide it") and enters version 3 of the specification with the other changes.
- What can be flagged and hidden is what `docs/product/specification.md` M11 names - a report, a geozone and, with O2, a photo; a fact converted from OpenStreetMap counts as a report, because it is shown as a user report (`plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, section Domain rules), while an OpenStreetMap fact cannot be flagged. A flag stores nothing about who flagged, because the specification asks for nothing that would need it. Agent decision at C:40, without asking: following M11 and keeping personal data to what a rule needs.
- The status of a fact is derived in this order: outdated when the denials in the window reach at least 2 and outweigh the confirmations; otherwise disputed when the window has both confirmations and denials; otherwise confirmed when the confirmations reach 2; otherwise unverified. A single denial therefore turns a confirmed fact into disputed until it falls out of the window or the denials make it outdated. Decided by the user on 2026-10-03 (question 8), keeping scenario 3 of `plans/mvp/MVP_SHAPE.md` and AC-6 of `plans/mvp/MVP_PRD.md`, against the wording of `docs/product/specification.md` M4, which version 3 corrects. This settles the defect reported in `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_SHAPE.md`, section Out of scope.
- What is known about each barrier on each stretch of way is stored as the result of the tag mapping of `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_SHAPE.md` - present, absent or unknown, once and independently of the profile. The segment state is not stored: it is derived for each route from that result, the profile carried by the route request and the user facts, because the profile never reaches the server outside the route request (`docs/product/specification.md`, M1). Agent decision at C:40, without asking: a consequence of those two rules.
- The model also holds what the specification names without leaving a choice: the date of the OpenStreetMap copy in use (M6), the date of the last OpenStreetMap edit of an OpenStreetMap fact and the date of the last confirmation of every fact (M4, M10), the optional number of steps of a stairs report (M3), the moderator role of an account, assigned by hand (M11), and the sample data mark of a report or a geozone (M10). Recorded without asking as answers found in the specification.
- A vote of a deleted account counts as the vote of a person of its own in the window, since nothing ties it to anyone any more (`docs/product/specification.md`, M9). Agent decision at C:40, without asking: a consequence of question 5 and M9.
- A pseudonym is unique without regard to letter case, so that two accounts cannot log in under names that differ only in case; the pseudonym of a deleted account is free to take again, because nothing keeps it (`plans/mvp/MVP_PRD.md`, AC-11). The moderator view shows nothing about the author either, because `docs/product/specification.md` M9 hides the author from every other user and no moderator action of M11 needs it. Agent decision at C:40, without asking; to be corrected by the user if wrong.
- The radius of a geozone is chosen from 10, 25, 50 and 100 m, the list `docs/product/specification.md` M5 gives as an example. Agent decision at C:40, without asking: the specification names no other list, and a closed list is what lets the database refuse any other value; to be corrected by the user if wrong.
- The 30 days run from the instant of the vote, not from calendar days in the Europe/Warsaw zone. Agent decision at C:40, without asking: the identifier is a retention period, not a date shown to anyone, so the display rule of `docs/product/specification.md` M10 does not apply to it; the difference is at most one hour around a change of the clock.
- The target schema - tables, columns, indexes and constraints as DDL - lives in `docs/product/schema.md`, a separate file that `docs/product/specification.md` declares part of the specification. It is the target state against which a revision is reviewed line by line, as `docs/standards/standard_database.md` requires, while the specification itself stays a description of product behavior. Decided by the user on 2026-10-03 (question 2), against a section with the DDL inside `docs/product/specification.md` and against changing `docs/standards/standard_database.md` so that it no longer points to the specification. A change of the file is approved like a change of the specification, by the user (`docs/product/specification.md`, section Decision provenance); agent decision at C:40, without asking, as a consequence of the file being part of the specification. `docs/standards/README.md`, section Mapping, names the file in its row about tables and columns.

## Notes on data, performance and security

- The identifier of a vote without an account is pseudonymized personal data, not anonymous data in the sense of the GDPR (`plans/mvp/MVP_PRD.md`, Risks and notes).
- Expiry of anonymous votes needs something that deletes them on time; when and how it runs is the worker of `plans/mvp/MVP_PLAN.md` Q-11, not this model. Until it runs, an expired vote still counts, so the delay of that job is a delay of the status change.
- One person with two accounts confirms a fact alone, because two logged-in votes reach the sum of 2 (question 4). The specification names no protection against this, and none is added here; it is a risk to name in the presentation, not a rule of this model.
- A person who sees that a barrier is gone shortly after confirming it cannot deny it until x days have passed; others can. This is the cost of the vote limit (question 5).
- The optional description of a report is free text that other users see, so it can carry personal data; moderation (M11) is the only control the specification names.
