Document state: 2026-10-03, plan in progress

## Goal

## Decisions

D-1. The backend is Python 3.13 with FastAPI, on PostgreSQL with PostGIS. The Python profile of the standards stays in force in full. Decided by the user on 2026-10-03 in phase B, against three alternatives: Python with plain PostgreSQL, TypeScript full-stack, no own backend.

D-2. Every remaining technical direction of this plan is decided in its own initiative by the team role responsible for it, not in this plan. Decided by the user on 2026-10-03 in phase B; the initiatives and their owners are listed in the entry Technical directions of the MVP plan of `docs/standards/decision_registry.md`, each settled direction in the decision of this plan that names its initiative, D-3 - D-12, and the one still open, Q-11, under Open questions, and the conversation is recorded verbatim in their seeds. The assignment of initiatives to the five team roles named by the user - frontend, db, import, external API, backend - was made by the agent at the user's request.

D-3. Address search, settling the former Q-5. The search is answered by the public Nominatim instance, called only by the server, with the rules, parameters and tests of `plans_finished/geocoding/GEOCODING_PLAN.md` D-1 - D-16. Constraints for the rest of this plan: the search is the explicit exception of a read from an external system during request handling (D-2 there), its text travels only in the body of a POST request (D-3 there), the backend runs as exactly one process (D-15 there), and the work package of the search includes the tests of D-16 there. Decided by the user with the external API person on 2026-10-03 in `plans_finished/geocoding/`.

D-4. Source of the OpenStreetMap data and its refresh, settling the former Q-2. The copy is the Geofabrik extract of Małopolska, cut to the administrative boundary of Kraków, read with pyosmium, fetched once before the demo and refreshed only by hand, with the rules, parameters and tests of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-1 - D-22. Constraints for the rest of this plan: a refresh is an administrative run, never part of request handling, and two runs never overlap (D-11 there); a fresh copy, its reconciliation with the stored facts and its date become visible in one commit or not at all, and D-11 stores the copy under that constraint (D-9 there); the identity of an OpenStreetMap fact is the type and OpenStreetMap identifier of its element together with its fact type, with no matching by geometry (D-7 there), and the reconciliation of every refresh follows D-10 there; Q-11 decides the form of the trigger and the machine the run executes on, using the measurements of F-4, F-10 and F-11 there; the routing engine of D-9 takes the facts and the segment states from this copy under the condition of D-17 there; and the work package of the import includes the tests of D-22 there. The facts for the description of the data sources are D-19 there. The rules of FR-7 - FR-11 of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PRD.md` enter `docs/product/specification.md` version 3, written by `plans_finished/osm_barrier_mapping/` (D-20 there). Decided by the user, answering for the import person, on 2026-10-03 in `plans_finished/osm_data_source/`.

D-5. Mapping of OpenStreetMap tags to the closed list of barriers and amenities, settling the former Q-8. The tag rules, thresholds and value lists are those of `docs/product/specification.md` version 3, M6, with the segment rules of M7 and M8 and the contradiction of M2, applied as `plans_finished/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6 - D-17 decide. Constraints for the rest of this plan: the import applies the rule once per element, independently of the profile, and keeps for every barrier of a way one of the states present, absent, absent by default and unknown (D-6 there), so that the route can tell an explicit absence, which contradicts a report, from the default of no stairs, which does not; the thresholds and value lists are constants of the third configuration layer next to the code of the rule (D-14 there); the import and route work packages include the tests of D-17 there. Decided by the user on 2026-10-03 in `plans_finished/osm_barrier_mapping/`; the import person confirms or changes the thresholds before the demo is recorded.

D-6. Frontend, settling the former Q-3. The frontend is a single-page application in TypeScript with React, built by Vite into static files and kept in `frontend/` as one code unit. The map is drawn by MapLibre GL JS from one archive of vector tiles of Kraków served by the project, and the browser talks only to the server of the project. Frontend code is held to the workflow core and to `docs/standards/standard_frontend.md`, whose four gates are set up by the work package that writes the first frontend code. The decisions, the facts behind them and the rejected variants are in `plans_finished/frontend_stack/FRONTEND_STACK_PLAN.md` D-1 - D-13. Constraints for the rest of this plan: the page, the programming interface and the tiles are served from one host (D-3 there); the work package of the map produces the tile archive and serves the map fonts and sprites from the project (D-5 and D-6 there); the first screen applying a display rule of the specification creates the pair of documents of the code unit (D-10 there). Decided by the frontend person on 2026-10-03 in `plans_finished/frontend_stack/`, the tile source after consulting the external API person.

D-7. Local database environment, settling the former Q-4. Every member of the team who writes backend code runs their own PostgreSQL 18.6 with PostGIS 3.6.4 and the files of pgRouting 4.0.1 in a project image built from the official image `postgres:18.6-trixie` and started by Docker Compose, on Windows x64 and Linux x64, with the versions, accounts and rules of `plans_finished/local_database/LOCAL_DATABASE_PLAN.md` D-1 - D-8. Constraints for the rest of this plan: a work package of this plan builds the local setup - the image, the Compose file, the script creating the database and the accounts, the entries of the environment templates and the README instructions - and the Alembic configuration (D-8 there); besides the bootstrap superuser of the image the database has two accounts, the schema owner, a superuser that applies the revisions, and the service account, which is not a superuser, owns nothing and gets its rights only from grants in revisions (D-5 there); the first revision in the chain creates PostGIS (D-7 there); the environment carries pgRouting without creating it (D-7 there), and the graph in memory of D-9 does not use it. Decided by the user, answering for the db person, on 2026-10-03 in `plans_finished/local_database/`.

D-8. Account sessions, settling the former Q-6. The browser uses a signed token retained across browser closure, renewed on every authenticated request including read-only requests, and expiring 24 hours after the latest such request. Logout removes the active token from that browser; a deleted account no longer resolves to an account actor. Moderator authorization checks the current role on every moderator request, so role removal denies the next request. Requests without an authenticated account are anonymous contributions. The credential and actor-resolution behavior, including the API handoff boundary, is recorded in `plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-3. The user selected this mechanism on 2026-10-03 in `plans_finished/account_sessions/`. The rules of that initiative on vote deduplication (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-2) are not part of this decision: the user rejected them on 2026-10-03, because they contradict `docs/product/specification.md` version 4, M4 and M9. Numbered D-8 on 2026-10-03, because it arrived from `dev` as a second D-7. Changed on 2026-10-03 by `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-5 and D-6, decided by the user: a request with a malformed, wrongly signed or expired token, or with the token of a deleted account, is refused, so only a request without a token is an anonymous contribution, and a route request and an address search take no token and renew no session. Added on 2026-10-03: passwords are stored as Argon2id hashes (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-4), and the pseudonym and the password are checked where the input is accepted by the rules of `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-8.

D-9. Routing engine, settling the former Q-1. Routes are computed by a graph of the pedestrian network in the memory of the one backend process, searched with scipy over numpy arrays, with the rules, values and tests of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-1 - D-17. Constraints for the rest of this plan: nothing of a route request leaves the project and no routing service outside it is called (D-1 there); the route work package builds the graph, the weights, the segment states, the alternative and the route with the fewest barriers in the rules layer from data read by the data layer, together with the segment combination and the contradiction handed to it by D-5 (D-2 there); the import stores only the ways of the pedestrian network of `docs/product/specification.md` M2, with the ordered nodes and coordinates of D-11 (D-4 and D-11 there); Q-11 builds the graph when the backend process starts and rebuilds it in that process when the copy in use changes (D-3 there); the route work package adds numpy and scipy as pinned runtime dependencies and the tests of D-16 there. Decided by the user, answering for the backend person, on 2026-10-03 in `plans_finished/routing_engine/`.

D-10. Where the demo runs, settling the former Q-7. The demo runs on the virtual private server of the db person, reached at the IP address of the server over a secure connection, with the reason, the cost and the resources of `plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md` D-8. Constraints for the rest of this plan: Q-11 places the backend process, the worker, PostgreSQL with PostGIS and the static frontend on that one server, within 4 GB of free memory and 64 GB of free disk, and decides whether the import runs there or on a team machine (D-8 there); the server also runs other services of its owner, so the demo uses only its own services, database and logs (`CLAUDE.md`, section Target environment); the secure connection and the unreachable routing of the live demo are built by the task `DEPLOYMENT` of `plans/deployment/` once Q-11 and the backend skeleton exist. Decided by the user, answering for the db person, on 2026-10-03 in `plans_finished/demo_environment/`.

D-11. Domain model and database schema of facts and votes, settling the former Q-10. The target schema is `docs/product/schema.md`, part of `docs/product/specification.md` since version 6, with the rules of votes, statuses, flags and hiding of version 4, as `plans_finished/fact_schema/FACT_SCHEMA_PLAN.md` D-1 - D-21 decide. Constraints for the rest of this plan: the import and the backend write one shared schema, the import the OpenStreetMap tables and the facts with an OpenStreetMap identity, the backend the reports, geozones, votes, accounts, flags and hiding (D-1 there); a fresh copy is written in one transaction together with its reconciliation and its date (D-2 there); the status of a fact and the date of its last confirmation are derived from the votes on every read and never stored, and the segment state is derived for every route (D-4 there); a vote is written with `INSERT ... ON CONFLICT DO NOTHING`, where no returned row means the vote limit refused it (D-9 there); the database itself refuses the states of `plans_finished/fact_schema/FACT_SCHEMA_PRD.md` FR-15; the first revision creates `postgis` and `btree_gist` and grants the service account of D-7 only the rights listed in the schema (D-16, D-17 there). The schema is built by the task `SCHEMA_REVISION` of `plans/schema_revision/` once the local setup and the Alembic configuration of D-7 and the backend skeleton of Q-11 exist, and the work packages of the import, the voting, the accounts, the moderation and the route build on that revision. Decided on 2026-10-03 in `plans_finished/fact_schema/`: the rules by the user in place of the db person, whose ruling is still to be confirmed, the split into two tasks and the storage of a fresh copy by the user, the rest by the agent at C:40.

D-12. Programming interface contract, settling the former Q-9. Every operation between the clients and the service, with its request, responses and errors, is in `docs/product/api_contract.md`, with the decisions of `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-1 - D-18. Constraints for the rest of this plan: the clients and the service use the operations, codes and shapes of that document, and a change of an operation is a change of that document first (D-2 there); the session token of D-8 travels in the header `Authorization: Bearer` and comes back renewed in the response header `Session-Token`, and a request with an expired token is refused, never handled without an account (D-4, D-5 there); a route request, an address search, an account creation and a login carry no token (D-6 there); a saved report or geozone carries an idempotency key that the stored data of D-11 does not hold yet, which the task `SCHEMA_REVISION` of `plans/schema_revision/` answers (D-9 there); the implementation of the operations goes with Q-11. Decided by the user on 2026-10-03 in phase B of `plans_finished/api_contract/`, approving the contract in place of the frontend person, whose confirmation is still to be obtained; the rest by the agent at C:40.
