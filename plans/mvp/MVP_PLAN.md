Document state: 2026-10-03, plan in progress

## Goal

## Decisions

D-1. The backend is Python 3.13 with FastAPI, on PostgreSQL with PostGIS. The Python profile of the standards stays in force in full. Decided by the user on 2026-10-03 in phase B, against three alternatives: Python with plain PostgreSQL, TypeScript full-stack, no own backend.

D-2. Every remaining technical direction of this plan is decided in its own initiative by the team role responsible for it, not in this plan. Decided by the user on 2026-10-03 in phase B; the initiatives and their owners are listed under Open questions, and the conversation is recorded verbatim in their seeds. The assignment of initiatives to the five team roles named by the user - frontend, db, import, external API, backend - was made by the agent at the user's request.

D-3. Address search, settling the former Q-5. The search is answered by the public Nominatim instance, called only by the server, with the rules, parameters and tests of `plans_finished/geocoding/GEOCODING_PLAN.md` D-1 - D-16. Constraints for the rest of this plan: the search is the explicit exception of a read from an external system during request handling (D-2 there), its text travels only in the body of a POST request (D-3 there), the backend runs as exactly one process (D-15 there), and the work package of the search includes the tests of D-16 there. Decided by the user with the external API person on 2026-10-03 in `plans_finished/geocoding/`.

D-4. Source of the OpenStreetMap data and its refresh, settling the former Q-2. The copy is the Geofabrik extract of Małopolska, cut to the administrative boundary of Kraków, read with pyosmium, fetched once before the demo and refreshed only by hand, with the rules, parameters and tests of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-1 - D-22. Constraints for the rest of this plan: a refresh is an administrative run, never part of request handling, and two runs never overlap (D-11 there); a fresh copy, its reconciliation with the stored facts and its date become visible in one commit or not at all, and Q-10 stores the copy under that constraint (D-9 there); the identity of an OpenStreetMap fact is the type and OpenStreetMap identifier of its element together with its fact type, with no matching by geometry (D-7 there), and the reconciliation of every refresh follows D-10 there; Q-11 decides the form of the trigger and the machine the run executes on, using the measurements of F-4, F-10 and F-11 there; the routing engine of Q-1 takes the facts and the segment states from this copy under the condition of D-17 there; and the work package of the import includes the tests of D-22 there. The facts for the description of the data sources are D-19 there. The rules of FR-7 - FR-11 of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PRD.md` enter `docs/product/specification.md` version 3, written by `plans_finished/osm_barrier_mapping/` (D-20 there). Decided by the user, answering for the import person, on 2026-10-03 in `plans_finished/osm_data_source/`.

D-5. Mapping of OpenStreetMap tags to the closed list of barriers and amenities, settling the former Q-8. The tag rules, thresholds and value lists are those of `docs/product/specification.md` version 3, M6, with the segment rules of M7 and M8 and the contradiction of M2, applied as `plans_finished/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6 - D-17 decide. Constraints for the rest of this plan: the import applies the rule once per element, independently of the profile, and keeps for every barrier of a way one of the states present, absent, absent by default and unknown (D-6 there), so that the route can tell an explicit absence, which contradicts a report, from the default of no stairs, which does not; the thresholds and value lists are constants of the third configuration layer next to the code of the rule (D-14 there); the import and route work packages include the tests of D-17 there. Decided by the user on 2026-10-03 in `plans_finished/osm_barrier_mapping/`; the import person confirms or changes the thresholds before the demo is recorded.

D-6. Frontend, settling the former Q-3. The frontend is a single-page application in TypeScript with React, built by Vite into static files and kept in `frontend/` as one code unit. The map is drawn by MapLibre GL JS from one archive of vector tiles of Kraków served by the project, and the browser talks only to the server of the project. Frontend code is held to the workflow core and to `docs/standards/standard_frontend.md`, whose four gates are set up by the work package that writes the first frontend code. The decisions, the facts behind them and the rejected variants are in `plans_finished/frontend_stack/FRONTEND_STACK_PLAN.md` D-1 - D-13. Constraints for the rest of this plan: the page, the programming interface and the tiles are served from one host (D-3 there); the work package of the map produces the tile archive and serves the map fonts and sprites from the project (D-5 and D-6 there); the first screen applying a display rule of the specification creates the pair of documents of the code unit (D-10 there). Decided by the frontend person on 2026-10-03 in `plans_finished/frontend_stack/`, the tile source after consulting the external API person.

D-7. Local database environment, settling the former Q-4. Every member of the team who writes backend code runs their own PostgreSQL 18.6 with PostGIS 3.6.4 and the files of pgRouting 4.0.1 in a project image built from the official image `postgres:18.6-trixie` and started by Docker Compose, on Windows x64 and Linux x64, with the versions, accounts and rules of `plans_finished/local_database/LOCAL_DATABASE_PLAN.md` D-1 - D-8. Constraints for the rest of this plan: a work package of this plan builds the local setup - the image, the Compose file, the script creating the database and the accounts, the entries of the environment templates and the README instructions - and the Alembic configuration (D-8 there); besides the bootstrap superuser of the image the database has two accounts, the schema owner, a superuser that applies the revisions, and the service account, which is not a superuser, owns nothing and gets its rights only from grants in revisions (D-5 there); the first revision in the chain creates PostGIS (D-7 there); the environment carries pgRouting without creating it, so a choice of pgRouting in Q-1 needs only a new revision (D-7 there). Decided by the user, answering for the db person, on 2026-10-03 in `plans_finished/local_database/`.

D-8. Account sessions, settling the former Q-6. The browser uses a signed token retained across browser closure, renewed on every authenticated request including read-only requests, and expiring 24 hours after the latest such request. Logout removes the active token from that browser; a deleted account no longer resolves to an account actor. Moderator authorization checks the current role on every moderator request, so role removal denies the next request. Requests without an authenticated account are anonymous contributions. The credential and actor-resolution behavior, including the API handoff boundary, is recorded in `plans/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-3. The user selected this mechanism on 2026-10-03 in `plans/account_sessions/`. The rules of that initiative on vote deduplication (`plans/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-2) are not part of this decision: the user rejected them on 2026-10-03, because they contradict `docs/product/specification.md` version 4, M4 and M9. Numbered D-8 on 2026-10-03, because it arrived from `dev` as a second D-7.

D-9. Routing engine, settling the former Q-1. Routes are computed by a graph of the pedestrian network in the memory of the one backend process, searched with scipy over numpy arrays, with the rules, values and tests of `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-1 - D-17. Constraints for the rest of this plan: nothing of a route request leaves the project and no routing service outside it is called (D-1 there); the route work package builds the graph, the weights, the segment states, the alternative and the route with the fewest barriers in the rules layer from data read by the data layer, together with the segment combination and the contradiction handed to it by D-5 (D-2 there); the import stores only the ways of the pedestrian network of `docs/product/specification.md` M2, with the ordered nodes and coordinates of Q-10 (D-4 and D-11 there); Q-11 builds the graph when the backend process starts and rebuilds it in that process when the copy in use changes (D-3 there); the route work package adds numpy and scipy as pinned runtime dependencies and the tests of D-16 there. Decided by the user, answering for the backend person, on 2026-10-03 in `plans_finished/routing_engine/`.

## Open questions

- Q-7. Where the demo runs, and the target environment entry of `docs/standards/decision_registry.md` - `plans/demo_environment/`, owner: db, consulted: backend.
- Q-9. Contract of the programming interface between the frontend and the backend - `plans/api_contract/`, owner: backend, consulted: frontend. Depends on Q-10 for the resources and statuses it exposes and on D-8, the former Q-6, for authentication. It does not depend on Q-1: the route response carries the segment states of Q-10, not anything specific to the routing engine. Confirmed by the user, answering for the backend person, on 2026-10-03 in `plans_finished/consistency_check/` (U-5 of its review): the route response describes the data of the product - the segments with their geometry and states, the list, the alternative and the messages - and the engine adapts to it.
- Q-10. The domain model and database schema of facts and votes: the stored OpenStreetMap elements, the facts from OpenStreetMap and from users, geozones, votes with the identifier of a vote without an account, the states of the ways of the pedestrian network from which the segment states are derived, and the accounts - `plans/fact_schema/`, owner: db, consulted: backend, import. Moved out of this plan into its own initiative at the user's request on 2026-10-03. Its shape is closed and its PRD passed the gate on 2026-10-03, which keeps the segment state out of the stored data and derives it for each route (`plans/fact_schema/FACT_SCHEMA_PRD.md` FR-5); its plan is still to be written. Q-10 closes when the task `FACT_SCHEMA` of that initiative is implemented - the target schema written and approved, and the decision entry of its FR-16 recorded here - not with the first schema revision, which the task `SCHEMA_REVISION` of the same initiative builds once the local setup and the Alembic configuration of the work package of D-7 exist (U-1 of `plans/dependency_check/`). Depends on the rules of D-5 and, of the former Q-2, now D-4, only on the question what happens to the votes on an OpenStreetMap fact that disappears in a fresh copy. Both are settled: the rules of D-5 in `docs/product/specification.md` version 3 and the question of the former Q-2 in `plans_finished/osm_data_source/OSM_DATA_SOURCE_SHAPE.md` (questions 2, 5 and 6), both interviews closed on 2026-10-03, so Q-10 can be decided now. It does not depend on the numeric thresholds of D-5, which are constants of the third configuration layer (`plans_finished/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-14), nor on the choice of the source in D-4. It does not depend on D-6 (the former Q-3), Q-6, Q-7 or Q-9, and not on Q-1, which depends on it instead: the routing engine adapts to the ways and points Q-10 stores, and a need beyond them is raised with the db person (U-2 of `plans/dependency_check/`); the session storage of Q-6 is outside it.
- Q-10 inputs from `plans_finished/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, section Domain rules, which the schema has to be able to hold: an OpenStreetMap fact keeps the identity of its OpenStreetMap element and its fact type, because a fact that returns in a later copy on the same element with the same type is the same fact again, with all its votes (question 6); an OpenStreetMap fact missing from a fresh copy becomes a user fact with its votes when its confirmations outweigh its denials, and otherwise becomes outdated with the reason that it was removed in OpenStreetMap, with its votes kept in its history (questions 2 and 5); a converted fact shows the source "user report" with the date of its last confirmation; an OpenStreetMap fact and a user fact of the same type at the same place are two separate facts, never merged.
- Q-10 inputs from `plans_finished/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6, which the schema has to be able to hold: for every way of the pedestrian network, for each of stairs, poor surface, steep incline and narrow passage one of the states present, absent, absent by default and unknown, where absent by default exists only for stairs; the number of steps of stairs when OpenStreetMap gives it; the `wheelchair=no` marking of the way; for every node of such a way its point facts - stairs, a narrow passage, a kerb point that is high, lowered or unknown - and whether it also belongs to a way for motor traffic; for every amenity fact its element and a point; and for every fact the type and identifier of its OpenStreetMap element and the calendar day of its last OpenStreetMap edit. OpenStreetMap contradicts a user report only through an explicit absence or an opposite kerb point, never through absent by default or unknown (`docs/product/specification.md` version 3, M2).
- Q-10 inputs from `plans_finished/osm_data_source/`, settling the two points its shape handed to Q-10: a vote, a vote without an account included, keeps its weight in the sums of the conversion for as long as the fact exists, also after its 30-day identifier is deleted (`plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-21); and the same OpenStreetMap element is the element with the same type and OpenStreetMap identifier, with no matching by geometry when OpenStreetMap splits, joins or recreates a way (D-7 there). The storage constraints of a refresh are D-9 and D-10 there.
- Q-10 caveats: the rules above are in `docs/product/specification.md` version 3, written by `plans_finished/osm_barrier_mapping/` and approved by the user, except the weight of a vote after its 30-day identifier is deleted, which lives in `plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-21. The rules of questions 2, 5 and 6 of `plans_finished/osm_data_source/` were given by the user on behalf of the import person, whose ruling is still to be confirmed. `plans/fact_schema/` first answered the weight of such a vote the other way and follows D-21 since the user chose it on 2026-10-03 (`plans/fact_schema/FACT_SCHEMA_SHAPE.md`, section Domain rules). Version 4 of the specification, approved by the user on 2026-10-03 and written by `plans_finished/consistency_check/`, now states D-21 too, together with the rules of votes, statuses, flags and hiding of `plans/fact_schema/` and the statuses of OpenStreetMap facts decided in `plans_finished/consistency_check/` (U-1, U-2 of its review).
- Q-11. The backend architecture with the worker. Decided in this plan, owner: backend. Depends on D-9 (the route graph is built at the start of the backend process and rebuilt in it), D-4 (the import and refresh run) and Q-7 (where the service runs).

The owners of Q-10 and Q-11 were proposed by the agent.
