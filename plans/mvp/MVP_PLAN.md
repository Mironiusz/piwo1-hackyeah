## Decisions

D-1. The backend is Python 3.13 with FastAPI, on PostgreSQL with PostGIS. The Python profile of the standards stays in force in full. Decided by the user on 2026-10-03 in phase B, against three alternatives: Python with plain PostgreSQL, TypeScript full-stack, no own backend.

D-2. Every remaining technical direction of this plan is decided in its own initiative by the team role responsible for it, not in this plan. Decided by the user on 2026-10-03 in phase B; the initiatives and their owners are listed in the entry Technical directions of the MVP plan of `docs/standards/decision_registry.md`, each settled direction in the decision of this plan that names its initiative, D-3 - D-12, and the one still open, Q-11, under Open questions, and the conversation is recorded verbatim in their seeds. The assignment of initiatives to the five team roles named by the user - frontend, db, import, external API, backend - was made by the agent at the user's request.

D-3. Address search, settling the former Q-5. The search is answered by the public Nominatim instance, called only by the server, with the rules, parameters and tests of `plans_finished/geocoding/GEOCODING_PLAN.md` D-1 - D-16. Constraints for the rest of this plan: the search is the explicit exception of a read from an external system during request handling (D-2 there), its text travels only in the body of a POST request (D-3 there), the backend runs as exactly one process (D-15 there), and the work package of the search includes the tests of D-16 there. Decided by the user with the external API person on 2026-10-03 in `plans_finished/geocoding/`. Corrected on 2026-10-04 by `plans_finished/nominatim_client/`: `plans_finished/geocoding/GEOCODING_PLAN.md` D-7 puts, in place of a missing `address.road`, `address.neighbourhood` followed by a space and `address.house_number` when the number is present, and drops a result whose label repeats the label of an earlier result of the same list, keeping the first in the order of the service, see `plans_finished/nominatim_client/attachments/nominatim_check_2026-10-04.md` R-7.

D-4. Source of the OpenStreetMap data and its refresh, settling the former Q-2. The copy is the Geofabrik extract of Małopolska, cut to the administrative boundary of Kraków, read with pyosmium, fetched once before the demo and refreshed only by hand, with the rules, parameters and tests of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-1 - D-22. Constraints for the rest of this plan: a refresh is an administrative run, never part of request handling, and two runs never overlap (D-11 there); a fresh copy, its reconciliation with the stored facts and its date become visible in one commit or not at all, and D-11 stores the copy under that constraint (D-9 there); the identity of an OpenStreetMap fact is the type and OpenStreetMap identifier of its element together with its fact type, with no matching by geometry (D-7 there), and the reconciliation of every refresh follows D-10 there; Q-11 decides the form of the trigger and the machine the run executes on, using the measurements of F-4, F-10 and F-11 there; the routing engine of D-9 takes the facts and the segment states from this copy under the condition of D-17 there; and the work package of the import includes the tests of D-22 there. The facts for the description of the data sources are D-19 there. The rules of FR-7 - FR-11 of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PRD.md` enter `docs/product/specification.md` version 3, written by `plans_finished/osm_barrier_mapping/` (D-20 there). Decided by the user, answering for the import person, on 2026-10-03 in `plans_finished/osm_data_source/`.

D-5. Mapping of OpenStreetMap tags to the closed list of barriers and amenities, settling the former Q-8. The tag rules, thresholds and value lists are those of `docs/product/specification.md` version 3, M6, with the segment rules of M7 and M8 and the contradiction of M2, applied as `plans_finished/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6 - D-17 decide. Constraints for the rest of this plan: the import applies the rule once per element, independently of the profile, and keeps for every barrier of a way one of the states present, absent, absent by default and unknown (D-6 there), so that the route can tell an explicit absence, which contradicts a report, from the default of no stairs, which does not; the thresholds and value lists are constants of the third configuration layer next to the code of the rule (D-14 there); the import and route work packages include the tests of D-17 there. Decided by the user on 2026-10-03 in `plans_finished/osm_barrier_mapping/`; the import person confirms or changes the thresholds before the demo is recorded.

D-6. Frontend, settling the former Q-3. The frontend is a single-page application in TypeScript with React, built by Vite into static files and kept in `frontend/` as one code unit. The map is drawn by MapLibre GL JS from one archive of vector tiles of Kraków served by the project, and the browser talks only to the server of the project. Frontend code is held to the workflow core and to `docs/standards/standard_frontend.md`, whose four gates are set up by the work package that writes the first frontend code. The decisions, the facts behind them and the rejected variants are in `plans_finished/frontend_stack/FRONTEND_STACK_PLAN.md` D-1 - D-13. Constraints for the rest of this plan: the page, the programming interface and the tiles are served from one host (D-3 there); the work package of the map produces the tile archive and serves the map fonts and sprites from the project (D-5 and D-6 there); the first screen applying a display rule of the specification creates the pair of documents of the code unit (D-10 there). Decided by the frontend person on 2026-10-03 in `plans_finished/frontend_stack/`, the tile source after consulting the external API person.

D-7. Local database environment, settling the former Q-4. Every member of the team who writes backend code runs their own PostgreSQL 18.6 with PostGIS 3.6.4 and the files of pgRouting 4.0.1 in a project image built from the official image `postgres:18.6-trixie` and started by Docker Compose, on Windows x64 and Linux x64, with the versions, accounts and rules of `plans_finished/local_database/LOCAL_DATABASE_PLAN.md` D-1 - D-8. Constraints for the rest of this plan: a work package of this plan builds the local setup - the image, the Compose file, the script creating the database and the accounts, the entries of the environment templates and the README instructions - and the Alembic configuration (D-8 there); besides the bootstrap superuser of the image the database has two accounts, the schema owner, a superuser that applies the revisions, and the service account, which is not a superuser, owns nothing and gets its rights only from grants in revisions (D-5 there); the first revision in the chain creates PostGIS (D-7 there); the environment carries pgRouting without creating it (D-7 there), and the graph of the route with the fewest barriers of D-9 does not use it. Decided by the user, answering for the db person, on 2026-10-03 in `plans_finished/local_database/`.

D-8. Account sessions, settling the former Q-6. The browser uses a signed token retained across browser closure, renewed on every authenticated request including read-only requests, and expiring 24 hours after the latest such request. Logout removes the active token from that browser; a deleted account no longer resolves to an account actor. Moderator authorization checks the current role on every moderator request, so role removal denies the next request. Requests without an authenticated account are anonymous contributions. The credential and actor-resolution behavior, including the API handoff boundary, is recorded in `plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-3. The user selected this mechanism on 2026-10-03 in `plans_finished/account_sessions/`. The rules of that initiative on vote deduplication (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-2) are not part of this decision: the user rejected them on 2026-10-03, because they contradict `docs/product/specification.md` version 4, M4 and M9. Numbered D-8 on 2026-10-03, because it arrived from `dev` as a second D-7. Changed on 2026-10-03 by `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-5 and D-6, decided by the user: a request with a malformed, wrongly signed or expired token, or with the token of a deleted account, is refused, so only a request without a token is an anonymous contribution, and a route request and an address search take no token and renew no session. Added on 2026-10-03: passwords are stored as Argon2id hashes (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-4), and the pseudonym and the password are checked where the input is accepted by the rules of `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-8.

D-9. Routing engine, settling the former Q-1. Routes are computed by one Valhalla service run by the project, with the rules, values and tests of `plans/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-1 - D-16, which replace `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-1, D-3, D-6, D-7 and D-13 and keep its D-2, D-4, D-5, D-8 - D-12 and D-14 - D-17; under the kept D-2 every call to Valhalla has one call site in the data layer and one seam in the rules layer (`docs/standards/standard_architecture.md`, section Calls to external systems). Constraints for the rest of this plan: nothing of a route request leaves the project and no routing service outside it is called; the service runs the image built by `valhalla/Dockerfile` on the internal network of the demo, with no port of the host (D-1 there); the import work package stores only the ways of the pedestrian network of `docs/product/specification.md` M2, with their ordered nodes and coordinates, and in the same run, before the downloaded file is deleted, writes the network file and builds the routing data of the copy, kept with the instant of that copy (D-2 there); the route work package builds the image and the configuration of the service, the requests with the barriers and geozones to avoid, the alternative, the route with the fewest barriers on its own graph of the stretches with numpy and scipy as pinned runtime dependencies, the tie of every route to the stored stretches, the check of every route before it is shown and the cases of `routing_unavailable`, in the rules layer from data read by the data layer, together with the segment combination and the contradiction handed to it by D-5 (D-3 - D-11 and D-13 there); Q-11 decides how the backend learns the instant of the routing data the service serves and holds the graph of the route with the fewest barriers, about 630 MB, in the one backend process, and where the service runs, within the needs of D-14 there. Routes with public transport, the optional feature O9 of the specification, are built by a separate initiative set up by the user (D-12, D-13 there). Decided by the user on 2026-10-04 in `plans/valhalla_routing/`, superseding the decision of 2026-10-03 in `plans_finished/routing_engine/`; the answers were given by the user for the backend person, whose ruling is still to be confirmed (D-16 there).

D-10. Where the demo runs, settling the former Q-7. The demo runs on a server of the user in a data centre, with 16 GB of memory and 16 cores, reached at its IP address over plain HTTP. Everything of the demo on the server runs in Docker containers orchestrated by Docker Compose and is started with one command and an environment file kept on the server (`plans/deployment/DEPLOYMENT_SHAPE.md`, sections Current state and Domain rules). It supersedes the virtual private server of `plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md` D-8.

Constraints for the rest of this plan:

- Q-11 places on that server the backend process, the worker, PostgreSQL with PostGIS in an instance of its own, the static frontend and the Valhalla routing service of `plans/valhalla_routing/`, and decides whether the import runs there or on a team machine.
- What else runs on the server is not known, so the demo uses only its own services, database and logs (`CLAUDE.md`, section Target environment).
- The demo has no secure connection, so the start from the current location of FR-2 of `plans/mvp/MVP_PRD.md` does not work on the hosted link. Nor does the hosted demo provide a way to take routing down (`plans/deployment/DEPLOYMENT_SHAPE.md`, section Out of scope); `docs/product/specification.md` version 9 dropped that scene from M10, and the behavior of FR-17 of `plans/mvp/MVP_PRD.md` stays, checked by AC-16 there outside the hosted link.
- The deployment configuration is built by the task `DEPLOYMENT_CONFIG` of `plans/deployment/` once Q-11 and the backend skeleton exist. The written instructions are written by the task `DEPLOYMENT` there.

Decided by the user, answering for the db person, on 2026-10-03 in `plans_finished/demo_environment/`, and changed by the user on 2026-10-03 and 2026-10-04 in `plans/deployment/`.

## Risks

- The plan cannot be closed, and `plan-implement` cannot start, until Q-11 is decided in `plans/backend_architecture/`, whose interview closed on 2026-10-04 with no question that blocks it and which has no PRD or plan yet. Every hour it stays open is taken from the time left before the Kraków deadline at 11:00 on 4 October 2026, and no product code exists (F-3).
- The demo knowingly does not meet two points of the Kraków brief: it is served over plain HTTP, while the brief lists secure connections (D-10), and, if O9 is built, it shows a public transport segment without accessibility data as green (`docs/product/specification.md` M7 and O9). Both cost points in the criteria of data protection and of data reliability, and the Kraków submission has to state them, not hide them (`docs/hackathon/challenge_requirements.md`, Conflicts and open points, item 10).
- Q-11 is the critical path. No cycle is left between the questions of this plan since `plans_finished/dependency_check/` (U-1 - U-3 there). Three steps wait for Q-11: the work package of D-7 names the files of the Alembic configuration inside the backend skeleton that Q-11 shapes; the work package of the first schema revision of D-11 builds it once that skeleton, the local setup and the Alembic configuration exist, and the work packages of the import, the voting, the accounts, the moderation and the route build on its revision; the task `DEPLOYMENT_CONFIG` of `plans/deployment/` writes the deployment configuration once Q-11 and the backend skeleton exist (D-10). The revision waits only for the local setup and the skeleton with the Alembic configuration, not for the whole work package of D-7: the critical tests of `plans_finished/local_database/LOCAL_DATABASE_PLAN.md` D-8 that check the first revision run after it, so that work package is not delivered as one step together with them, or the loop cut by U-1 of `plans_finished/dependency_check/` comes back inside this plan. The parts of Q-11 that concern the routing - how the backend learns the instant of the routing data, where it holds the graph of the route with the fewest barriers and where Valhalla runs - take the needs of `plans/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-3, D-7 and D-14. D-9 takes its pedestrian network and segment states from the copy of D-4 under the condition recorded there, and adapts to the ways and points D-11 stores (`plans_finished/fact_schema/FACT_SCHEMA_PRD.md` FR-5; U-2 of `plans_finished/dependency_check/`). - Valhalla of D-9 is decided on the measurements of the spike of 2026-10-03 (`plans/valhalla_routing/spike/VALHALLA_SPIKE_REPORT.md`), but nothing of it is built: the import and route work packages of this plan build D-1 - D-11 of `plans/valhalla_routing/VALHALLA_ROUTING_PLAN.md` (D-13 there), and they exist only once Q-11 closes.
