D-2. Every remaining technical direction of this plan is decided in its own initiative by the team role responsible for it, not in this plan. Decided by the user on 2026-10-03 in phase B; the initiatives and their owners are listed in the entry Technical directions of the MVP plan of `docs/standards/decision_registry.md`, each settled direction in the decision of this plan that names its initiative, D-3 - D-12, and the one still open, Q-11, under Open questions, and the conversation is recorded verbatim in their seeds. The assignment of initiatives to the five team roles named by the user - frontend, db, import, external API, backend - was made by the agent at the user's request.

D-3. Address search, settling the former Q-5. The search is answered by the public Nominatim instance, called only by the server, with the rules, parameters and tests of `plans_finished/geocoding/GEOCODING_PLAN.md` D-1 - D-16. Constraints for the rest of this plan: the search is the explicit exception of a read from an external system during request handling (D-2 there), its text travels only in the body of a POST request (D-3 there), the backend runs as exactly one process (D-15 there), and the work package of the search includes the tests of D-16 there. Decided by the user with the external API person on 2026-10-03 in `plans_finished/geocoding/`. Corrected on 2026-10-04 by `plans_finished/nominatim_client/`: `plans_finished/geocoding/GEOCODING_PLAN.md` D-7 puts, in place of a missing `address.road`, `address.neighbourhood` followed by a space and `address.house_number` when the number is present, and drops a result whose label repeats the label of an earlier result of the same list, keeping the first in the order of the service, see `plans_finished/nominatim_client/attachments/nominatim_check_2026-10-04.md` R-7.

D-4. Source of the OpenStreetMap data and its refresh, settling the former Q-2. Constraints for the rest of this plan: a refresh is an administrative run, never part of request handling, and two runs never overlap (D-11 there); a fresh copy, its reconciliation with the stored facts and its date become visible in one commit or not at all, and D-11 stores the copy under that constraint (D-9 there); the identity of an OpenStreetMap fact is the type and OpenStreetMap identifier of its element together with its fact type, with no matching by geometry (D-7 there), and the reconciliation of every refresh follows D-10 there; Q-11 decides the form of the trigger and the machine the run executes on, using the measurements of F-4, F-10 and F-11 there; the routing engine of D-9 takes the facts and the segment states from this copy under the condition of D-17 there; and the work package of the import includes the tests of D-22 there. The rules of FR-7 - FR-11 of `plans_finished/osm_data_source/OSM_DATA_SOURCE_PRD.md` enter `docs/product/specification.md` version 3, written by `plans_finished/osm_barrier_mapping/` (D-20 there). Decided by the user, answering for the import person, on 2026-10-03 in `plans_finished/osm_data_source/`.

D-7. Local database environment, settling the former Q-4. D-8. Account sessions, settling the former Q-6. The browser uses a signed token retained across browser closure, renewed on every authenticated request including read-only requests, and expiring 24 hours after the latest such request. Logout removes the active token from that browser; a deleted account no longer resolves to an account actor. Moderator authorization checks the current role on every moderator request, so role removal denies the next request. Requests without an authenticated account are anonymous contributions. The credential and actor-resolution behavior, including the API handoff boundary, is recorded in `plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-3. The user selected this mechanism on 2026-10-03 in `plans_finished/account_sessions/`. The rules of that initiative on vote deduplication (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-2) are not part of this decision: the user rejected them on 2026-10-03, because they contradict `docs/product/specification.md` version 4, M4 and M9. Numbered D-8 on 2026-10-03, because it arrived from `dev` as a second D-7. Changed on 2026-10-03 by `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-5 and D-6, decided by the user: a request with a malformed, wrongly signed or expired token, or with the token of a deleted account, is refused, so only a request without a token is an anonymous contribution, and a route request and an address search take no token and renew no session. Added on 2026-10-03: passwords are stored as Argon2id hashes (`plans_finished/account_sessions/ACCOUNT_SESSIONS_PLAN.md` D-4), and the pseudonym and the password are checked where the input is accepted by the rules of `plans_finished/api_contract/API_CONTRACT_PLAN.md` D-8.

D-9. Routing engine, settling the former Q-1. Walking routes are computed by Valhalla, run by the project as a service of its own on the server of D-10, in place of the graph of the pedestrian network in the memory of the backend process that `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-1 decided on 2026-10-03. Constraints for the rest of this plan: nothing of a route request leaves the project, the request to Valhalla included (`docs/product/specification.md` M2); the behavior of M2, M7 and M8 does not change, so the pedestrian network of M2, version 5, stays the rule and Valhalla routes only on the ways that rule admits; the avoided barriers and geozones, the alternative for an unverified or disputed barrier, the route with the fewest barriers, the stretch to the network in the state no data, the segment states and the barrier list stay with the project in the rules layer, together with the segment combination and the contradiction handed to it by D-5, and the route with the fewest barriers needs logic of the project, because Valhalla excludes an area without a soft penalty; the import stores only the ways of the pedestrian network of M2, with the ordered nodes and coordinates of D-11 (`plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-4 and D-11). Of `plans_finished/routing_engine/`, the graph in memory with its search, its build and its rebuild, and the dependencies numpy and scipy (D-1, D-3 and D-14 there) no longer apply; its values that entered the specification as version 5 (D-15 there) stay in force through the specification, and which of its other decisions still apply is decided in phase B of `plans/valhalla_routing/`. Routes with public transport from the static GTFS of ZTP Kraków, proposed by the same initiative as the optional feature O9, built before O1 within a time box of 4.5 hours of work, are not part of this plan, whose goal is M1 - M11. Their rule that a public transport segment without accessibility data is green departs from the rule of the Kraków brief that missing information is never shown as a confirmation of accessibility (`docs/hackathon/challenge_requirements.md`, line 60); the user accepted that departure on 2026-10-04, siding with the decision of `plans/valhalla_routing/`, and the new version of the specification and the exception in `CLAUDE.md` it needs are written by that initiative (functional requirement 8 there).
