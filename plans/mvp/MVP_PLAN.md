# Plan: MVP of the accessibility app

Document state: 2026-10-03, plan in progress

## Goal

Implement the mandatory core M1-M11 of `docs/product/specification.md`, version 3, as defined by `plans/mvp/MVP_PRD.md` (FR-1 - FR-20, AC-1 - AC-19): a phone-first web app for Kraków with a Python backend, split into work packages that can be built in parallel, ordered so that the main scenario works first.

## Decisions

D-1. The backend is Python 3.13 with FastAPI, on PostgreSQL with PostGIS. The Python profile of the standards stays in force in full. Decided by the user on 2026-10-03 in phase B, against three alternatives: Python with plain PostgreSQL, TypeScript full-stack, no own backend.

D-2. Every remaining technical direction of this plan is decided in its own initiative by the team role responsible for it, not in this plan. Decided by the user on 2026-10-03 in phase B; the initiatives and their owners are listed under Open questions, and the conversation is recorded verbatim in their seeds. The assignment of initiatives to the five team roles named by the user - frontend, db, import, external API, backend - was made by the agent at the user's request.

D-3. Address search, settling the former Q-5. The search is answered by the public Nominatim instance, called only by the server, with the rules, parameters and tests of `plans/geocoding/GEOCODING_PLAN.md` D-1 - D-16. Constraints for the rest of this plan: the search is the explicit exception of a read from an external system during request handling (D-2 there), its text travels only in the body of a POST request (D-3 there), the backend runs as exactly one process (D-15 there), and the work package of the search includes the tests of D-16 there. Decided by the user with the external API person on 2026-10-03 in `plans/geocoding/`.

D-4. Source of the OpenStreetMap data and its refresh, settling the former Q-2. The copy is the Geofabrik extract of Małopolska, cut to the administrative boundary of Kraków, read with pyosmium, fetched once before the demo and refreshed only by hand, with the rules, parameters and tests of `plans/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-1 - D-22. Constraints for the rest of this plan: a refresh is an administrative run, never part of request handling, and two runs never overlap (D-11 there); a fresh copy, its reconciliation with the stored facts and its date become visible in one commit or not at all, and Q-10 stores the copy under that constraint (D-9 there); the identity of an OpenStreetMap fact is the type and OpenStreetMap identifier of its element together with its fact type, with no matching by geometry (D-7 there), and the reconciliation of every refresh follows D-10 there; Q-11 decides the form of the trigger and the machine the run executes on, using the measurements of F-4, F-10 and F-11 there; the routing engine of Q-1 takes the facts and the segment states from this copy under the condition of D-17 there; and the work package of the import includes the tests of D-22 there. The facts for the description of the data sources are D-19 there. The rules of FR-7 - FR-11 of `plans/osm_data_source/OSM_DATA_SOURCE_PRD.md` enter `docs/product/specification.md` version 3, written by `plans/osm_barrier_mapping/` (D-20 there). Decided by the user, answering for the import person, on 2026-10-03 in `plans/osm_data_source/`.

D-5. Mapping of OpenStreetMap tags to the closed list of barriers and amenities, settling the former Q-8. The tag rules, thresholds and value lists are those of `docs/product/specification.md` version 3, M6, with the segment rules of M7 and M8 and the contradiction of M2, applied as `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6 - D-17 decide. Constraints for the rest of this plan: the import applies the rule once per element, independently of the profile, and keeps for every barrier of a way one of the states present, absent, absent by default and unknown (D-6 there), so that the route can tell an explicit absence, which contradicts a report, from the default of no stairs, which does not; the thresholds and value lists are constants of the third configuration layer next to the code of the rule (D-14 there); the import and route work packages include the tests of D-17 there. Decided by the user on 2026-10-03 in `plans/osm_barrier_mapping/`; the import person confirms or changes the thresholds before the demo is recorded.

D-6. Frontend, settling the former Q-3. The frontend is a single-page application in TypeScript with React, built by Vite into static files and kept in `frontend/` as one code unit. The map is drawn by MapLibre GL JS from one archive of vector tiles of Kraków served by the project, and the browser talks only to the server of the project. Frontend code is held to the workflow core and to `docs/standards/standard_frontend.md`, whose four gates are set up by the work package that writes the first frontend code. The decisions, the facts behind them and the rejected variants are in `plans/frontend_stack/FRONTEND_STACK_PLAN.md` D-1 - D-13. Constraints for the rest of this plan: the page, the programming interface and the tiles are served from one host (D-3 there); the work package of the map produces the tile archive and serves the map fonts and sprites from the project (D-5 and D-6 there); the first screen applying a display rule of the specification creates the pair of documents of the code unit (D-10 there). Decided by the frontend person on 2026-10-03 in `plans/frontend_stack/`, the tile source after consulting the external API person.

## Risks

- The plan cannot be closed, and `plan-implement` cannot start, until the initiatives under Open questions are decided. Every hour they stay open is taken from the time left before the Kraków deadline at 11:00 on 4 October 2026.
- The open questions depend on each other: Q-10 depends on the rules of D-5 and on one question of Q-2, both settled on 2026-10-03; Q-9 depends on Q-10 and Q-6; Q-11 depends on Q-1, D-4 and Q-7; Q-1 takes its pedestrian network and segment states from the copy of D-4 under the condition recorded there; Q-3, Q-4, Q-6 and Q-7 depend on no other open question. The critical path is Q-10 -> Q-9. Deciding them in the wrong order means guessing a contract.

## Open questions

- Q-1. Routing engine - `plans/routing_engine/`, owner: backend, consulted: external API.
- Q-4. Local database environment with PostGIS - `plans/local_database/`, owner: db.
- Q-6. Account session mechanism - `plans/account_sessions/`, owner: backend.
- Q-7. Where the demo runs, and the target environment entry of `docs/standards/decision_registry.md` - `plans/demo_environment/`, owner: db, consulted: backend.
- Q-9. Contract of the programming interface between the frontend and the backend - `plans/api_contract/`, owner: backend, consulted: frontend. Depends on Q-10 for the resources and statuses it exposes and on Q-6 for authentication. It does not depend on Q-1: the route response carries the segment states of Q-10, not anything specific to the routing engine.
- Q-10. The domain model and database schema of facts and votes: the stored OpenStreetMap elements, the facts from OpenStreetMap and from users, geozones, votes with the identifier of a vote without an account, the segment states, and the accounts - `plans/fact_schema/`, owner: db, consulted: backend, import. Moved out of this plan into its own initiative at the user's request on 2026-10-03. Depends on the rules of D-5 and, of Q-2, only on the question what happens to the votes on an OpenStreetMap fact that disappears in a fresh copy. Both are settled: the rules of D-5 in `docs/product/specification.md` version 3 and the question of Q-2 in `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md` (questions 2, 5 and 6), both interviews closed on 2026-10-03, so Q-10 can be decided now. It does not depend on the numeric thresholds of D-5, which are constants of the third configuration layer (`plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-14), nor on the choice of the source in D-4. It does not depend on Q-1, Q-3, Q-6, Q-7 or Q-9; the session storage of Q-6 is outside it.
- Q-10 inputs from `plans/osm_data_source/OSM_DATA_SOURCE_SHAPE.md`, section Domain rules, which the schema has to be able to hold: an OpenStreetMap fact keeps the identity of its OpenStreetMap element and its fact type, because a fact that returns in a later copy on the same element with the same type is the same fact again, with all its votes (question 6); an OpenStreetMap fact missing from a fresh copy becomes a user fact with its votes when its confirmations outweigh its denials, and otherwise becomes outdated with the reason that it was removed in OpenStreetMap, with its votes kept in its history (questions 2 and 5); a converted fact shows the source "user report" with the date of its last confirmation; an OpenStreetMap fact and a user fact of the same type at the same place are two separate facts, never merged.
- Q-10 inputs from `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-6, which the schema has to be able to hold: for every way of the pedestrian network, for each of stairs, poor surface, steep incline and narrow passage one of the states present, absent, absent by default and unknown, where absent by default exists only for stairs; the number of steps of stairs when OpenStreetMap gives it; the `wheelchair=no` marking of the way; for every node of such a way its point facts - stairs, a narrow passage, a kerb point that is high, lowered or unknown - and whether it also belongs to a way for motor traffic; for every amenity fact its element and a point; and for every fact the type and identifier of its OpenStreetMap element and the calendar day of its last OpenStreetMap edit. OpenStreetMap contradicts a user report only through an explicit absence or an opposite kerb point, never through absent by default or unknown (`docs/product/specification.md` version 3, M2).
- Q-10 inputs from `plans/osm_data_source/`, settling the two points its shape handed to Q-10: a vote, a vote without an account included, keeps its weight in the sums of the conversion for as long as the fact exists, also after its 30-day identifier is deleted (`plans/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-21); and the same OpenStreetMap element is the element with the same type and OpenStreetMap identifier, with no matching by geometry when OpenStreetMap splits, joins or recreates a way (D-7 there). The storage constraints of a refresh are D-9 and D-10 there.
- Q-10 caveats: the rules above are in `docs/product/specification.md` version 3, written by `plans/osm_barrier_mapping/` and approved by the user, except the weight of a vote after its 30-day identifier is deleted, which lives in `plans/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-21. The rules of questions 2, 5 and 6 of `plans/osm_data_source/` were given by the user on behalf of the import person, whose ruling is still to be confirmed. `plans/fact_schema/` first answered the weight of such a vote the other way and follows D-21 since the user chose it on 2026-10-03 (`plans/fact_schema/FACT_SCHEMA_SHAPE.md`, section Domain rules).
- Q-11. The backend architecture with the worker. Decided in this plan, owner: backend. Depends on Q-1 (where the route is computed), D-4 (the import and refresh run) and Q-7 (where the service runs).
- Q-10 was narrowed to the domain model on 2026-10-03 at the user's request, and the backend architecture with the worker moved to Q-11, because the former condition of Q-10 "once Q-1 - Q-9 are settled" blocked the domain model on decisions it does not depend on. The owners of Q-10 and Q-11 were proposed by the agent.
