# Code quality standard

Document state: 2026-10-03

Status: ready - full content. The full description of this standard's position relative to the others is in `docs/standards/README.md`.

## Why this document exists

Code in this repository is to be readable, safe to maintain and verifiable automatically before a human or an agent starts reading it line by line. This standard collects the quality requirements for production code that do not have their own dedicated standard: commenting style, automatic style and formatting checks, function complexity, static typing, dead code, dependency consistency and performance. Without one place describing these requirements, every reviewer and every agent would have to reconstruct them from memory or from scattered fragments in other files, with the risk that different people adopt different thresholds for what is good enough.

## Scope and boundaries

This standard is responsible for the quality of production code unrelated to its architecture: commenting style and control of content generated by the chat, automatic style and formatting checks and their scope, function complexity, static typing, dead code detection, consistency between declared and actually used dependencies, and performance requirements.

What is not here:

- Tests - that is `standard_tests.md`. This document regulates nothing that concerns files in `tests/`.
- Code formatting as a standalone topic: line length, forbidden characters, quotation marks, the style of writing parameters - that is `standard_formatting.md`.
- Static security analysis of code and the dependency vulnerability scan - that is `standard_security.md`.
- Architecture above a single code unit - that is `standard_architecture.md`. The internal architecture of a layer itself has no standard today; the reason and the condition for creating one are in `docs/standards/README.md`, section Unresolved boundaries and debts.
- Module documentation - that is `standard_documentation.md`.
- Docstrings as an element of code quality belong to this standard. The structure of a separate document describing a code unit - that is `standard_documentation.md`.

## Deviation rule

The standard describes the target state and applies in full from the first commit. A project created from the template has no legacy code, so there is nothing to protect with a transition period - code that does not comply with the standard blocks review regardless of who wrote it and when.

When the repository has legacy code, relaxing this rule to the soft version is to be an explicit decision recorded in `docs/standards/README.md` together with the date and the reason. It is not a state that takes effect on its own.

## Comments in code

Code contains no line comments unless they are truly necessary. Two exceptions: a complicated algorithm that cannot be described sufficiently with a docstring, and a configuration constant acting as a switch - then a short line comment indicating which options this switch can take is acceptable. Outside these two exceptions, documenting logic goes into the docstring, not into a comment next to a line - a docstring describes the whole intent of the function in one place, while a line comment drifts apart from the code at the first change nearby, because nobody remembers it during a refactor.

Documents, including this one, use no bold in prose; the rule and the places where bold stays allowed are in `standard_formatting.md`, section Emphasis in prose.

Forbidden characters in code and documentation - see `standard_formatting.md`.

Code generated by the chat (agent) goes through a thorough check before it is accepted: whether it removed existing documentation, and whether it introduced regressions in places the task was not supposed to touch. Along the way, the chat can delete a docstring or a test during an unrelated change - such a loss is easy to miss, because the diff looks consistent with the task until someone compares it line by line with what was there before.

## Static analysis and formatting

Code must pass `ruff check` and `ruff format` without violations before the change is merged. The binding check scope (`select` in `pyproject.toml`) is: `E4`, `E7`, `E9` (syntax errors and obvious errors), `F` (Pyflakes - unused imports and variables, undefined names), `I` (import order), `B` (bugbear - typical pitfalls), `UP` (syntax matching the target Python version), `SIM` (simplifications), `C4` (comprehensions), `C90` (cyclomatic complexity, threshold described in the section on code complexity), `A` (shadowing built-in names), `N` (PEP 8 naming conventions), `RUF` (ruff-specific rules), `G` (lazy placeholders in a logger call instead of an f-string or `.format()`, in line with `standard_logging.md`, section Entry content format). Changing this scope in `pyproject.toml` is a change to the target state of this standard - it requires a deliberate decision, not a silent configuration edit made without remembering that this standard lists the scope here.

The check does not cover markdown files. Since version 0.16 ruff formats code blocks inside documentation, and with `docstring-code-format` enabled, code formatting would rewrite the examples in `docs/` along the way. The exclusion sits in `extend-exclude` and concerns documentation only - formatting of examples in docstrings of the code itself stays enabled. Markdown files have their own formatter, prettier, run from the same `make lint` and `make format` targets as ruff; the rule and the configuration are in `standard_formatting.md`, section Markdown formatting.

## Code complexity

The cyclomatic complexity of a single function does not exceed 15, enforced by the `C901` rule in ruff (`[tool.ruff.lint.mccabe]`, `max-complexity = 15`). The threshold is 15, not 10: at 10 a large share of violations are functions with a natural series of conditions serving one intent, for example normalization or parsing many input variants, where a forced split into smaller functions tears apart coherent logic without improving readability. At 15 the threshold mostly hits functions whose size actually signals several separate responsibilities glued together in one place. A function with branches and loops exceeding this threshold is hard to grasp as a whole during review and hard to cover exhaustively with tests - the number of possible execution paths grows with each additional condition, and review realistically checks only some of them. Exceeding the threshold is a signal to split the function into smaller, named steps, not to raise the threshold for a single case.

## Static typing

Code has type annotations checked with mypy in basic mode, without `--strict`. Obvious type mismatches - a wrong argument, a wrong return value, a missing attribute - are caught before the code runs, without requiring full annotation coverage of every line of existing code. Lack of typing moves the detection of such errors from the review stage to runtime, where the cost of fixing is higher and the error may surface only in production, on a specific set of input data that happened to hit the mismatched type.

## Dead code

Code contains no functions, variables or imports that are not used anywhere, detected with vulture at the confidence threshold that is the default for that tool. The scan covers production code together with tests, because use in a test is use - a scan of production code alone reports as dead the things that tests call, and thereby gives a worse result than the wider scan. Ignored names sit in `ignore_names` in `pyproject.toml`, each with its reason written next to it; these are exclusively names that a library or framework looks up by their text, which vulture has no way to see as uses. Adding a name to this list is a change to the target state of this standard, just like changing the scope of linter rules - it requires a deliberate decision with a reason, not a silent configuration edit. Dead code misleads the reader about the module's actual behavior - it suggests an execution path or a dependency that does not really exist, and it grows over time, because nobody has an incentive to remove it until it explicitly gets in the way.

## Dependency consistency

Dependencies declared in `pyproject.toml` match the dependencies actually imported in code, detected with deptry. An unused declared dependency needlessly increases the surface of security updates and the size of the environment. A dependency that is actually imported but undeclared works today only thanks to its accidental presence in the environment - for example as a transitive dependency of another package - and stops working the moment that accidental presence disappears.

This requirement is checked at the level of the whole repository, not of a single module - a change in one module can reveal a mismatch introduced earlier elsewhere. Under the strict deviation rule of this repository every mismatch found this way blocks review, also one introduced earlier elsewhere; narrowing it to the mismatch of the changed module would be the soft version, which only an explicit decision in `docs/standards/README.md` brings in.

## Code performance requirements

### Performance of database and API interactions

- O(1) or O(n/batch_size) complexity for batch operations.
- O(n) complexity for non-batch operations. Higher complexity requires explicit justification in the code or in the code unit documentation.
- Estimating the total execution time and confronting it with the requirements before deployment.

### Profiling and timing

A suspected performance regression is checked with a profiler, for example `cProfile`, not optimized on the basis of a guess about which place in the code is slow - a guess without measurement regularly hits the wrong place and ends with optimizing a fragment that was not the bottleneck anyway.

Code with a hard time requirement, marked with a `critical` test (see `standard_tests.md`), has a measurement of the real execution time in the test, not only an estimate on paper - an estimate made once, at the first deployment, does not detect a later regression introduced by an unrelated change in the same module.

## Applying the architectural standards

Architectural style above a single module - shared helpers, wrappers for external systems, loggers, cache, library consistency - see `standard_architecture.md`.

## Checklist

- Does new or changed code have line comments outside the two allowed exceptions (complicated algorithm, switch constant)?
- Was documentation removed or changed along the way during an unrelated change noticed and restored or deliberately justified?
- Does the code pass `ruff check` and `ruff format` without violations?
- Does the cyclomatic complexity of every new or changed function stay within the threshold of 15 (rule C901)?
- Does new or changed code have type annotations consistent with the basic mypy mode?
- Does the change avoid introducing dead code - unused functions, variables, imports?
- Do the dependencies in `pyproject.toml` match those actually used - no unused ones, no missing ones?
- Does the complexity of batch and non-batch operations stay within the O(1)/O(n/batch_size)/O(n) requirement, with explicit justification when exceeded?
- When a performance regression was suspected, was a profiler used instead of optimizing on a guess?
- Does code with a hard time requirement have a measurement of the real execution time in a `critical` test?
