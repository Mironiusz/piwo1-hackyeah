# Agentic workflow standard

Document state: 2026-10-03

Purpose: this document describes the entire agentic system of the repository - the chain that takes a task from a raw request to an implemented change, the durable memory system, and the mechanism that keeps the two agentic tools used in this repo (Claude Code and Codex) consistent with each other. The document is written for a human: someone who joins the team and wants to understand how work with agents is done here. It is also meant to serve a future agent instance as source material. After reading the whole of it, it should be possible to reproduce every step of the process by hand, even without calling the corresponding tool by name.

---

## 1. Why this document exists

Knowledge about the agentic system is spread across several places: `CLAUDE.md`/`AGENTS.md` describes the general rules and the "what to open before a task" mapping, `agent_docs/ai_workflows/shape_prd_workflow.md` describes the chain methodology in short, and the skills carry the behavior specific to their phase. The rationale behind decisions, for example why the seed is immutable or why transitions between phases are manual, has no place in any of them.

Without a single place for rationale it is hard to onboard a new person into the process, and the rationale is lost together with the task during which it arose. This document collects all of it in one place, deliberately accepting that part of the content overlaps with what is already in `CLAUDE.md`, `AGENTS.md` and `agent_docs/ai_workflows/shape_prd_workflow.md` - those files remain untouched and still apply as the core of the repository rules. This document supplements them with the full picture and the "why"; it is not their replacement.

### 1.1. Scope and boundaries

Inside: the mechanism of the seed -> shape -> PRD -> plan -> implementation -> review chain and its checkpoints (ch. 3-4), the ten blocking risk categories (ch. 3.3), the interview detail regulator (ch. 3.5), the skills and subagents that serve the chain, archiving a finished initiative to `plans_finished/` and resuming it (ch. 4.6), parallel work on one working tree (ch. 4.7), the `agent_docs`/memory system as a mechanism, not as a format (ch. 5), the duality of the Claude Code/Codex agentic tools, hooks, subagents and the parity test (ch. 6).

This document deliberately overlaps in part with `CLAUDE.md`/`AGENTS.md` (general rules and the "what to open before a task" mapping) and with `agent_docs/ai_workflows/shape_prd_workflow.md` (the chain methodology in short) - those files remain the core of the binding rules; this document supplements them with the full picture and the rationale, it is not a replacement.

What is not here: the format and template of each of the five chain artifacts (SEED, SHAPE, PRD, PLAN, REVIEW) and the format of an `agent_docs/memory` entry - that belongs exclusively to `standard_agent_docs.md` (ch. 5.2 of this document points there directly).

### 1.2. Deviation rule

The deviation rule common to all standards (`docs/standards/README.md`) applies in its strict version: the standard describes the target state and applies in full from the first commit, because a project created from the template has no legacy state that would require a transition period. Any future relaxation of this rule is to be an explicit decision recorded in the standards map, not a state that comes into force on its own.

Narrowing specific to this standard: the unit of deviation is a file of the chain mechanism - a skill definition (`SKILL.md`), a hook, a subagent, a configuration file (`settings.json`, `hooks.json`) or an architecture test (`tests/architecture/test_agent_docs_parity.py`) - not a production code module and not a task artifact in `plans/`. Modifying one of these files is the moment when the obligation to align it with this standard arises.

## 2. Glossary

- Initiative - the `plans/<INITIATIVE>/` directory, grouping one or more related agentic tasks. The initiative name is durable and visible in the repo, so it is set once, at the beginning, and not changed later without a good reason. When an initiative carries more than one task, its five artifacts per task may sit flat or in a `<TASK>/` subdirectory - see section 3.2. An initiative that is explicitly finished or cancelled moves as a whole, under the same name, to the `plans_finished/<INITIATIVE>/` archive (ch. 4.6).
- Task and task prefix - a single unit of work within an initiative. All files of one task share a common prefix `<TASK>_`, for example `docs_SEED.md` and `docs_SHAPE.md` belong to the `docs` task in the `agentic_workflow_docs` initiative.
- SEED - a verbatim record of the request, with an explicit source. Immutable once saved.
- SHAPE - a loose plan, produced by the clarifying interview conducted after the seed is saved.
- PRD - a document that answers "what and why", without any technical decisions.
- PLAN - a document that answers "how", based on facts verified in the code, the database and the documentation.
- REVIEW - a log of the implementation run: what was skipped, what the agent ran into, what decisions were made while writing the code and what needs to be revisited in the future. This is not durable memory - it is the state of a specific task.
- Blocking risk category - one of ten predefined areas (for example the database schema or an external API contract) in which a question asked in the shape phase must be unambiguously resolved before the task can move on to the PRD.
- Detail regulator - a task parameter, a number from 0 to 100 given in the seed and in force from the shape header, which determines how many decisions the agent makes on its own and how many it asks about. It does not reach blocking questions at any point of the scale.
- Parity - the state in which corresponding files on the Claude Code side (`.claude/`) and the Codex side (`.agents/`) have identical rule content, differing only in explicitly allowed places.
- Hook - a Claude Code script run automatically on a specific event, for example at session start or on an attempt to call a tool.
- Subagent - a separate agent definition, with its own set of tools and constraints, called from the main session for a narrowly defined task.
- Dogfooding - running a real task through the whole chain, to check whether the system actually works in practice and does not just look consistent on paper.

## 3. The decision chain - what it is and how it works

### 3.1. Phase sequence and checkpoints

A task goes through the sequence: seed -> shape -> PRD -> plan -> implementation -> review -> (optionally) durable memory -> archiving the initiative, when it is explicitly finished (ch. 4.6). Three skills serve this sequence: `plan-shape` (seed -> shape), `plan-prd` (shape -> PRD -> plan) and `plan-implement` (plan -> implementation -> review -> archiving).

Every transition between skills is manual, with one exception. A skill finishes its work, says plainly what was produced and what can be called next, but does not start the next skill on its own. Reason: every phase boundary is a checkpoint at which the user is to see the result and be able to turn back - automatic transitions would turn the chain into one uninterrupted run with no room for correction, which is the opposite of why this chain was created in the first place. The only exception is the end of the work of `plan-implement`, which itself calls review (`implementation-dod-review`) right after the implementation finishes - described in detail in section 4.4.

### 3.2. Five task artifacts

Every task leaves behind up to five files, each with one allowed kind of content: `<TASK>_SEED.md`, `<TASK>_SHAPE.md`, `<TASK>_PRD.md`, `<TASK>_PLAN.md`, `<TASK>_REVIEW.md`. The exact section template of each of them is described in section 4, next to the skill that produces it.

The default location is flat in `plans/<INITIATIVE>/` - correct as long as the initiative carries one task. When an initiative groups more than one task, a subdirectory per task is allowed: `plans/<INITIATIVE>/<TASK>/<TASK>_SEED.md` and so on for the other four. The five artifacts of one task stay together in both variants - the split, if any, goes by task, never by artifact type (there is no separate directory collecting only SHAPEs or only PRDs from different tasks). The variant is chosen once, at the first save of a seed for a given initiative, and does not change later without a good reason - just like the initiative name.

The process state lives only in these files, never in the conversation history - thanks to that, interrupting a session costs nothing, and every skill called again on the same task loads the existing artifacts and continues from the first unfilled item instead of starting from scratch (more in section 4.5).

### 3.3. Ten blocking risk categories

A question asked in the shape phase that touches one of the categories below must be marked `Block: yes` together with the category name, and it holds back the transition to the PRD until it is unambiguously resolved - always by asking the user, never by guessing. The list is chosen for a service with a database and a programming interface. A project with a different risk profile changes it simultaneously here, in `agent_docs/ai_workflows/shape_prd_workflow.md` and in the `plan-shape` skill.

1. Access token and permission scope contract - the block applies when the task assumes anything about the contents of the token, the way it is resolved to an actor, or the permission scopes. The contract is agreed with the token issuer and with the interface consumers, not guessed from the code. Almost everything in the service depends on this layer, so a wrong assumption here invalidates the work done above it.
2. Stability of the programming interface (API) contract - the block applies when the change touches the shape of a request or a response, a path, an error code or the semantics of an existing field. On the other side there is a consumer outside this repository whose work we cannot see.
3. Database schema - the block applies when the task assumes the existence of a table, column, view or data type without checking. Verification: the schema dump for the actual state of the server, the product specification for the target state. These two sources may differ, and that difference is itself information.
4. Form of a schema change - the block applies to every schema change. Verification: whether the change follows the form described in `standard_database.md`. The category stays blocking after the form is settled, because it guards not only against the form being unknown, but also against the fact that the schema is the only thing in the service that cannot be released again.
5. Source of truth for data - the block applies when the same information occurs in more than one place and the task does not say unambiguously which of them is authoritative. Always a question to the user - this cannot be resolved by reading the code.
6. Time semantics and zone offset - the block applies when the task writes or reads a time value in a way that could change its offset. When the project preserves the offset in force at the moment of the event (`standard_time.md`), the driver layer carries a risk here that a test comparing only instants will not detect.
7. Idempotency and deduplication - the block applies when the change may cause a double write or a record lost on retry, or when it touches the reconciliation key: the external identifier of a record or the idempotency keys (`standard_idempotency.md`).
8. Read visibility and permissions - the block applies when the change touches who can read or do what. A mistake on the permissive side exposes other people's data, a mistake on the restrictive side looks like a broken service; both are easy to introduce in one place and not in the other.
9. Personal data - the block applies when the task touches first and last names, contact data or information about the actions of a specific person. Information about who did not do something or whose work was rejected is data about the assessment of a person, even if it is nowhere called an assessment. This also applies to logs and reports, not only to writes to the database.
10. Query volume and cost - the block applies when the number of rows passing through the change cannot be estimated, or when the change lies on the path of a read performed at every display of a list. A visibility predicate poorly matched to the indexes turns a lookup into a scan, and the cost grows together with the number of rows and permissions.

### 3.4. Blacklist of content forbidden in a PRD

A PRD answers only "what and why", never "how". Forbidden in a PRD: data models, column lists, migrations, code file paths, function names, library decisions, deployment details, secrets and credentials. If while writing the PRD there is an urge to record a technical solution, that material belongs to the implementation plan, not to the PRD.

### 3.5. Interview detail regulator

The same chain handles a small fix in a document and a change touching a contract with an external team, and in both cases the interview has the same depth. The regulator is a knob with which the requester says how many decisions they want to make personally: a number from 0 to 100, where a low value means more decisions made by the agent and a high value means more questions put to the human. This chapter is the source of truth for the whole mechanism - the skill definitions (ch. 4.1-4.3) carry the behavior specific to their phase and point here for the rest.

The parameter and how it is recognized. The value is given in the content of the request. The agent recognizes it regardless of the label used, on one condition: the label is directly followed by a number in the range 0-100. The condition is not a formality - a pattern made of a single letter and a colon opens every Windows disk path, and such paths do occur in the requests of this repository. The reference form, given in the documentation and written by the agent itself, is `C:N`. A request carrying two different occurrences of the parameter stops the agent on one question about which value to adopt, asked before the first interview question: as long as the conflict lasts, it is not even known how inquisitive the rest is supposed to be, and a silent choice between two equivalent values would be exactly the kind of silent decision the whole mechanism is meant to prevent.

Where it is given and where it applies. The value is given in the seed, and it applies from the header of `<TASK>_SHAPE.md`, where `plan-shape` copies it as a separate line under the document state. All three skills read it only from there. Separating these two places is intentional and is not a mistake: the seed is a verbatim and immutable record of the request, so the process parameter must have a second place, so that it can be changed without breaking that inviolability. A difference between the value in the seed and the value in the header is therefore not a conflict and does not trigger a question - the header applies, because by definition it is newer.

Default value. No parameter in the request means 40, that is, the threshold at which the agent asks about every choice with different consequences for the scope or for future tasks.

Five thresholds. The number is given as any value in the range, but it applies as one of five thresholds with explicitly described behavior. The reason is verifiability: the model has no way to tell the behavior at 61 from the behavior at 64, so a continuous scale would give an impression rather than a rule against which a violation can be established. Each threshold contains everything the lower one does and adds its own:

- 0-19: only blocking questions. The agent resolves everything else on its own. A task that touches no risk category may pass the phase without a single question.
- 20-39: additionally, choices whose reversal would require rewriting work already done.
- 40-59: additionally, every choice between variants with different consequences for the task scope or for future tasks. The agent resolves on its own whatever follows from decisions already made. This is the default level.
- 60-79: additionally, things that at lower thresholds the agent would derive as a consequence, and scope boundaries that the request does not name explicitly.
- 80-100: a question about every decision that has more than one reasonable variant. The agent resolves on its own only what has a single variant or is stated explicitly in the repository.

The description of a threshold says what stays at it, not only what disappears. The behavior specific to a phase - what the thresholds mean for questions about the problem and scope, what for the technical decisions of the plan, and what for gaps detected during implementation - is in the definitions of the three skills, because it differs between them enough that a common wording would stop being verifiable.

The regulator's floor. The ten blocking risk categories from ch. 3.3 and the ban on guessing the contract stand outside the regulator's reach across the whole scale. The reason is hierarchical, not cosmetic: `CLAUDE.md` puts "No guessing of contracts - better to ask than to add a fallback" in second place in the hierarchy for resolving rule conflicts, higher than compliance with the standards and readability, so a task parameter cannot stand above that rule. A setting of 0 gives an interview made up only of blocking questions, not an empty interview, and the absence of a due blocking question is a violation, not a saving.

Relevance as the second axis. Before asking a question, the agent checks whether the answer is already in the repository. The obligation applies at every point of the scale, including at 100, and in all three phases. The regulator and relevance are two axes, not one: this check removes unnecessary questions, and the regulator controls only what remains after that removal. Gluing the two into one would make lowering the value cut relevant questions as readily as unnecessary ones. The agent records an answer it found in the artifact together with a pointer to the source, instead of asking the human about it.

Four signals. Finding an answer does not close the topic when one of the following holds. Then the question is asked despite the finding and states plainly which signal triggered it:

1. Two sources say different things about the same thing, including a difference between the actual and the target state - for the database, the difference between the schema dump and the product specification is information in itself (ch. 3.3, category 3).
2. The topic is covered by an open entry in `docs/standards/decision_registry.md` or described in a standard with partial status - the rule is deliberately missing there.
3. The answer stands only in an artifact of a closed task in `plans/`, without confirmation in the code, a standard or the product specification. A task log describes the state at the moment of writing, not the state in force.
4. The document has not been updated after an explicitly identified event that may have invalidated it. This signal requires a specific reference event and does not work as a general expiry date of the document - without this narrowing every older file would generate a question, which would turn the relevance rule into its opposite.

Marking decisions made without asking. An artifact item resolved by the agent instead of by asking carries in the prose the phrase "Agent decision at C:N, without asking", at the place of that item, not in a collective section at the end of the document. A marking in place does not drift apart from the content, and a reader of a single rule immediately sees whether a human stood behind it.

Changing the value during a task. The value may be changed at any moment. The agent then updates the shape header and adds one line saying from which moment the new value applies; items created earlier stay untouched. This freedom is needed, because the right value often emerges only after a few questions, and requiring it to be hit before the conversation would shift the cost of a mistake onto the whole task. Recording the moment of the change is the condition of this freedom - without it the document cannot be read backwards, because it is not known which items were created at which value.

What the regulator does not change. The one-question-at-a-time rule applies unchanged across the whole scale: the regulator controls the selection and depth of questions, never the way they are asked. A series of short questions gives the possibility of changing direction after each answer, which the changeability of the value described above relies on. The place of technical questions does not change either - they are asked only in phase B of `plan-prd` (ch. 4.2). Shape stays non-technical at every point of the scale, and a high value raises there the depth of questions about the problem, scope and rules, not about the solution. Any other placement would create a path that bypasses the PRD, and the PRD is a contract the plan must not silently bypass.

Limits of the mechanism. No automatic check will verify how many questions were asked or whether they were justified - such a test cannot be written and this standard does not promise it. The regulator is therefore a declaration of intent binding the agent, not a switch with guaranteed behavior, and the boundary between thresholds will never be as sharp as a numerical boundary. Verification is only observational, spread over successive tasks, and that is why marking decisions made without asking is not decoration: it is the only material on which that observation can be based.

## 4. Each chain step in detail

### 4.1. `plan-shape`

The entry point to the whole chain. It has three duties that the other skills do not have:

1. It sets the initiative name and the task prefix. If the user has not given them, it proposes both based on the content of the request and waits for confirmation before creating anything on disk - the name is durable and visible in the repo.
2. It checks whether `<TASK>_SEED.md` already exists. The user may have created this file themselves, pasting a ready note instead of dictating the seed in the conversation - in that case `plan-shape` never overwrites it, it only loads it. If the file does not exist, `plan-shape` saves it verbatim as its first action, before asking any question, with an explicit source (conversation with the user, pasted email, meeting note, branch description, report from a team member).
3. It creates `<TASK>_SHAPE.md` with a skeleton of sections (Problem, Recipient and trigger, Current state, Smallest meaningful scope, Out of scope, Functional requirements, Scenarios, Challenging own assumptions, Domain rules or explicit TODO, Notes on data/performance/security, Open questions), filling in at the start only what follows directly from the seed.

Then it conducts the interview: one question at a time, closed ones via `AskUserQuestion`, open ones as plain text. It reads the regulator value (ch. 3.5) from the content of the seed and writes it into the header of `<TASK>_SHAPE.md`, from where the other phases read it, and the thresholds govern the selection and depth of questions, never the way they are asked. After each answer it adds a minimal note to the appropriate section, removes the corresponding entry from "Open questions" and saves the file - the interview can be interrupted at any moment, because the state lives in the file, not in the conversation. Every question touching one of the ten risk categories (section 3.3) is marked `Block: yes` together with the category name. The "Challenging own assumptions" section - a record of the questions the agent asked itself about its own understanding of the problem, together with what came out of them - is mandatory and must not stay empty: if nothing raises doubts, it is a sign that the problem has not been understood yet.

The skill finishes its work when all sections are filled in and no item in "Open questions" has `Block: yes`. It then changes the document state to "interview closed" and reports that `plan-prd` can be called - it does not do it on its own.

### 4.2. `plan-prd`

It produces two files in two clearly separated phases, because the PRD is banned from containing technical content and the implementation plan requires it - mixing both in one run would lead to freezing technical decisions prematurely.

Phase A - PRD: it loads `<TASK>_SHAPE.md` and `<TASK>_SEED.md`; it stops if the shape has unresolved `Block: yes` questions (it does not try to resolve them by guessing, it asks them to the user and comes back after the answer); it writes `<TASK>_PRD.md` according to the template (Business goal, Problem and its consequences, Scope, Out of scope, Functional requirements, Acceptance criteria, Domain rules, Dependencies and impact on other modules, Risks and notes), observing the blacklist from section 3.4; it shows the PRD to the user and waits for confirmation before moving to phase B - this is the only gate between "what" and "how" in this skill, so it never passes through it silently.

Phase B - implementation plan: it opens the documents indicated by the task type -> document mapping from `CLAUDE.md`/`AGENTS.md`; it verifies in the code, the database and the documentation everything the PRD assumes, and records the findings in the "Facts" section in the format from `standard_agent_docs.md`; it computes the blast radius of the change, that is, the call sites, schema objects, configuration keys and automatic checks touched indirectly, and when this list goes beyond the scope agreed in the PRD, it stops and asks about splitting the plan instead of silently expanding the scope; it writes `<TASK>_PLAN.md` according to the template (Goal, Facts, Decisions, Scope of changes, Rollout order, Definition of Done, Risks, Open questions, Supplementary files), where every step in "Scope of changes" has specific names of files, functions and data contracts, never a description in the style of "something like"; if verification overturns an assumption from the PRD, it stops and goes back to phase A, because the PRD is a contract and must not be silently bypassed in the plan. It finishes when the plan meets the completeness criteria that `plan-implement` will require anyway: zero TODOs, zero items in "Open questions", every step with an unambiguous input and output. It reads the regulator value (ch. 3.5) from the header of `<TASK>_SHAPE.md`, never from the seed, and it is this value that determines here how many technical decisions the skill makes on its own and how many it puts to the user.

### 4.3. `plan-implement`

Implementing exactly what is in the given plan and in the supplementary files, without guessing what the plan does not specify. The run has nine steps:

1. Loading the plan and all the supplementary files it points to.
2. Reviewing the completeness of the plan before writing any code: whether every step has an unambiguous input and output and specific names, not "something in the style of"; whether any TODOs, `[UNCLEAR]` markers or items in "Open questions" remain; whether the plan assumes something that can and must be verified in the code or the database instead of being taken on faith; whether the facts of the plan are still true after the changes that have happened since their check date - the format check verifies only the form of the evidence, and the plan stops being true at the first merge into the files it cites.
3. If it finds gaps, it stops before writing code and asks - one question at a time, closed ones via `AskUserQuestion`, open ones as text - and after the answer it adds a minimal fragment to the plan, removes the entry from "Open questions" and goes back to step 2. It also checks whether the related SHAPE has unresolved `Block: yes` items - if it does, it goes back to `plan-prd` instead of trying to resolve them on its own. How many gaps it resolves on its own and how many it asks about is determined by the regulator read from the shape header (ch. 3.5). This is the place where a silent decision of the agent costs the most, because it goes straight into the code.
4. When the plan is complete, it implements it step by step, following the repo conventions (`CLAUDE.md`, `docs/standards`).
5. If during implementation it runs into something the plan did not foresee, it stops at that point and asks the user. It records what happened in `<TASK>_REVIEW.md` (not in the plan itself - `_PLAN.md` is a contract and does not grow during the work, while `_REVIEW.md` is meant exactly for what was skipped, what was run into and what decisions were made at the code), and then continues from the point of interruption.
6. At the end it summarizes what was done relative to the plan and whether anything was skipped or changed, together with the reason.
7. It assesses whether the task yields anything worth recording durably in `agent_docs/memory/<group>/<module>.md` - full criteria in section 5.2. If nothing qualifies, it adds nothing - this is a deliberate assessment, not an obligation at any cost.
8. It calls `implementation-dod-review` on the changes made. This is the only transition in the whole chain that happens automatically - `plan-implement` itself starts the review after finishing its work, instead of waiting for the user to call it manually.
9. After returning from the review it completes the record in `<TASK>_REVIEW.md` and checks whether the whole initiative is explicitly finished in the sense of ch. 4.6: a `ready` verdict covering its whole scope or another explicit closure. Settling one task does not close a multi-task directory. If the initiative is finished, it moves the whole directory to `plans_finished/` and gives the new path in the final message. A review of a plan or of part of the code does not trigger the move; an ambiguous status leaves the directory in place and ends with a question to the user.

### 4.4. Final review: `implementation-dod-review` and `dod-reviewer`

The review criteria, the report order and the Definition of Done of the repository are described in `docs/standards/standard_review.md` - that is the source of truth for this topic, not this chapter.

The same process is available in two forms: as the `implementation-dod-review` skill, called directly or automatically by `plan-implement` (step 8 of ch. 4.3), and as the `dod-reviewer` subagent (`.claude/agents/dod-reviewer.md`), which has access to `Read`, `Grep`, `Glob`, `Bash`, `PowerShell`, does not implement fixes, and has the same skill (`implementation-dod-review`) assigned explicitly in its definition. `dod-reviewer` works in `permissionMode: plan` (it cannot make changes) with a limit of 16 turns.

Review stays read-only with respect to the archive as well: it reports what scope the verdict covers and whether the initiative qualifies for `plans_finished/` according to ch. 4.6, but it does not perform the move itself - that belongs to `plan-implement` (step 9 of ch. 4.3) or to an agent whom the user explicitly told to clean up.

### 4.5. Resuming after a break

Each of the three skills works the same way in this respect: the process state lives only in the files in `plans/<INITIATIVE>/`, never in the conversation history. A skill called again on a task whose artifacts already exist loads them and continues from the first unfilled item, instead of starting from scratch. Thanks to this, interrupting a session - for any reason, at any moment - costs nothing: it is enough to call the same skill on the same file again.

Resuming from a handover note left by an interrupted session starts with reading the state, not with repairing it: `git status`, the contents of both initiative locations and a comparison of the files with `git show HEAD:<file>`. An interrupted session or an agent being stopped may finish its work after the note was saved, so a state described in it as urgent may be out of date, and repairing such a state on a tree that is already consistent destroys the only copy. A mismatch between the note and the actual state is recorded in the review.

Resuming after a break concerns an initiative that still sits in `plans/`. An initiative that has been explicitly finished and moved to the archive returns to work by another route - described in ch. 4.6.

### 4.6. Archiving and resuming an initiative

This chapter is the only full description of when an initiative leaves `plans/`, where it goes and how it comes back. The other places in the repository - the `CLAUDE.md`/`AGENTS.md` core, `agent_docs/ai_workflows/shape_prd_workflow.md`, the chain skills, the reviewer definitions and `plans_finished/README.md` - point here instead of repeating the rule.

Two locations. `plans/` is the place of current work. `plans_finished/` is the archive of whole initiatives that have been explicitly finished or explicitly cancelled. An initiative directory moves between them as a whole, under the same name and with the same file layout - also when it carries the task subdirectories from section 3.2. Archiving does not change names or prefixes, does not merge directories and does not choose which files to keep. An empty or non-existent `plans_finished/` is not an error: the directory is created at the first move, and `plans_finished/README.md` only says what this place is and points here. The archive has no separate status registry, no status file per initiative and no new closure marker - the state of an initiative is told by its own artifacts.

The unit of archiving is the whole initiative, that is, the directory. Closing one stage, one task or part of the scope is not closing the initiative: a directory with several tasks stays in `plans/` until all of its tasks are settled or the initiative itself is explicitly closed. Reason: the directory holds the history of one matter as a whole, and moving part of the files would tear apart the mutual references between the artifacts.

The evidence of completion must be explicit, concern the whole initiative and refer to the current state of the work. One of the following two is enough:

1. A final `ready` verdict in `<TASK>_REVIEW.md`, covering the whole scope of the initiative. It does not require a separate closure entry - the verdict itself is the closure.
2. When there is no `ready`: another explicit marking of the completion or cancellation of the whole initiative, recorded in its artifacts - for example a review state line saying "initiative closed" or "initiative cancelled", with the reason recorded. A full chain of artifacts is not a condition: an initiative settled with a review alone, without a PRD and a PLAN, qualifies just the same.

What must not be accepted as evidence, although it is tempting: the mere occurrence of the word `ready` anywhere in the document, a `ready after minor fixes` or `not ready` verdict, a review covering only the plan or part of the code, a complete set of five files, a closed interview in SHAPE, the "plan closed" marker in PLAN (this marker brings the plan under the format check from `standard_agent_docs.md`, it does not close the initiative), the age of the directory or a lack of activity. Each of these things describes a stage, not the end of the matter. A lack of activity is not a cancellation - a cancellation has to be recorded too.

Contradictions are not resolved by guessing. When one entry speaks of closure and another of unfinished or resumed work, the agent reads the order and the scope of the entries. A later closing entry that explicitly settles an earlier list of gaps is not a contradiction. Actions left to the user as post-closure steps do not block archiving, but archiving proves nothing about them: moving the directory does not confirm that these actions were performed or that the code was deployed. An unsettled contradiction, an ambiguous status or a closure recommendation waiting for the user's decision stop the move - the directory stays in `plans/`, and the agent asks the user about the state of the initiative before anything else.

Who moves it and when. With unambiguous evidence the agent moves the initiative on its own, without asking. In the chain this is done by `plan-implement` after returning from the review (step 9 of ch. 4.3): first it completes the current record in the review, then it checks whether the verdict covers the whole initiative and whether nothing undermines its completion, and only then does it move the directory. The final message gives the new path. Outside the chain the same criterion is applied by an agent whom the user told to clean up `plans/` or to close a specific initiative. Review - the `implementation-dod-review` skill and the `dod-reviewer` subagent - stays read-only: it reports what scope the verdict covers and whether the initiative qualifies for the archive, but it does not move anything. An explicit read-only restriction from the user takes precedence over every rule in this chapter.

How to move it. Before the move the agent checks: that the target `plans_finished/<INITIATIVE>/` does not exist (an existing target means a collision to be clarified with the user, never merging or overwriting); that the source directory has no changes in `git status` made after the qualification, because a change after closure undermines the closure; that the resolved source and target paths lie in the same repository and the directory contains no links leading outside the repository; that it knows the list of files and their checksums, so that after the move it can confirm the set is complete. It moves using the native directory move command, not `git mv` - the git index and the commit are handled by a human, in line with the rules for working with git in the repository core. An error during the move stops any further moving; the agent deletes neither the source nor the leftovers, and does not overwrite the target on retry.

Protecting history. The move does not change the content of seeds, of existing review entries, of `agent_docs/memory/` entries or of the frozen materials of the initiative: dated reports, readouts, attachments and correspondence. An old path in such a record is a historical record and stays that way. Only editable references are updated: documentation, docstrings, active artifacts of other initiatives, maps, indexes and registries - in the `_PLAN.md` of another initiative only the location of the reference changes, never the contract. Two boundaries of this rule have to be named explicitly, because otherwise they are a gray zone: an attachment is frozen as to its data, queries and logic, but the run instruction in the docstring of an attachment script is a reference and gets the new path - this is the only allowed change in such a file, confirmed by comparing the tokens outside the docstring; the `_SHAPE.md` and `_PLAN.md` of the archived initiative itself are treated like the plan of another initiative, that is, only the location of references between artifacts changes in them, never the content of the findings, unless the document itself declares an append-instead-of-rewrite rule - then it stays a historical record in its entirety. References in code and tools that actually read the files of the initiative must keep working after the move; a scan of path names alone has to tell apart an editable reference, a historical record and a real consumer of the path. The same rule applies in both directions of the move.

Resumption. An initiative returns from `plans_finished/` to `plans/` only on an instruction to continue the same work. Merely reading the archive, a question about a historical result or a review of an old change resumes nothing. The return is a move of the whole directory under the same name, with the same checks as for archiving, after which the agent adds a resumption entry to the review: the date, the reason and the scope. The existing closure history stays untouched - resumption is another entry, not a correction of the previous one. When the initiative has no review, the agent creates one according to `standard_agent_docs.md` with this entry as the first one. A new scope that only touches the topic of a closed initiative gets a separate initiative instead of a resumption. Before creating a new directory in `plans/` the agent checks both locations; the same name present in both at once is a state to be clarified with the user, not to be chosen arbitrarily.

Automatic checks do not weaken through archiving: the plan format check from `standard_agent_docs.md` covers `plans_finished/` on equal terms with `plans/`, the prose style check scans them recursively with no exception for the archive, and markdown formatting deliberately skips them (`.prettierignore`), so that the format check does not force rewriting frozen materials. Apart from formatting, moved documents are subject to the same rules they were subject to in `plans/`. Archiving is not an occasion for bulk formatting of protected materials.

### 4.7. Parallel work on one working tree

A second agent session or a human may be working in parallel on one working tree. A test run measures the whole tree, not one change, so red caused by someone else's work in progress looks exactly like one's own regression, and fixing what someone is writing right now is getting in their way.

- On unexpected red the agent checks `git status --short` and the modification time of files it has not touched. A write later than the start of the session means someone else's work. The agent tells the user about it instead of fixing it and repeats the run only after that work is wrapped up.
- A step that is destructive to the environment, for example recreating the database, deleting data or moving the head of the migration chain, requires asking the user on a shared tree, even when it stands explicitly in an approved plan.
- A measurement made at the start of a task goes stale. Before writing outward, to someone else's system or database, the agent repeats the measurement right before the write itself.
- A movement of `HEAD` during the session, such as a commit or merge made by a human, invalidates conclusions issued on the earlier state. Before each phase the agent checks `git log --oneline -3` and `git status --short`, and after a movement of `HEAD` it compares the evidence files and verifies the issued verdicts again, keeping their original wording as history.
- A message from the editing tool that a file has changed since the last read is a signal of someone else's edit, faster than the modification time. The agent then checks the `git diff` of the file and does not revert the other person's change, but takes it as the current state.
- During a longer editing of an artifact the agent, before closing the work, reads the key sections again and compares them with the reading from the start. Its own write stamps the file with the agent's time and hides someone else's edit from the modification time check.

## 5. The `agent_docs`/memory system

### 5.1. `docs/` versus `agent_docs/`

The repository distinguishes two layers of documentation. `docs/` is fixed and not editable by the agent. It holds `docs/standards/` (fixed standards written by a human, this document is one of them) and directories that the project adds itself, for example a machine-generated schema dump, vendor documentation or operational knowledge about the environment - each entered in the map in `docs/standards/README.md` together with its provenance. The agent never edits `docs/` outside a task that is explicitly about it.

`agent_docs/` is the opposite - it is the layer actively written by the agent, made up of three parts: `agent_docs/session_context.md` (the project description inserted at session start by the hook from ch. 6.3), `agent_docs/ai_workflows/shape_prd_workflow.md` (the methodology of the chain described in sections 3-4 of this document) and `agent_docs/memory/` (durable memory of decisions per module, described below).

### 5.2. `agent_docs/memory`

`agent_docs/memory/` is durable memory of decisions per module - something different from Claude's global auto-memory (`~/.claude/projects/.../memory/`), which holds the preferences and context of a specific user. `agent_docs/memory/` holds knowledge about the repository itself, available to every tool - to Claude Code and Codex alike.

Entry format, group structure and the rules for when to write and when not to: see `docs/standards/standard_agent_docs.md`, section "agent_docs/memory entry format" - that is the only source of truth for this convention.

## 6. Implementation and technicalities

### 6.1. Duality of `.claude/` vs `.agents/` (Claude Code versus Codex)

The repository is used from two agentic tools - Claude Code and Codex - and maintains two parallel sets of skills for them: `.claude/skills/` and `.agents/skills/`. This is intended duplication, not accidental sprawl: by default the content of a skill is to differ between the copies only in the path to the scripts, never in the rules. Full identity of the two tools is not the goal - subagents in the sense defined in the glossary are a mechanism of Claude Code only, and `.agents/` contains only `skills`. Hooks exist on both sides, but not as a full, symmetric set - see ch. 6.3. The requirement is narrower: every shared chain step must be possible to go through in both tools on the same artifacts and the same rules.

Five skills of the team have a pair on both sides: `plan-shape`, `plan-prd`, `plan-implement`, `implementation-dod-review`, `load-context`. Today there is not a single skill that exists only on one side - the exceptions allowlist in the parity test is empty and is to stay that way. A one-sided exception requires all of the following together: a dependency on a capability available in only one tool, an explicit decision in an accepted task plan and an entry on that allowlist. Mere convenience or lack of time for the second version is not a reason - a skill without a pair silently splits the repository into two different processes depending on what someone opened it with.

A Codex-only exception requires all of the following together: a platform dependency, an explicit decision in an accepted task plan and an entry on the strict allowlist of the architecture test. It must not be used for an ordinary shared skill or to hide an accidentally missing copy. Every allowlist entry must actually exist only in `.agents/skills/`.

A third-party skill installed by its own installer is a separate case, not a skill of the team. Today there is one: `impeccable` (Impeccable 4.5.0, Apache 2.0), installed on 2026-10-03 into both `.claude/skills/` and `.agents/skills/`, together with four Claude Code agent roles `.claude/agents/impeccable-*.md`, whose Codex variants the installer put inside the skill, in `.agents/skills/impeccable/agents/`. The installer generates each variant for its tool, so the two copies differ on purpose - in the invocation prefix (`/impeccable` versus `$impeccable`), in the frontmatter keys and in the paths - and an edit made by hand would be overwritten by the next update of the skill. Such a skill is not edited by the team and is not held to its rules: it is exempt from the two identity checks of ch. 6.2 and from the prose gate of `standard_formatting.md`, while the check that it exists on both sides still covers it. The list of third-party skills and roles is one, in `tests/architecture/common_vendored_content.py`. An entry names a skill or a role separately, never a pattern, and `tests/architecture/test_vendored_content.py` fails when an entry points to something no longer in the repository. A skill the team writes or edits never goes on that list.

`load-context` deserves a separate explanation, because it is not a step of the seed -> plan chain described in section 4 - it is a separate helper tool that on demand creates a single dump (`output.txt`) of the contents of a given repository folder, so that analysis can rely on one file instead of many individual reads. Even so it is covered by the same parity mechanism as the chain skills, because it exists in both locations.

### 6.2. Parity test

`tests/architecture/test_agent_docs_parity.py` is the anti-drift gate for the whole duality described above. It contains four tests: parity of `AGENTS.md`/`CLAUDE.md`; a ban on skills that exist only on the Claude side and a ban on unknown skills that exist only on the Codex side outside the strict allowlist; identity of the content of every shared pair of skills after normalization; and identity of the instructions of every pair of agent role definitions (ch. 6.4). The test additionally requires every allowlisted Codex-only skill to exist in `.agents/skills/` and to have no copy in `.claude/skills/`, and every role of the team to have a variant on both sides. The two identity checks skip the third-party skills and roles from ch. 6.1.

Normalization of the core and skill pairs allows three, and only three, explicitly named differences: the core file name (`AGENTS.md` or `CLAUDE.md` reduced to a common form), the phrase "Codex is to apply" / "Claude Code is to apply" (reduced to a common form), and the path to the skill scripts (`.claude/skills/<name>/scripts/` reduced to `scripts/`). Normalization of role pairs is a separate list and has exactly one item on it: the name of the command runner ("via `Bash` or `PowerShell`" versus "via the terminal"), because Codex does not know tools with those names. Each of these rules is one deliberately allowed difference - adding another one is to be a decision, not an accident, and an accidental difference is to be fixed in the content of the files, not hidden by normalization. The comparison works through `difflib.SequenceMatcher`, not line by line, so that a section inserted or removed in one file does not distort the diff for the rest of the file. The test code (the `PLAN_REFERENCE` constant) points in the failure message to this chapter as the place with the list of allowed exceptions; the message about a role pair mismatch points separately, to ch. 6.4.

Role pairs are compared by the content as read, not by the raw text of the file: the Claude Code variant is a markdown file with frontmatter, the Codex variant is the `developer_instructions` key in a TOML file with literal end-of-line escape sequences. The frontmatter stays out of the comparison, because it carries tool configuration (tool list, permission mode, turn limit) that has no counterpart on the other side.

### 6.3. Hooks

One hook has a counterpart on both sides, one works only in Claude Code:

- `local_docs_context.py` - a `SessionStart` hook, registered separately for each tool (`.claude/settings.json` and `.codex/hooks.json`), with the same script in `.claude/hooks/` and `.codex/hooks/`. Byte identity of the two copies is guarded by `tests/architecture/test_session_context_hook.py`. At the start of every session it adds to the context the content of `agent_docs/session_context.md` (the project description and the pointer to the product specification), a warning about personal skills shadowing project skills (ch. 6.5), a pointer to the `docs/standards/README.md` map and to the decisions registry, and two items from `agent_docs/` (the chain workflow and the memory convention). Apart from `session_context.md` it only checks whether the files exist and does not read their content, so as not to raise the cost of session start.
- `block_dangerous_commands.py` - a `PreToolUse` hook, only in Claude Code, with no counterpart in Codex. It runs on an attempt to call `Bash` or `PowerShell`. It blocks `git reset --hard`, `git clean`, `git restore` touching the working tree, forms of `git checkout` that point to a path or pathspec, recursive deletion via `rm`, `Remove-Item`, PowerShell aliases and cmd commands with the `/s` flag, deletion via `find -delete`, deletion of the `.git` directory and of `.env` files, and `git commit` and `git push`, also with the `-C` or `-c` option before the command - commit and push are done by a human. `git restore --staged` without the `--worktree` flag passes, because it changes only the index. An ambiguous `git checkout <name>` is blocked when `<name>` is also an existing path; to switch to such a branch, the unambiguous `git switch` is used. On invalid input or an exception the hook works fail-closed: it returns a valid `deny` decision with exit code 0 and gives the error type without the command content. Thanks to this, an error in the guard does not disable the protection as a non-blocking hook error.

Codex therefore gets the same start-up context as Claude Code, but has no protection against dangerous commands corresponding to `block_dangerous_commands.py`.

### 6.4. Claude-only subagents

Two subagents of the team exist only in `.claude/agents/`, with no counterpart in `.agents/` (which contains only skills):

- `repo-researcher` - an agent for fast, read-only research in the repository. It has access to `Read`, `Grep`, `Glob`, `Bash`, `PowerShell`, works in `permissionMode: plan` (it does not edit files or run commands with side effects), with a limit of 12 turns. It returns exactly three kinds of items: a finding together with a pointer to the file and line, an explicit "not found" for a question with no answer in the repository, and an explicit "not checked" for a question it did not get to before the call limit. It does not return recommendations or risk assessments, because assessment belongs to the caller: the research role knows a slice of the repository but does not know the context of the task, so its recommendation would be a conclusion drawn from an incomplete picture. No answer is a result here, not a failure.
- `dod-reviewer` - an agent for review against the Definition of Done. The same tools as above, plus the explicitly assigned `implementation-dod-review` skill, with a limit of 16 turns. It does not implement fixes, it only assesses the readiness of the changes, in the same reporting order as described above in this section.

Each of these roles has a variant on the Codex side, in a different mechanism and a different format: `.codex/agents/<name>.toml`, a native Codex role, not a subagent. The pair of variants is covered by the parity check from ch. 6.2 - a change to the content of a role goes to both files in parallel, and a mismatch beyond the single allowed difference in the command runner name stops the tests.

The four `impeccable-*` definitions in `.claude/agents/` are not roles of the team: they came with the third-party skill from ch. 6.1, their Codex variants live inside that skill, and the role parity check skips them.

Turn limit. Both roles end their work at the turn limit, and without an explicit instruction they can stop at it without a report, because a broad slice of the repository eats up the limit on reading alone. That is why both definitions tell them to hand in the report at the latest after about ten tool calls, with an explicit list of what they did not manage to check. The caller narrows the file list in the instruction, and splits a large scope into several parallel calls with disjoint file lists and a shared description of the gates already run by the main session, so that the roles do not repeat them. A role stopped without a report is resumed with an instruction to hand in the report without further tool calls, not with a request to continue.

What stays outside the check is something else: content consistency between the `implementation-dod-review` skill and the `dod-reviewer` definition - these two documents describe the same process, but they are not copies of each other, so comparing them by machine makes no sense and it has to be watched manually.

### 6.5. Personal/project skill name collision

When a skill with the same name exists simultaneously in the project directory (`.claude/skills/`) and in the user's personal directory (`~/.claude/skills/`), Claude Code loads the personal copy - this is documented behavior, with no configuration option that would change it. With subagents it is the other way round: the definition from the project's `.claude/agents/` wins over the personal one. The loading order for the same kind of collision on the Codex side has not been established.

Rule: skills with the names of project skills are not kept in the personal directory. The personal copy is not covered by the parity test from ch. 6.2 and goes stale independently, so calling the skill by name would run content different from the one described in this standard, without any message. The `local_docs_context.py` hook checks the directories `~/.claude/skills`, `~/.agents/skills` and `~/.codex/skills` at session start and prints a warning with the names of the colliding skills. Until the collision is removed, the skill content is read directly from `.claude/skills/<name>/SKILL.md`.

## 7. Where to find living examples

This document describes the chain abstractly. The template does not carry a sample initiative - the first living example is the first initiative of the project run through the full chain.

More generally: any directory containing a complete set of files `_SEED.md`, `_SHAPE.md`, `_PRD.md`, `_PLAN.md` (and optionally `_REVIEW.md`) - whether `plans/<INITIATIVE>/` directly, `plans/<INITIATIVE>/<TASK>/`, or their counterparts under `plans_finished/` - is a living example of what the chain looks like in practice for a specific type of task. References to `plans/<INITIATIVE>/` in seeds, old review entries and memory of an archived initiative are a historical record - a directory with that name then has to be looked for in `plans_finished/`.

## 8. Checklist

- A task goes through seed -> shape -> PRD -> plan -> implementation -> review, with a manual transition between phases except for one exception: `plan-implement` itself calls review at the end.
- Every shape-phase question touching one of the ten blocking risk categories (ch. 3.3) has `Block: yes` and is unambiguously resolved before moving to the PRD.
- The PRD contains nothing from the blacklist: data models, columns, migrations, code paths, function names, libraries, deployment, secrets (ch. 3.4).
- The PLAN has specific names of files, functions and data contracts in every "Scope of changes" step, zero TODOs, zero open questions.
- The regulator value stands in the shape header, and every item resolved without asking carries the phrase about the agent's decision (ch. 3.5).
- The regulator has not removed a single blocking question - the ten categories apply at every point of the scale (ch. 3.3 and 3.5).
- The format of each of the five chain artifacts and of an `agent_docs/memory` entry - see `standard_agent_docs.md`, not this document.
- REVIEW describes the run of a specific task and loses its meaning after the task is closed - durable knowledge goes to `agent_docs/memory`, never the other way round.
- An initiative goes to `plans_finished/` as a whole and only on explicit evidence of completion or cancellation: a final `ready` for the whole scope or another explicit closure. A complete set of files, a closed interview, a closed plan, settling one task out of several, a partial verdict or the age of the directory do not replace it; a contradictory status means a question to the user, not a move (ch. 4.6).
- The move does not change seeds, old review and memory entries or frozen materials; it updates only editable references, in both directions. Resuming the same work means returning the directory to `plans/` with an added resumption entry; a new scope is a new initiative (ch. 4.6).
- A shared chain step works the same way in Claude Code and Codex, on the same artifacts and rules (ch. 6.1).
- Every Codex-only exception in skills has an entry on the allowlist in the architecture test and a justification in an accepted task plan (ch. 6.1-6.2).
- Only a third-party skill installed by its own installer, and the agent roles that came with it, stand on the list in `tests/architecture/common_vendored_content.py`, each by name; a skill or role the team writes or edits does not (ch. 6.1).
- Hooks and subagents are not symmetric between Claude Code and Codex - check ch. 6.3-6.4 before assuming that a mechanism works the same way on both sides.
- On a shared tree, unexpected red and a destructive step start with checking `git status` and the modification time of files, and someone else's work in progress is not fixed (ch. 4.7).
- A call of the `repo-researcher` or `dod-reviewer` role has a narrowed file list, and the role hands in its report before the turn limit (ch. 6.4).
- There are no skills with the names of project skills in the user's personal directory; a collision warning from the hook means that the skill content has to be read directly from `.claude/skills/<name>/SKILL.md` (ch. 6.5).
- The chapter numbering of this document is cited by other files of the repo - every future change of the numbering requires checking all citing places, not only the content of the document itself.
