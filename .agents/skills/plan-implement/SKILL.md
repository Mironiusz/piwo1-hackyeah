Before starting, it checks whether the plan is complete - if something is missing, it stops, asks the user directly, adds the answer to the plan and only then returns to implementation. At the end it appends an entry to agent_docs/memory if there is something to record, calls the review itself, and moves an explicitly finished initiative in its entirety to plans_finished/. The third skill of the chain plan-shape -> plan-prd -> plan-implement, but it also works on its own on any plan in this format. Use when the user wants to carry out a previously written plan.

# Executing the plan

Goal: implement exactly what is in the given plan document and in the supplementary files it refers to - without guessing what the plan does not specify.

## Flow

1. Read the plan and all supplementary files it points to (links, data dumps, code or SQL fragments).
2. Before you write any code, review the plan's completeness:
   - does every step have an unambiguous input and output and concrete names (file, function, data contract), rather than "something like"?
   - are there still TODOs, `[UNCLEAR]` or items in the "Open questions" section?
   - does the plan assume something that can and must be verified in the code or in the database (the existence of a table, column, endpoint, function) instead of taking it on faith? Checking the repository is an obligation here independent of the regulator - an answer found in the code, a standard or the product specification pointed to in `CLAUDE.md` does not turn into a question to the user, unless it is disputed or out of date.
   - are the facts from the `## Facts` section still true? The format check verifies only the form of the evidence, and the plan stops being true with the first merge into the files it cites. Intersect the list of files changed since the check date of the facts (`git log --since`, `git diff --name-only`) with the files cited in the facts, and for every hit check the content under the reference, not the reference alone. Separately check assumptions about the state of the world that are not a line of code: free numbers, counts, the existence of functions the plan intends to add, the tips of branches of other repositories. You correct an outdated fact in the plan before starting, with a new check date.
3. If you find gaps, stop before writing code. Do not guess. How many of these gaps you resolve yourself and how many you ask about is set by the regulator read from the header of `<TASK>_SHAPE.md`; no value means 40. At 0-19 you ask only about gaps touching blocking risk categories, at 80-100 about every gap that has more than one reasonable variant. At no threshold are you allowed to fill a gap by guessing a contract, and record every gap filled in independently in `<NAME>_REVIEW.md` with the phrase "Agent decision at C:N, without asking". Ask only one question at a time - AskUserQuestion for closed decisions, plain text for open questions. After the answer, add a minimal fragment to the plan in the appropriate section, remove the corresponding entry from "Open questions" and save the file. Return to step 2 only after all gaps are filled. If the plan comes from the `plan-shape` -> `plan-prd` chain, also check whether the related `_SHAPE.md` has unresolved `Block: yes` questions - if it has, go back to `plan-prd`, do not try to resolve them here.
4. When the plan is complete, implement it step by step, following the repo conventions (CLAUDE.md, docs/standards).
5. If during implementation you run into something the plan did not foresee, stop at that point and ask the user. Record what happened in `<NAME>_REVIEW.md` (a file next to `_PLAN.md`, the same task name with the `_REVIEW.md` suffix - create it if this is the first such situation in this task), not in the plan itself: `_PLAN.md` is a contract and does not grow during implementation, `_REVIEW.md` is for what was skipped, what was run into and what decisions were made while writing code. Continue from the point of interruption - do not start the whole thing over.
6. At the end, summarize what was done relative to the plan and whether anything was skipped or changed during implementation, together with the reason.
7. Assess whether the task yields anything worth recording durably - a recurring pattern, a non-obvious workflow, an architectural decision affecting the future (full criteria in `docs/standards/standard_agent_docs.md`, section "agent_docs/memory entry format"). If so, append an entry to `agent_docs/memory/<group>/<module>.md` for the affected module (create the file if the module does not have one yet) according to the template from that section of the standard. If nothing qualifies for recording, add nothing - this is a deliberate assessment, not an obligation at any cost.
8. Call the `implementation-dod-review` skill on the changes made. This is the only transition in the whole chain that happens automatically - `plan-implement` starts the review itself after finishing its work, instead of waiting for the user to call it manually.
9. After returning from the review, close the current record in `<NAME>_REVIEW.md` (the verdict together with the scope it covers) and check whether the whole initiative is explicitly finished according to `docs/standards/standard_agentic_workflow.md` ch. 4.6: a final `ready` for the whole scope of the initiative or another explicit closure, with no entries undermining the completion. Settling one task does not close a directory with several tasks. If the initiative is finished, move the whole `plans/<INITIATIVE>/` directory to `plans_finished/<INITIATIVE>/` according to that chapter (the target does not exist, no changes in git since qualification, a native move, the complete set of files confirmed, editable references corrected, tools that read the initiative's files still work, seeds and past entries untouched) and give the new path in the final message. A review of the plan or of part of the code, `ready after minor fixes` and `not ready` do not trigger the move. A contradictory or ambiguous status leaves the directory in `plans/` and ends with a question to the user. An explicit read-only restriction from the user takes precedence.

## Rules

- Zero guessing of contracts, names, scopes - that is a question for the user, not a decision of the model.
- The regulator does not reach the blocks or the ban on guessing a contract - at every value, a gap that cannot be resolved without knowledge from outside the repository is a question to the user.
- Update the status in the plan as you go, so that the user sees the progress without reading the whole conversation.
- Settle acceptance criteria with a run wherever a run is possible: tests, a brought-up local environment, reading the database state. Reading code and documents is weaker evidence than a run and does not replace it when the environment can be brought up.
- After every merge during implementation, repeat the fact check from step 2 for the files the merge changed.
- On a tree on which another session may be working in parallel, apply the rules from `docs/standards/standard_agentic_workflow.md` ch. 4.7: an unexpected red result and a destructive step start with checking `git status` and the modification time of files, and someone else's work in progress is not fixed.
- `_PLAN.md` is the intent and does not grow during the work; `_REVIEW.md` is the run and grows; `agent_docs/memory/` is durable knowledge, which receives only what survives the end of the task.
- A plan under `plans_finished/` belongs to a finished initiative. Do not implement from the archive: first the resumption, that is, the return of the directory to `plans/` on the user's instruction with a resumption entry in `_REVIEW.md` (ch. 4.6 of the workflow standard). Merely reading the archive resumes nothing.
- `_REVIEW.md` and memory entries name a place in another file by a section, an item or a code symbol, never by a line number. See `docs/standards/standard_formatting.md`, section References to a place in a file.
- `_REVIEW.md` and memory entries have no bold in prose or bold labels opening a paragraph or a list item - order provides the emphasis, not the typeface. See `docs/standards/standard_formatting.md`, the section on emphasis in prose. Identifiers of deviations and findings such as O-1 or Z-1 remain plain text, because they serve for cross-referencing, not for emphasis.
