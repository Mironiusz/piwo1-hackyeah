# Cross-cutting decisions

## 2026-10-03 - Personal data in requests to outside services (plans/geocoding)

- What changed: no code yet. `plans/geocoding/GEOCODING_PLAN.md` D-3 and D-12 set how the address search keeps the searched text out of every log, and `plans/mvp/MVP_PLAN.md` D-3 carries them into the MVP.
- Why: the text a person searches for, like the current location, can reveal where they go and, for a hospital, information about health (`docs/product/specification.md`, M2); the shape of `plans/geocoding/` decided that it is never logged.
- Reusable pattern: a value that is personal data - the search text, the current location in a route request - travels from the browser to the server only in the body of a POST request, never in a URL, because the access log of the HTTP server and of the hosting records the URL. On the outgoing call to an outside service, the request logging of the HTTP client is switched off or kept above INFO, because httpx logs every request with its URL at INFO and INFO is the default log level of the project. The integration uses no client helper that puts the URL into an exception message, such as `raise_for_status` of httpx, and its own exceptions carry only the cause and the status code. A unit test captures the log at the DEBUG level for every outcome of the call and asserts that the personal value appears in no record, formatted tracebacks included.
- Risk / notes: the same trap applies to `plans/routing_engine/` if routing calls an outside service with the coordinates of the current location in a URL; that initiative has not decided it yet.

## 2026-10-03 - OpenStreetMap data in the repository and the identity of an OpenStreetMap element (plans/osm_data_source)

- What changed: no code yet. `plans/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-7, D-10 and D-16 decide how an OpenStreetMap element is identified and that no OpenStreetMap data enters the repository, and `plans/mvp/MVP_PLAN.md` D-4 carries them into the MVP.
- Why: the repository is public, and an extract or a fixture cut from real OpenStreetMap data would bring the attribution and share-alike obligations of the ODbL into it. A fact that disappears from a fresh copy and returns later has to find its votes again, and the specification forbids matching facts by distance (`docs/product/specification.md`, M3).
- Reusable pattern: a test of the import, of the tag mapping of `plans/osm_barrier_mapping/` or of the routing builds its own small elements with invented identifiers, tags and coordinates, and writes any `.osm` file it needs itself at run time; no downloaded file and no part of the copy is ever saved in the repository tree. An OpenStreetMap element is identified by its type - node, way or relation - together with its OpenStreetMap identifier, never by the identifier alone, because a node and a way can share a number, and never by geometry. An OpenStreetMap fact is that identity plus its fact type, and the unique constraint on it covers converted and outdated facts too, so a returning fact lands on its old row with `INSERT ... ON CONFLICT`.
- Risk / notes: when OpenStreetMap splits a way, only the part that keeps the old identifier keeps its facts; the other parts get new facts without votes, which can leave a converted user fact next to an OpenStreetMap fact of the same barrier, accepted for the MVP (D-7 there). An external routing engine has no such identity on its ways, so its route has to be matched to the ways of the copy first (D-17 there).

## 2026-10-03 - OpenStreetMap tag thresholds live in the specification and next to the rule (plans/osm_barrier_mapping)

- What changed: no code yet. `docs/product/specification.md` version 3, M6, states every tag value and threshold that makes a barrier or an amenity present, absent or unknown, and `plans/osm_barrier_mapping/OSM_BARRIER_MAPPING_PLAN.md` D-14 makes the same values constants of the third configuration layer in one module next to the code of the rule; `plans/mvp/MVP_PLAN.md` D-5 carries both into the MVP.
- Why: the thresholds are a product rule approved by the user, so the specification has to show them, while the import needs them as code; the user chose on 2026-10-03 to put the values into version 3 in full instead of keeping them out of the specification until the import person confirms them.
- Reusable pattern: a change of a threshold or a value list - 6 percent of incline, 0.9 m of width, 0.03 m of kerb height, the poor and good surfaces, the classes of ways for motor traffic - is three changes together: the constant next to the rule, a new version of the specification with its Decision provenance entry, and a fresh import, because the rule runs once per element at import time and the facts already stored keep the old result. The rule keeps four states for a barrier of a way, present, absent, absent by default and unknown; only absent, from an explicit tag value, contradicts a user report, and absent by default, which exists only for stairs on a way not tagged as steps, never does and does not count against the state no data. A test or a schema that folds the two absences into one breaks the contradiction rule of M2.
- Risk / notes: the import person of the team may still change the values before the demo is recorded; a change made only in code leaves the specification, which prevails, saying something else. The weight of a vote after its 30-day identifier is deleted is not in version 3; it lives in `plans/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-21 and the Q-10 caveat of the MVP plan.

## 2026-10-03 - What the local database setup creates and what only a revision creates (plans/local_database)

- What changed: no code yet. `plans/local_database/LOCAL_DATABASE_PLAN.md` D-1 - D-8 decide that every member who writes backend code runs PostgreSQL 18.6 with PostGIS 3.6.4 and the files of pgRouting 4.0.1 in a project image started by Docker Compose, and `plans/mvp/MVP_PLAN.md` D-7 carries the decision into the MVP; a work package of that plan builds the files and chooses their names.
- Why: `docs/standards/standard_database.md` makes every schema object and every grant a revision and fixes the locale for good when the database is created, and PostGIS, which is not a trusted extension, can only be created by a superuser, so the schema owner that applies the revisions is one.
- Reusable pattern: the init script of the image runs only when the data volume is empty, so a change of the script or of the names in the local environment files does nothing to an existing database, and recreating it, also after an applied revision was edited, means removing the named volume and starting the service again. The script creates only the database, with `TEMPLATE template0`, the builtin provider and `C.UTF-8`, and the two accounts; an extension, a table or a grant written there instead of in a revision is missing from the chain that the hosted demo applies too. A new extension the image already carries, pgRouting included, is one revision with `CREATE EXTENSION` applied by the schema owner, never a change of the image. The service account owns nothing, so a table whose revision forgets its grant passes the migration and fails only in the service, with a permission error; it also has no CREATE on the public schema of a database created on PostgreSQL 15 or newer, so it cannot create anything there either.
- Risk / notes: the image pins exact PGDG builds, because the version of an extension is recorded in the database when it is created; when the index drops those builds the image no longer builds, and the pins are raised for every member at once. On the hosted demo the account that applies revisions is a superuser on a server that also runs other services of its owner; this is handed to the task `DEPLOYMENT` of `plans/demo_environment/` and not decided yet.

## 2026-10-03 - Route graph in the memory of the backend (plans/routing_engine)

- What changed: no code yet. `plans/routing_engine/ROUTING_ENGINE_PLAN.md` D-1 - D-17 decide that routes are computed by a graph of the pedestrian network held in the memory of the one backend process and searched with scipy over numpy arrays, and `plans/mvp/MVP_PLAN.md` D-9 carries the decision into the MVP; the route work package of that plan builds it and chooses the module names with Q-11. The tag values of the pedestrian network, the 15 m within which a point report lies on a stretch, the 5 m of a kerb contradiction, the cover of a geozone and the unknown stairs on the stretch to the network are product rules in `docs/product/specification.md` version 5, M2 and M8.
- Why: nothing of a route request leaves the project (`docs/product/specification.md`, M2), so no routing service outside it can be called, and the copy of OpenStreetMap lives only in the database (`plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-14), so the graph is built from the database, never from a file.
- Reusable pattern: the graph is a cache of the copy in use. Every route request reads, in one read-only transaction, the instant of the copy in use together with the facts and geozones it needs, and when that instant differs from the instant the graph was built from, the graph is rebuilt from the same transaction under a lock inside the process, so ways, facts and the date of one route always come from one copy, and a new vote or report counts in the next route without a restart. The list of tag values that make the pedestrian network lives only next to the tag rule of the import, because the import stores only the ways of the network and the graph uses every stored way; a change of the list is a new version of the specification and a fresh import, like a threshold of the tag rule. The weight of a stretch is its length plus 1 000 000 per stretch with an avoided barrier, so one shortest path search gives both the route without barriers and, when none exists, the route with the fewest barriers. The ordered nodes of a way, which the graph needs, are `osm_way_node` of `plans/fact_schema/FACT_SCHEMA_PLAN.md` D-6. Tests build their own small networks with invented identifiers, tags and coordinates.
- Risk / notes: the time of reading the stored network from the database and building the graph is not measured, because no database with the copy existed; the first route after a start or a refresh may take longer than the 5 seconds a route across Kraków has, which is checked on the server after the first deployment. The weight counts stretches, not barrier facts, so a kerb point at a junction counts for every stretch of the route that ends there.
- Decisions: the risk note of the entry Personal data in requests to outside services, which named `plans/routing_engine/` as undecided, is settled by D-1 there: no route request goes to a service outside the project, so only the first half of that pattern applies to the route, the current location travelling from the browser only in the body of a POST request.
