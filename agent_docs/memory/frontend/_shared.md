# Frontend - shared decisions

## 2026-10-03 - Frontend technology and standard decided (plans/frontend_stack)

- What changed: no code yet. D-1: the frontend is a single-page application in TypeScript with React, built by Vite into static files. D-4: the map is drawn by MapLibre GL JS, used directly from one React component, without a wrapper library. D-5: the map of Kraków is one archive of vector tiles in the PMTiles format, cut out of the daily Protomaps build of OpenStreetMap data, served by the project and read by the browser in byte ranges. D-10: frontend code lives in `frontend/` in the repository root as one code unit. The rules and the four gates are in `docs/standards/standard_frontend.md`; the decisions with the facts behind them are in `plans/frontend_stack/FRONTEND_STACK_PLAN.md`.
- Why: D-1 because every piece of data comes through the programming interface, which a second client has to be able to use, so pages rendered by the backend are excluded and a framework with its own server adds a second server process for nothing the MVP needs. D-4 because the Leaflet renderer of the same tiles is in maintenance mode and its React wrapper carries a licence outside the usual open source ones. D-5 because the browser talks only to the server of the project, the public OpenStreetMap tiles may not be fetched ahead for the whole city, and generating tiles from the extract needs a tool chain the team has no hours for. D-10 because `docs/standards/standard_documentation.md` asks a project outside the Python profile to record its code unit, and the frontend person chose the whole application over feature directories as separate units.
- Reusable pattern: a file the browser needs is served by the project. Before a new asset is added - a font, a style, a script, a tile source, an image - it is checked for an outside address, and the asset is installed with npm or copied to the project instead of being loaded from another host.
- Risk / notes: `frontend/FRONTEND.md` and `frontend/FRONTEND_ALGORITHM.md` do not exist yet. The condition for creating them: the work package of `plans/mvp/` that builds the first screen applying a display rule of the specification creates the pair; the route result is the first such screen, with the rules of M7, M8 and M10. The four gates of the standard do not run until `plans/mvp/` writes the first frontend code and sets them up, so until then a frontend change is checked by review alone.

## 2026-10-04 - Map files of the base map: archive, fonts and generated style (plans/map_tiles)

- What changed: the browser asks for four things at fixed addresses - the tile archive at `/tiles/krakow.pmtiles`, the style at `/map/style-pl.json` or `/map/style-en.json`, and the fonts at `/map/fonts/{fontstack}/{range}.pbf`. The repository holds nine font files and the two style files under `frontend/public/map/`; the archive lies at `frontend/public/tiles/krakow.pmtiles`, which git ignores. The style files are generated by `frontend/scripts/generate_base_map_style.mjs` from the Protomaps style package 5.7.2 and committed. The record of the archive, the instructions and the list of colors are in `docs/setup/MAP_SETUP.md`.
- Why: Adrian chose committed fonts over a script, so that a fresh copy of the repository and the build on the server need no outside connection, and two generated style files over a style built in the browser. The style has no sprite, because the base map draws no points of interest, no arrows of one-way streets and no road shields; only three ranges of each font are committed, because the names of Kraków need no other script.
- Reusable pattern: a color or a layer of the base map is changed in the generator, never in a generated file; after the change run the generator and then `node frontend/scripts/generate_base_map_style.mjs --check`, which fails when a committed file differs from the generated one or when a style gains a sprite, an icon, a font outside the three, or an address outside the archive and the attribution. A new map asset is checked the same way before it is added: no address of a file the browser loads names an outside host.
- Risk / notes: the look of the style was never seen on a drawn map when it was committed; `plans/frontend_app/` checks the colors, the labels, the attribution and the requests of the browser when it builds the map. The addresses in the style start with a slash, and whether MapLibre GL JS resolves them against the page was not checked; if it does not, the map component resolves them when it loads a style. The generator needs the style package, which the frontend project has to list as a development dependency. The archive is handed to the backend persons as a file, and until the server serves it the hosted demo has no map.

## 2026-10-04 - The web frontend built: one map, a scene for each view, a mock of the service (plans/frontend_app)

- What changed: `frontend/` holds the application of `plans/frontend_app/FRONTEND_APP_PLAN.md`: every view of `docs/product/views.md` on the sixteen operations of `docs/product/api_contract.md`, the four gates with their `make` targets, and the pair `frontend/FRONTEND.md` and `frontend/FRONTEND_ALGORITHM.md`. One map lives in the layout of the map views; a view never touches MapLibre GL JS and describes a scene instead (`src/map/mapScene.ts`). During development the frontend runs on `frontend/mock-server/server.mjs`, behind the proxy of the development server.
- Why: Adrian chose paths over addresses after a hash sign, a mock that is a server of its own over mock data inside the frontend, React alone for the state, Tailwind CSS for the styles, i18next for the texts, and trust in the types over checks of every answer (D-3 - D-8 of the plan). The map is one component because the map library keeps state a view must not rebuild.
- Reusable pattern: a new map view builds its scene with `useMemo` from `EMPTY_MAP_SCENE` and hands it over with `useMapScene`; it reads where the map rests from `useMap()` and never asks for data while the map moves. A new text goes into both dictionaries and into `docs/product/interface_texts.md` in the same change. The linter runs every `jsx-a11y` rule as an error and the rules of the React compiler: a status message is the element `output` or the part `Note` with `announce`, state is not set synchronously in an effect, and a prop is not changed. A file under `src/state/` that exports a provider with its hook reloads the whole page in development when it changes, which drops a planned route.
- Risk / notes: every check was made on the mock; no backend ran during the build, so step 12 of the plan, the run against the service, is open, and a difference between the contract and the service shows as a wrong screen or as the text that something went wrong. The server of the demo has to answer unknown paths with the page and to serve `/tiles/krakow.pmtiles` with byte ranges. A server that answers the path of the archive with the page, or without byte ranges, gives the message that the map could not be loaded in place of the map: the map component treats an error of the base map source that names no tile as a failed map, and passes over an error of one tile or of a font. The check with a screen reader on a phone was not made; what works and what does not is in `docs/product/accessibility_status.md`. The texts added during the build were not approved one by one. Node.js 22.22.0 or newer is asked for by `react-router` 8.4.0; the build ran on 22.20.0 with a warning.
