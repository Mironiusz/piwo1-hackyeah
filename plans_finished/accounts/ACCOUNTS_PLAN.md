D-1. The accounts code is written against the interfaces the skeleton plan declares (F-12) and starts when `config/`, `common_time.py`, `config/logging.py`, `api/app.py`, `api/errors.py` and `data/engine.py` exist in the working tree. A delivered interface whose name or signature differs from F-12 is used as delivered and the difference is recorded in `ACCOUNTS_REVIEW.md`; no stand-in of a missing skeleton part is written. Decided by Kuba on 2026-10-04 in this phase, against waiting for Marek to add the missing seams and against accounts building its own foundation.

D-2. The two generic seams F-13 finds missing are added by this initiative as small additions to the skeleton files, agreed with Marek before they are written: `data/engine.py` gains `fetch_api_engine() -> Engine`, the one engine of the API process built by `build_engine(API_STATEMENT_TIMEOUT_MS)` with the 5000 ms of F-12 and kept by `functools.cache`, whose docstring states that the configuration it is built from does not change during the life of the process; and `build_app()` in `api/app.py` gains one call, `apply_account_routes(app)`. When Marek has delivered an equivalent seam first, it is used instead and nothing is added. Decided by Kuba on 2026-10-04 in this phase. The installation of `accessibility_db` into the backend and the clash of F-13 between `database/` with `DATABASE_URL` and `db/` with the `DB_` entries stay with Marek and Kuba as owners of those parts and are not decided here.

D-3. A pseudonym is accepted when, after removing the character U+0020 at both ends, it has 3 to 30 code points, each one of the 26 Latin letters in both cases, the nine Polish letters `ąćęłńóśźż` in both cases, the digits `0` - `9`, `_` or `-`; this is exactly the set the HarmonyOS client checks (F-14). Decided by Kuba on 2026-10-04 in this phase, against any Unicode letter and against any Unicode letter and decimal digit. `docs/product/api_contract.md`, section create_account, names the set explicitly in S-1, with the confirmation of Adrian pending as for the earlier pseudonym correction. Agent decision at C:40, without asking: only U+0020 is trimmed, because the contract and M9 say "spaces", and no Unicode normalization is applied, because the contract keeps the pseudonym "as it is after the trim", so a decomposed `ó` is refused as a character outside the set.

D-4. A password is checked only for 5 to 128 code points at registration and is never trimmed. It is hashed with argon2-cffi 25.1.0 by `PasswordHasher(time_cost=2, memory_cost=19456, parallelism=1)`, exactly the floor of F-7, and stored in the encoded form, so the parameters can be raised later without a schema change. Agent decision at C:40, without asking: the floor keeps one login at about 32 ms and 19 MiB (F-15) on the shared server of the demo, and the library is the reference binding of Argon2 for Python.

D-5. `log_in` validates only the shape, two strings. A trimmed pseudonym that matches no account, a pseudonym or password outside its registration rules, and a wrong password all end in `invalid_credentials`. A pseudonym with no account is verified against a hash of a random value built once per process, so its duration matches a wrong password (FR-3 of the PRD). Agent decision at C:40, without asking: the contract lists only `invalid_credentials` for `log_in` and sets no input rules for it.

D-6. A session token is `<payload>.<signature>`, both parts base64url without padding: the payload is the compact JSON `{"a": <account id>, "e": <expiry as integer milliseconds since the UTC epoch>}`, the signature HMAC-SHA256 of the payload part under the required secret entry `SESSION_SIGNING_KEY` of at least 32 characters. The expiry is the instant of the request from `fetch_utc_now()` plus 24 hours; a token is valid while the current instant is earlier than its expiry; signatures are compared with `hmac.compare_digest`; a token that does not split into two parts, does not decode, is not a JSON object with exactly those two integer keys, carries a boolean, zero or negative identifier or fails the signature is malformed. Each response gives a new token and earlier tokens stay valid until their own expiry, which the contract allows by having the client replace its token. A deleted account makes all its tokens fail, and the identity always column never gives its identifier to a new account, so a token of the old account never resolves to the account that took its pseudonym. Agent decision at C:40, without asking: the standard library covers signing, so no library is added, and the token is opaque to the clients, so its form binds no other initiative.

D-7. `service/actors.py` is the one place that turns a request into an actor and checks the role (F-19). `resolve_request_actor(authorization: str | None, now: datetime) -> SessionResolution` returns no actor and no token for an absent header; a present header must be the scheme `Bearer`, compared without regard to letter case, one space and a token without spaces, and anything else, a malformed or expired token or an identifier with no account raises `SessionExpired`; otherwise it reads the account by its identifier on every request, so its existence and its role are current, and returns an `AccountActor` with a renewed token. `resolve_account_actor(resolution: SessionResolution) -> AccountActor` raises `AuthenticationRequired` without an actor; `resolve_moderator_actor(resolution: SessionResolution) -> AccountActor` raises `AuthenticationRequired` without an actor and `ModeratorRoleRequired` for an account without the role. The consumer contract for `community_facts`: an operation that admits a person without an account depends on `fetch_request_session`, one that needs an account on `fetch_account_actor`, a moderator one on `fetch_moderator_actor`, and the four operations without a token declare none of them. An account deleted between the resolution and the write of a consumer makes that write fail on `fk_vote_account`, which the consumer answers with `session_expired`. Agent decision at C:40, without asking: reading the account per request is what the current role and the deleted account require, and the contract of the consumers follows from F-3.

D-8. The renewed token reaches the client through the request state: `fetch_request_session` stores it as `request.state.session_token`, and `SessionTokenMiddleware`, a pure ASGI middleware in `api/sessions.py`, adds `Session-Token` on `http.response.start` when the state holds one (F-17). A request with a valid token therefore gets the renewed token on success and on a handled refusal such as `moderator_role_required` or `invalid_request`; `delete_own_account` clears the state to answer `204` without the header; a response to an operation without a token never carries one. A failure that ends in `internal_error` outside the handlers carries no renewed token, and the token the client keeps stays valid until its own expiry. Agent decision at C:40, without asking: a dependency alone cannot reach responses built by exception handlers.

D-9. `data/accounts.py` reads and writes only through `fetch_api_engine()` connections passed in by the service, with SQLAlchemy Core statements on the columns of `accessibility_db.tables.Account` and the typed `StoredAccount`. The insert is `ON CONFLICT (lower(pseudonym)) DO NOTHING RETURNING id` (F-16), so the unique index decides between two concurrent registrations and no returned row means `pseudonym_taken`; the lookup by pseudonym compares `lower(pseudonym)` with `lower(:pseudonym)`, the expression of the index, so Polish letter case follows the database (F-18), not Python; `created_at` is `build_offset_instant(fetch_business_now())`. Each service operation is one transaction opened by the service with `fetch_api_engine().begin()`, and the password is hashed before the transaction opens. Agent decision at C:40, without asking.

D-10. Deleting an account is one `DELETE` of its row in one transaction; `FK_vote_account` detaches its votes in the same statement, so a failure leaves nothing partly removed (F-8). A deletion that removes no row, because another request deleted the account first, raises `SessionExpired`. While a vote insert of a consumer holds its key-share lock on the account row, the deletion waits for it (F-23); a vote committed first is detached, and a vote insert that starts after the deletion committed fails on `fk_vote_account`. Agent decision at C:40, without asking.

D-11. The moderator role is assigned and removed by hand, as M11 says, with one `UPDATE account SET is_moderator = ... WHERE lower(pseudonym) = lower(...)`, documented in a section Moderator role of `db/README.md`, the description of the database Kuba owns; no operation or command is added. Running it on the hosted demo is a human step. Agent decision at C:40, without asking.

D-12. Tests follow F-20: the rules, passwords and tokens as scenario tests in `tests/service/`, the actor matrix in `tests/service/` with the data layer replaced, the contract of the four operations and of the session header as integration tests in `tests/api/` with the service replaced, and the database code as critical tests in `tests/data/` and `tests/service/` against the local database of `db/compose.yaml` after its revision chain. Data-layer critical tests run inside a rolled-back transaction; tests that commit register their pseudonyms in the cleanup fixture `stored_account_cleanup` appended to `tests/conftest.py`, which deletes those accounts as the service account; votes and facts, which the service account cannot delete (F-8), are written only inside rolled-back transactions. Agent decision at C:40, without asking.

D-13. The root `pyproject.toml` pins `argon2-cffi==25.1.0` in `project.dependencies` and lists `accessibility_db` in `[tool.deptry]` `known_first_party`, because the package is installed from `db/` of this repository; the new modules join the paths of mypy, vulture and the Bandit passes of the `makefile` that S-1 of the skeleton creates. ## Risks

- R-1. The skeleton has no code and its plan is not closed (F-11, F-12), so accounts can stand ready on paper while 2.3 of `FINAL_CHECKLIST.md` cannot be verified; S-1 and S-3 are the only steps without that wait.
- R-2. A skeleton interface may land unlike F-12; D-1 uses it as delivered, which can move names of S-2 - S-6.
- R-3. The two environments of F-13 can leave the backend unable to reach the database of `db/` until Marek and Kuba settle them.
- R-4. Anyone holding `SESSION_SIGNING_KEY` can forge a session of any account; it lives only in environment files, and changing it ends every session.
- R-5. Argon2 takes 19 MiB per login; 40 simultaneous logins in the thread pool of the API take about 760 MiB of the 16 GB of the server.
- R-6. A response of `internal_error` carries no renewed token (D-8), so a client that sees only such failures keeps its older token until its expiry.
- R-7. The web client of Adrian may check another character set than D-3 until Adrian confirms S-1.
