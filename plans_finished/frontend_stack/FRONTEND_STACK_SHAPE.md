## Scenarios: input, flow, expected state after the run

1. Opening the app at the public link. Input: a person opens the address of the demo in a phone browser. Flow: the browser loads the page, its scripts, its fonts and the map tiles of the visible area, all from the server of the project. State after: the map of Kraków is on the screen with the OpenStreetMap attribution; the browser made no request to any other host, so no service outside the project saw the IP address of the person or the area they look at.

3. A frontend change reaches review. Input: a merge request with frontend code that contains a type error, a forbidden character or an image without a text alternative. 6. Holding frontend code to the standards. Input: the chosen technology and the standards of the repository, which cover only Python code. ## Challenging own assumptions

- Is the frontend only a technology choice? No: the repository has no standards for non-Python code, so the choice also decides which gates check it, and that changes the standards map. Decided on 2026-10-03: the core standards plus one short frontend standard (Domain rules).
- Does a decision without any frontend code leave the open registry entry half answered? No: the entry asks this initiative to record how frontend code is held to the standards, and the frontend standard in the standards map is that record. The gates it names cannot run before frontend code exists, so they are set up with that code in `plans/mvp/`.
- Does the HarmonyOS port constrain the choice? Yes, but not through the frontend code: the port, if it is built, is a second client of the same programming interface, not an application embedding the web app (Domain rules). The web frontend does not have to run inside a HarmonyOS web view; what it shares with the port is the programming interface, which is planned for two clients from the start. This agrees with the dependency of `plans/mvp/MVP_PRD.md` that the solution must not prevent a second client from using the same data and rules: the route response already carries the segment states and the three groups of the list (`plans/api_contract/API_CONTRACT_SHAPE.md`, Functional requirements 2), so the data and the rules stay behind the programming interface.
- Can two interviews of one initiative both stand? Only where they agree. On 2026-10-03 this interview was closed twice within minutes, in two sessions. They agreed on the scope and differed on the second client of the programming interface; the frontend person, who owns the decision, accepted the answer of the parallel interview. The rule about services outside the project and the choice of the short frontend standard come from the interview of the frontend person alone: the parallel interview had left the tile service to the later choice, and the named standards and gates to the frontend person.
- Is the risk of the map tiles only a note for phase B? No: whether the browser of the person may contact a service outside the project at all is a rule about personal data, of the same kind as the one `plans_finished/geocoding/` decided for the search text, and the requirements of the PRD differ with the answer. Fonts and scripts loaded from an outside host reveal the IP address in the same way, so the question covered them too. Decided on 2026-10-03: the browser talks only to the server of the project (Domain rules).

## Notes on data, performance and security

- The profile and the current location never reach the account (`docs/product/specification.md`, M1 and M2); the frontend is where the profile lives.
- The map display does not rely on a tile service contacted by the browser (Domain rules). The source the project takes its tiles from still has terms, limits and a licence, and they are checked together with the choice in phase B of `plan-prd`.
- Nothing the browser loads reaches a service outside the project, so the privacy information (`plans/mvp/MVP_PRD.md` FR-20) gets no new item from the map display or from the fonts.
- Because the project serves the tiles itself, the live demo does not depend on the public OpenStreetMap tile service, which limits heavy use by IP address, while the whole venue shares a few addresses.
- Volume, an estimate by the agent: the public link is used by the team and the jury, at most a few dozen people, and one map view on a phone needs about twenty tiles, so the server of the project answers a few thousand tile requests over the demo, each of them a read of a stored file.
- The rule that the project serves the map tiles itself is a new input for `plans/demo_environment/DEMO_ENVIRONMENT_PLAN.md` Q-1, which asks how much free disk space the server has: the hosting has to store and serve the tiles of Kraków next to the files of the frontend.
- The base map and the data behind the routes may come from OpenStreetMap copies of different dates. FR-9 shows the date of the copy the routes use; whether the base map needs a date of its own is a question for phase B of `plan-prd`.
