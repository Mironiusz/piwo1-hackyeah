The only new files are the short frontend standard and the first memory entry of the frontend code unit.

## Decisions

D-1. Technology. The frontend is a single-page application written in TypeScript with React, built by Vite into static files. `plans/mvp/` creates it from the official Vite template for React with TypeScript, which fixes the versions: React 19.3, Vite 8.3 and TypeScript 6.0 (F-4), all of which run on the Node.js of the frontend person (F-3, F-5). Decided by the frontend person on 2026-10-03, against three variants: pages rendered by the backend, which a second client cannot use and which the shape forbids (PRD FR-8); a React framework with its own server, which adds a second server process to the hosting for nothing the MVP needs, because every piece of data comes through the programming interface; and another single-page library, which no requirement of the PRD favors over the one the frontend person builds in.

D-2. TypeScript stays on the version of the template, 6.0, not on the newest 7.0 (F-8). Agent decision at C:40, without asking: the template is the combination its authors keep working together, and the deadline leaves no time to find out what a version one major step ahead breaks.

D-3. Static files, one host. Nothing is rendered on the server. The page, its scripts and styles, the fonts, the map tiles, the map fonts and sprites and the programming interface are all served from one host, so the frontend calls the interface on its own origin and the browser makes requests to exactly one host (PRD FR-6, AC-5). No package of the frontend is loaded from a content delivery network at run time: everything is installed with npm and built into the static files. Agent decision at C:40, without asking: it follows from D-1 and from FR-6.

D-4. Map display. The map is drawn by MapLibre GL JS (F-9), used directly from one React component, without a wrapper library. Decided by the frontend person on 2026-10-03, against Leaflet with the Leaflet renderer of the same tiles, which is in maintenance mode and whose React wrapper carries a licence outside the usual open source ones (F-18). The lack of a wrapper is an agent decision at C:40, without asking: the app has one map, and a wrapper would add a dependency between React and the map that no requirement asks for.

D-5. Map tiles. The map of Kraków is one archive of vector tiles in the PMTiles format, cut out of the daily Protomaps build of OpenStreetMap data (F-13) for the bounding box of the administrative boundary of Kraków (F-15), zoom 0 to 15, with the command `pmtiles extract https://build.protomaps.com/<YYYYMMDD>.pmtiles krakow.pmtiles --bbox=19.7922355,49.9676668,20.2173455,50.1261338` (F-16), where the build is the newest one on the day the file is produced. Measured on the build of 2026-10-03 it takes 34.8 MB (F-14). The archive lies on the server of the project next to the frontend files, and the browser reads it in byte ranges through the protocol of the pmtiles library (F-10). During the demo neither the browser nor the server talks to Protomaps or to OpenStreetMap. The archive is not committed to the repository: it is a binary file of tens of megabytes that changes with every build. Decided by the frontend person on 2026-10-03 after consulting the external API person, who agreed, against two variants: the public OpenStreetMap tiles passed through the server of the project, which keeps the outside dependency and cannot be filled ahead for the whole city under the policy of that service (F-17, PRD AC-6); and tiles generated by the team from the OpenStreetMap extract, which needs a separate tool chain and extra data sets in hours the team does not have.

D-6. Map style and its assets. The style of the base map comes from the Protomaps style package (F-11), with the colors set to the design direction of the frontend person and the labels in the language of the interface. The fonts and sprites the style needs are copies served by the project, 11.2 MB in 776 files (F-12); the style never points at `protomaps.github.io`. Whether these copies are committed or fetched by a script is decided by the work package of `plans/mvp/` that sets up the map, which is where the PRD puts the setup. Agent decision at C:40, without asking: the package and the assets are the ones the documentation of the tiles names, and serving the copies follows from FR-6.

D-7. Attribution and dates. The attribution control of the map is always open, never collapsed, and shows the OpenStreetMap attribution stored in the archive (F-13, F-19; PRD FR-7). The interface shows no separate date for the base map: the date of `plans/mvp/MVP_PRD.md` FR-9 stays the date of the copy behind the routes, and the key of the build the archive was cut from is written down next to the file when it is produced. Agent decision at C:40, without asking: a second date on the screen would present the base map as a source of facts, which it is not.

D-8. How the chosen technology meets AC-1 - AC-7 of the PRD. Agent decision at C:40, without asking: each line names the facts it rests on, and AC-1 is confirmed by a run only when `plans/mvp/` builds the first map.

- AC-1. Everything the map shows is also in the list for the route, built from the same response. The markers of barriers and amenities are buttons placed on the map as page elements (F-19), each with a text name, so the keyboard reaches them in the order of the page. The map pans with the arrow keys and zooms with the plus and minus keys (F-19), and it is one stop in the order of focus, left with the Tab key. The point of a geozone is given by the address search of `plans_finished/geocoding/`, or by moving the map under a fixed center mark with the arrow keys and confirming with a button; the radius and the barrier type are native lists. On a device without WebGL (F-9) the map is replaced by a plain message, and the list carries everything.
- AC-2. Each of the four segment states is its own line layer with a color and a dash pattern (F-19), drawn from the segments of the response; the legend is page content, outside the map.
- AC-3. The texts live in the frontend, one dictionary per language, and the default comes from the language of the browser. The route result stays in the state of the page, so the switch redraws the texts without a new request for a route. This needs everything from a closed list - types, statuses, sources, segment states, missing attributes, kinds of messages - to arrive as a code, which is handed to `plans_finished/api_contract/` in step 9.
- AC-4. The profile is kept in the local storage of the browser and sent only inside the request for a route.
- AC-5. D-3.
- AC-6. D-5 and D-6.
- AC-7. The frontend draws what the response carries and applies no product rule of its own; the frontend standard forbids such a rule in frontend code (D-11).

D-9. Typefaces of the interface. The two typefaces of the design direction are installed as npm packages and built into the static files (F-20), never loaded from an outside host. Agent decision at C:40, without asking: it follows from FR-6.

D-10. Code unit and directory. Frontend code lives in `frontend/` in the repository root, with its own `package.json` and lock file, and the whole frontend application is one code unit. Decided by the frontend person on 2026-10-03, against the directory name `web/` and against feature directories as separate units. Its pair of documents, `frontend/FRONTEND.md` and `frontend/FRONTEND_ALGORITHM.md`, is created by the work package of `plans/mvp/` that builds the first screen applying a display rule of the specification; until then the condition stands in `agent_docs/memory/frontend/_shared.md` (F-25, F-33). The place of the pair next to the code and that condition are agent decisions at C:40, without asking: the standard names the files but not their directory, and the route result is the first screen that applies the rules of M7, M8 and M10.

D-11. The frontend standard. A new file `docs/standards/standard_frontend.md`, group frontend profile, status ready, with the core sections every standard has - Why this document exists, Scope and boundaries, Deviation rule, Checklist - and these sections of its own:

- Technology: D-1 - D-7 and D-9, each as one short paragraph, with a pointer to this plan for the rejected variants. A new run time dependency is added only with its reason stated in the merge request.
- Code unit and documentation: D-10.
- Rules that come from the product. The browser talks only to the server of the project: no address of another host stands in a request, a style, a font or a script of the frontend. Frontend code holds no product rule: the segment states, the groups of the list, the status of a fact and the calendar day of a date are shown as received. The map is never the only carrier of a piece of information and never holds the keyboard focus without a way out. Every interactive element is reachable with the keyboard and has a text name. Every text of the interface exists in both languages.
- Language. Code, names and documentation comments are in English. The Polish texts of the interface are product content required by the specification and stand only in the Polish dictionary.
- Comments. No line comments. A component, a hook or a function that needs explanation gets a documentation comment in the block form above it, in plain language.
- Formatting. prettier with the configuration of the repository, the same tool and the same file as for markdown (F-22): a width of 200 characters and double quotation marks.
- Tests of logic. Logic outside components - the state of the page, the mapping of codes to texts, the formatting of distances - has unit tests, and no test uses the network.
- Gates. Four automatic gates, the first three run from `frontend/`: the type check `npx tsc -b`; the lint `npx oxlint`, with the rule groups `react`, `jsx-a11y` and `typescript` turned on in `frontend/.oxlintrc.json` and every finding of `jsx-a11y` an error; the tests `npx vitest run`; and `pytest tests/architecture/test_prose_style.py`, extended to the files `.ts`, `.tsx`, `.css`, `.html` and `.json` under `frontend/`. The gates, their `make` targets and the extension of the test are set up by the work package of `plans/mvp/` that writes the first frontend code; until then the standard is checked by review alone.
- What this standard does not cover: the names of frontend files and the split of the frontend into directories.

The kind of standard - the workflow core plus one short standard with four gates - was decided by the frontend person in the shape. The tools are agent decisions at C:40, without asking: the type check and the linter are those of the template (F-4), oxlint carries the accessibility rules (F-6) while the ESLint route does not fit the current versions (F-7), Vitest fits the Vite of the template (F-5), and prettier is already the formatter of the repository (F-22). The exception for the Polish texts is an agent decision at C:40, without asking: the specification requires a Polish interface and prevails over the language rule of `CLAUDE.md` (F-26).

D-12. The standards map and the review map. `docs/standards/README.md` gets a third group, the frontend profile, with one standard, its row in the table, its row in the table of task types, and two debts; `docs/standards/standard_review.md` gets its row in the tool map; `docs/standards/standard_documentation.md` records the code unit. The Python profile is not touched. Agent decision at C:40, without asking: it follows from PRD FR-10 and from the way these documents already record a standard.

D-13. Inputs to the sibling initiatives. To `plans_finished/demo_environment/`: the frontend is static files; the hosting stores about 50 MB for it - the tile archive of 34.8 MB (F-14), the map fonts and sprites of 11.2 MB (F-12), and the built page with its scripts and typefaces, a few megabytes, not measured because no code exists; the server answers byte range requests for the tile archive (F-10); the page, the programming interface and the tiles are on one host (D-3). To `plans_finished/api_contract/`, as inputs of the first consumer that leave the contract with its owner: two clients from the start (shape, Domain rules); a code for everything from a closed list (D-8, AC-3); no product rule and no time zone conversion in the client, so the segment states, the groups of the list and the calendar day of every fact arrive as the specification defines them (F-34); one host for the page and the interface (D-3). Agent decision at C:40, without asking: each input follows from a requirement of the PRD.

## Risks

- AC-1 - AC-7 of the PRD are settled by a run only when `plans/mvp/` builds the frontend. The first map is the earliest run of the keyboard path through the map and of a device without WebGL (D-8).
- Whether the server of the project answers byte range requests for the tile archive is not known before the first deployment. One manual check follows it: the map shows a district of Kraków at the public link. A server that does not answer ranges shows no map, and the list for the route is then the only carrier.
- The free disk space of the server is not known yet (`plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md` Q-1). The frontend needs about 50 MB of it (D-13). If the server cannot hold it, the rule of the shape that the project serves its own tiles goes back to the frontend person; it is not replaced silently by an outside tile service.
- Producing the tile archive needs the pmtiles command line tool, which is a download, and a read of about 35 MB from the Protomaps build. From the address the venue shares, outside services already refuse requests (F-32), so the archive is produced early and its file kept by the person who produced it.
- `plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md`, a plan in progress of another owner, still says in its F-8 and Q-1 that the frontend is undecided. This plan does not edit it; its owner updates it from the input of step 10.
- The entry HarmonyOS port and the Huawei submission of `docs/standards/decision_registry.md` still lists the variant of an application embedding the web app, which the shape of this initiative excludes. The PRD does not cover that entry; whoever takes the go decision on the port updates it.
- `CLAUDE.md` and `AGENTS.md` name two exceptions to the rule that the repository is written in English. The Polish texts of the interface are a third one, grounded in the specification and recorded only in the frontend standard (D-11). Adding it to the two core files changes the rules of the repository and is left to their owner.
- Once the gate of forbidden characters covers `frontend/`, the texts of the interface fall under it: no ellipsis, middle dot, arrow, multiplication sign, typographic dash or curly quotation mark in the Polish and English texts, and icons are drawn as graphics. The approved mock already complies (F-31).
- The architecture tests of this branch already fail on the files of an installed design skill, outside this initiative. A full run therefore hides new violations, and the Definition of Done checks the files of this change by name.
- oxlint does not use type information, so rules that need it are not checked by the lint; the type check is a separate gate. TypeScript stays one major version behind the newest (D-2).
- The base map and the data behind the routes come from OpenStreetMap copies of different dates, and the interface shows only the date of the latter (D-7). A person may see on the map a path the route does not know, or the other way round.
