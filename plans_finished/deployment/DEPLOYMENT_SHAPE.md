## Scenarios: input, flow, expected state after the run

1. First deployment. Input: the skeleton of the app is on `dev`, the server of the user has Docker with Docker Compose, and the user has an environment file filled from the versioned templates, outside the repository. Flow: the user runs the one command of the written instructions; the reverse proxy, the backend as exactly one process, the PostgreSQL instance of the demo and the Valhalla routing service start; the database schema is brought to the current revision; the user then runs the loading program by hand. State after: the app opens at the public HTTP link on a phone, shows the map from the tile archive of the project, plans a walking route from an address or a point on the map, and one address search returns a list (`plans_finished/geocoding/GEOCODING_PLAN.md` D-16); the repository holds no address, host, login or secret of the server.
2. A fix during the night. Input: the demo has been running for an hour, with the loaded data and a few test reports and votes of the team. Flow: a fix is merged and the user runs the same one command again. State after: the app runs the new code, and every report, vote and account from before the restart is still there; the data is loaded again only if the user runs the loading program on purpose.
3. The address search is refused from the server. Input: the public Nominatim instance blocks or limits the address of the server. Flow: a user searches an address. State after: the app shows the search unavailable message of `plans_finished/geocoding/GEOCODING_PRD.md` FR-5, the start and the destination can still be picked on the map, and the team knows it from the check of scenario 1 before the submission, not from the jury.
4. A phone asks for the current location. Input: a juror opens the public HTTP link on a phone and picks the current location as the start. Flow: the browser refuses the location to a page without a secure connection. State after: no location is used and none is guessed; the start is picked from an address or the map, as accepted in section Out of scope.
5. The agent checks the demo. Input: a request to look into an error during the night. Flow: the agent reads the logs of the services of the demo. State after: nothing outside the services, the database and the logs of the demo was read or changed; anything beyond reading the logs was done only on an explicit request of the user (`CLAUDE.md`, section Target environment).
6. The demo is deleted on 4 October 2026, after the results. Input: the running demo with its data. Flow: the owner of the repository, with the user as the owner of the server, removes the containers of the demo and its PostgreSQL instance together with its data. State after: no service, database or stored data of the demo is left on the server, and the rest of the server is untouched.
