## Problem

Every backend initiative of `MVP.md` that reads or writes the OpenStreetMap copy, facts, votes or accounts - `osm_import`, `accounts`, `community_facts`, `route_planning` and `sample_data` - waits for the first schema revision, and no revision exists. The critical path of the MVP runs through `backend_skeleton` and this initiative (`MVP.md`, section Order and critical path), with the Kraków submission due at 11:00 on 4 October 2026.

The target schema `docs/product/schema.md` has run only in its parts without PostGIS, on PostgreSQL 15. Its `geography` columns, their GiST indexes, the constraints of the vote limit and the grants of the service account run for the first time in this revision, on PostgreSQL 18, and an error found there needs a new version of the specification approved by the user before the revision can match it (`plans_finished/mvp/MVP_PLAN.md`, section Risks).

The task of this initiative is the minimal model of the database - the tables - as one shared piece of code that the import and the backend both import, together with the first revision that creates the whole target schema in the database. It builds no code of the rules: the derivation of a status from the votes, the reconciliation of a fresh OpenStreetMap copy, the deletion of an account, hiding, the duplicate check and the readings stay with the initiatives that build them. Decided by Kuba on 2026-10-04 in this interview (question 2), against the literal reading of D-11 of `plans_finished/mvp/MVP_PLAN.md`, under which this initiative ran every scenario of AC-1 - AC-12 of `plans_finished/fact_schema/FACT_SCHEMA_PRD.md` with the code of the rules they need, and against building the derivation of a status here; "only the tables" means the model, while the revision still creates the domains, constraints, indexes and grants of the target schema, against a revision of bare tables without them and against a model without a revision.

## Challenging own assumptions

- Does the idempotency key hold the revision back? No: `plans_finished/schema_revision/` was carried out and version 12 approved on 2026-10-04, before `backend_skeleton` was finished. Changed on 2026-10-04 at the merge of `dev` `2dcccce`: before it the answer was "only if that task is not carried out before the skeleton is finished".
- Does the vote limit by calendar day leave the frontend unchanged? No longer: the code and the field of `vote_too_soon` keep their shape, but version 11 has the frontend show the own vote and keep on the device the moment the next vote is possible, computed today as a day after the vote, and the texts say "after a day has passed" and show that moment with an hour that would always be midnight. The version of requirement 7 rewrites those documents, so that `frontend_app` is not built on the old window (question 8).
- Does the length check bind more than the stored data? Yes: it fixes that the hash `community_facts` computes is 32 bytes long, which reverses `plans_finished/fact_schema/FACT_SCHEMA_PLAN.md` D-8, where the computation was left to the voting work package without a check. It does not fix what is hashed or with which secret; any function with a 32-byte output, SHA-256 or HMAC-SHA-256 among them, meets it (question 7).
- Can the street name of the decision registry change the first revision? Only if Marek decides it before the revision is written, and only by a new version of the specification; decided later, it adds the name of a way to `osm_way` in a second revision, which the linear chain of `docs/standards/standard_database.md` allows.
- Does the loop cut by U-1 of `plans_finished/dependency_check/` come back? No, as long as the critical tests of D-8 that check the first revision stay here and `backend_skeleton` does not deliver them (`MVP.md`, section Order and critical path). Changed on 2026-10-04 by Kuba during the implementation (questions 10 - 13): every critical test of D-8 is now delivered here, so `backend_skeleton` delivers none of them.
- Did I read "only the tables" right? Not at first: I asked about the code of the rules, and Kuba answered with the task as Kuba sees it, a minimal model as a library for the import and the backend. The follow-up with variants showed that "only the tables" limits the shared model, not the revision, which still creates every constraint the specification and `docs/standards/standard_database.md` require (Problem).
- Does every scenario of AC-1 - AC-12 that left this initiative still have an executor? Yes, each goes to the initiative of `MVP.md` that builds the code it runs (Out of scope). Their seeds do not name these scenarios, so until requirement 8 is written into `MVP.md` they are found only in this shape; that is why requirement 9 puts the documents first.
- Does the vote limit by calendar day change the result of a scenario the acceptance criteria quote? No: in scenarios 1 - 3 of `plans_finished/fact_schema/FACT_SCHEMA_SHAPE.md` and scenario 3 of `plans_finished/mvp/MVP_SHAPE.md` every repeated vote of one person falls on the same calendar day as the vote before it or days later, never across midnight within a day, so each is refused or accepted as before.
- What does the calendar day give up? A person can vote twice within minutes across midnight, and a vote repeated because its response was lost is accepted as a second vote when the retry crosses midnight. ## Notes on data, performance and security

- The hash of a vote without an account is pseudonymized personal data and is kept until the demo is deleted (`docs/product/specification.md`, M9 and section Personal data). The vote limit by calendar day uses it as part of a uniqueness and keeps nothing more about the person; the tests use made-up hashes, never one computed from a real address. The length check refuses a hash of another length, so a hash computed by a different function never enters that uniqueness unnoticed; it says nothing about how strong the hash is, which stays with `community_facts`.
- Time: every instant stays a pair of `timestamptz(3)` and its offset (`docs/standards/standard_time.md`), and the calendar day of a vote is the day of its instant in Europe/Warsaw, whatever offset the pair carries. A critical test proves the round trip of an offset (`plans_finished/fact_schema/FACT_SCHEMA_PLAN.md` D-21).
- Idempotency: the stored data refuses a second fact with an idempotency key already saved and a second vote of one person on one fact on the same calendar day; a vote retried across midnight is the one known repetition it accepts (Challenging own assumptions).
- Rights: the service account gets exactly the rights of `docs/product/schema.md` and no right to create, alter or drop; a table whose grant is forgotten passes the migration and fails only in the service, so the rights are proven by critical tests (`agent_docs/memory/_cross_cutting.md`, entry What the local database setup creates and what only a revision creates).
- Volume: the revision reads nothing on a list path; the votes of the demo are few, and the facts and ways of the copy of Kraków are written by `osm_import`, not here.
- No address, account name or password of any environment enters the repository; the name of the service account in the grants is supplied when the revision is applied (`docs/standards/standard_config.md`, section Secrets).
