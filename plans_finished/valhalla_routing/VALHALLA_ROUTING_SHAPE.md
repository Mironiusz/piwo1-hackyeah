# Shape: Valhalla as the routing engine and public transport routes from static GTFS

Document state: 2026-10-03, interview closed
Regulator: C:40

## Problem

The routing engine decided in `plans_finished/routing_engine/` (D-1 there, recorded as D-9 of `plans_finished/mvp/MVP_PLAN.md`) is an own graph of the pedestrian network in the memory of the backend process, searched with scipy. The user judges that writing an own router is the wrong call, all the more so because routes are also meant to use public transport from static GTFS (seed, message 1). No product code exists yet, so the change costs only documents.

## Recipient and trigger

The person planning a route in the app (M2 of `docs/product/specification.md`), through the backend, which hands the route request to the routing engine. Trigger: a route request.

## Current state

- The specification, version 7, puts public transport routes out of scope: "Turn-by-turn navigation and public transport routes." (`docs/product/specification.md`, section Out of scope).
- M2 says nothing of a route request leaves the project and it is never sent to a routing service outside the project. A self-hosted engine on the infrastructure of the project meets this.
- M2, version 5, fixes the tag rules of the pedestrian network, the 15 m a point report may lie from a stretch, the 5 m of a kerb contradiction, the cover of a geozone and the straight stretch to the network in the state no data.
- `plans_finished/routing_engine/ROUTING_ENGINE_PLAN.md` D-1 rejected a Valhalla run by the project, because it builds its tiles from a file the import deletes (F-4 there), reads the tags by its own costing instead of M6 (F-17 there) and adds a second service to the server. D-1 was decided by the user answering for the backend person; that ruling was still to be confirmed (D-17 there).
- The server of the demo has 4 GB of free memory, 64 GB of free disk and 4 cores after the other services of its owner (`plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md` D-8).
- The static GTFS of ZTP Kraków is published at `gtfs.ztp.krakow.pl` as three feeds: `GTFS_KRK_A.zip`, `GTFS_KRK_T.zip` and `GTFS_KRK_M.zip` (checked by the agent on 2026-10-03). In `GTFS_KRK_T.zip` `wheelchair_boarding` is empty for all 352 stops and `wheelchair_accessible` is `0`, meaning no information, for all 15 361 trips (checked by the agent on 2026-10-03). `GTFS_KRK_A.zip` holds 162 bus routes, with `wheelchair_boarding` of `0` for all 2 984 stops and `wheelchair_accessible` of `0` for all 86 234 trips; `GTFS_KRK_M.zip` holds 33 routes, all with `route_type` 3 (bus), with `0` for all 767 stops and all 22 644 trips (checked by the agent on 2026-10-03). Whether M stands for the agglomeration buses was not checked. `GTFS_KRK_T.zip` carries `feed_version` 20261002 and an empty `feed_start_date`; `GTFS_KRK_A.zip` (publisher MPK) carries `feed_version` `20260930_20261005` and `feed_start_date` 20260930; `GTFS_KRK_M.zip` (publisher R&G PLUS) carries `feed_version` `1684_1685` and `feed_start_date` 20260930. The server answers with `Last-Modified` of 2026-10-01 22:59:31 GMT for T, 2026-10-02 08:35:07 GMT for A and 2026-10-02 14:17:41 GMT for M (all checked by the agent on 2026-10-03). The `calendar.txt` and `calendar_dates.txt` of the tram feed span 2026-10-02 to 2026-12-30, so the day of the demo is covered (checked by the agent on 2026-10-03); the calendars of the two bus feeds were not checked.
- No product code exists: there is no `backend/` and no `frontend/` directory, and `pyproject.toml` declares no runtime dependency, numpy and scipy of `plans_finished/routing_engine/` D-14 included (checked by the agent on 2026-10-03).
- M10 asks that the demo show what the user sees when a source is unavailable: "when the routing service does not answer, a plain message and no guessed route".

## Smallest meaningful scope

1. Valhalla, run by the project on its own infrastructure, replaces the own graph as the engine of walking routes of M2. Decided by the user on 2026-10-03, against OpenTripPlanner 2 and GraphHopper, both run by the project; OSRM and pgRouting were rejected by the agent in the same comparison (seed, message 1, and the answer that followed it).
2. Public transport routes from static GTFS become an optional feature, on the condition that the router can be integrated with them quickly (seed, message 2). It is the first optional feature, built before O1, and "quickly" means at most 4.5 hours of work: when public transport routes do not work within that time, the feature is dropped and the work moves on to O1. Decided by the user on 2026-10-03, against the last place in the queue with a time box and against the first place without one.

## Out of scope

- GTFS-RT, any real-time public transport data (seed, message 2).
- A departure or arrival time chosen by the person; a public transport route always departs now (Domain rules).
- A date of the timetable in the interface; the freshness of the GTFS is stated in the description of the data sources (Domain rules).
- Turn-by-turn navigation, which stays out of scope as the specification says.

## Functional requirements

1. Walking routes of M2 are computed by Valhalla run by the project on its own infrastructure, in place of the own graph of `plans_finished/routing_engine/`. The behavior of M2, M7 and M8 does not change: the pedestrian network of M2, the avoided barriers and geozones, the alternative for an unverified or disputed barrier, the route with the fewest barriers, the stretch to the network in the state no data, the segment states and the barrier list.
2. Nothing of a route request leaves the project, the request to Valhalla included (M2, unchanged).
3. The route form has a switch between a walking route and a route with public transport; walking is the default, and one route is computed at a time.
4. A route with public transport uses the static GTFS of ZTP Kraków - the feeds `GTFS_KRK_T`, `GTFS_KRK_A` and `GTFS_KRK_M` - and always departs now, in the Europe/Warsaw zone. Its walking legs follow every rule of requirement 1.
5. A public transport segment - the ride and the boarding at the stop - is green whenever the GTFS gives no accessibility information for it, with the source GTFS of ZTP Kraków and no date. It is not a fact: it has no status and cannot be voted on or flagged.
6. When the route with public transport cannot be answered while walking routes can, the app computes the walking route on its own and shows it together with a plain statement that public transport was unavailable.
7. The copy of the GTFS is fetched before the demo as a whole or not at all, refreshed only by hand, and the last complete copy stays in use when a fresh one fails.
8. The specification gets a new version: public transport routes leave the section Out of scope and become an optional feature built first, before O1, with a time box of 4.5 hours of work, after which it is dropped; the exception for public transport of ZTP Kraków departs from M7 and M10 and is written next to them. `CLAUDE.md` names the exception next to the rule from the briefs, and `AI_WORKFLOW.md` records that change.
9. D-9 of `plans_finished/mvp/MVP_PLAN.md` is replaced by the decision of this initiative, together with the constraints D-9 hands to the rest of that plan.

## Scenarios: input, flow, expected state after the run

1. Walking route around a confirmed barrier. Input: profile "I use a wheelchair", start Rondo Mogilskie, destination Tauron Arena, a confirmed user report of stairs on the shortest way, switch on walking. Flow: the backend sends Valhalla the request with that barrier to avoid. State after: the route goes around the stairs, its segments carry the states of M7, the list of M8 is shown, and nothing of the request reached any service outside the project.
2. Every way crosses a barrier. Input: profile that avoids stairs, a destination reachable only by ways with 1, 2 and 4 known stairs. Flow: Valhalla with every barrier excluded answers no route; the logic of the project looks for the route with the fewest barriers. State after: the route with 1 barrier, the plain statement that no route without barriers exists, and the place of that barrier in the list.
3. Route with a tram. Input: profile "I walk with a baby stroller", Saturday 2026-10-04 at 10:52, Rondo Mogilskie to Tauron Arena, switch on public transport. Flow: Valhalla computes a multimodal route departing at 10:52 Europe/Warsaw: 200 m on foot, 4 stops by tram, 300 m on foot. State after: the walking legs carry their states of M7 and their barriers in the list of M8; the tram segment is green with the source GTFS of ZTP Kraków and no date.
4. Public transport unavailable. Input: 02:30 at night with no departure soon, or a GTFS copy that failed to load, switch on public transport. Flow: the route with public transport cannot be answered; the app computes the walking route on its own. State after: the walking route with its states and list, and a plain statement that public transport was unavailable.
5. Valhalla not answering. Input: the Valhalla service is down, any switch position. Flow: the request to Valhalla fails or times out. State after: the plain message of M10 and no route, walking or otherwise; nothing is sent to a routing service outside the project.
6. Time box exceeded. Input: 4.5 hours of work on public transport routes without a working route with a tram in Kraków. Flow: the team stops the feature. State after: the switch is not shown, walking routes of requirement 1 stay, and the work moves to O1.

## Challenging own assumptions

- Is "router" in message 2 the walking engine, the public transport routing, or both? Resolved: the walking engine is replaced by Valhalla in any case, as a mandatory part of M2, and the time box of 4.5 hours covers only public transport, as the question that set it was asked about "Valhalla with GTFS returning a working route with a tram".
- Does Valhalla make the walking part simpler at all, given that the network of M2, the rules of M6, the segment states, the alternative and the route with the fewest barriers stay with the project? Partly: it removes the search over the graph and adds public transport, but the import still has to give Valhalla the network of M2, and the route with the fewest barriers needs logic of the project because Valhalla excludes areas without a soft penalty. The old D-1 rejected Valhalla for exactly these reasons; the user accepted them as costs of the change. How long it takes is measured by the spike the user runs outside the project with the prompt drafted in the conversation on 2026-10-03.
- Do the walking legs of a multimodal route still honour the excluded barriers, the geozones and the network of M2? Not verified: it is the main technical risk of requirement 4 and one of the questions of that spike. If they do not, requirement 4 cannot keep the rules of requirement 1 and the time box decides.
- Is a green public transport segment safe for the person? Not by data: the feeds of 2026-10-03 carry no accessibility information at all, and older high-floor vehicles may serve a route. The user decided the exception knowingly; the risk to the person and to the criterion "Data reliability, presentation and updates" (15% of the Kraków task description) stays and belongs in the risks of the PRD.
- Does a walking route shown on its own in scenario 4 break "no guessed route" of M10? Read as no: the walking route is a computed route of another kind, stated as such, not a guess at the route with public transport. Scenario 5, where Valhalla itself does not answer, still ends with the message of M10 and no route.

## Domain rules or explicit TODO

- A segment of public transport organized by ZTP Kraków - trams and buses, the feeds `GTFS_KRK_T`, `GTFS_KRK_A` and `GTFS_KRK_M` - is treated as accessible whenever the GTFS gives no information on its accessibility. Decided by the user on 2026-10-03 as an exception "introduced on purpose" (seed, message 2), at first for trams, chosen against a separate state that claims nothing and against using trams only as plain no data, and then widened by the user to the whole public transport organized by Kraków, against trams only and against buses shown as no data; the user confirmed that it covers public transport only, never walking segments. The user chose it after the agent stated that it conflicts with the Kraków brief rule that missing information is never presented as a confirmation of accessibility, and that the feeds carry no accessibility information. The same rule stands in `CLAUDE.md`, section What we are building, as a constraint from the challenge briefs, and in M10 of the specification.
- A stop or a trip the GTFS explicitly marks as not accessible (`wheelchair_boarding` or `wheelchair_accessible` of `2`) is not accessible. Agent decision at C:40, without asking: the exception covers only what has no information, in the words of the user, so information that is given counts. No such value is in the feeds of 2026-10-03.
- The static GTFS of ZTP Kraków is a public data source of the city, not an internal system of UMK or MJO, so using it keeps the constraint of `CLAUDE.md` that the app does not rely on internal systems. Stated by the user on 2026-10-03.
- `CLAUDE.md`, section What we are building, gets the exception of public transport organized by ZTP Kraków without accessibility data next to the rule that missing information is never presented as a confirmation of accessibility, naming it a deliberate exception of the specification; the change of a workflow rule is recorded in `AI_WORKFLOW.md` as well. Decided by the user on 2026-10-03, against leaving `CLAUDE.md` unchanged and against recording it only in `docs/hackathon/challenge_requirements.md`.
- The pedestrian network of M2, version 5, stays the rule: Valhalla routes only on the ways that rule admits, and the specification does not take the access rules of Valhalla. Decided by the user on 2026-10-03, against changing the specification to the rules of Valhalla. How Valhalla is given that network is for phase B.
- A public transport segment of a route - the ride and the boarding at the stop - is shown exactly like a green walking segment, with no additional description, with the source GTFS of ZTP Kraków and without a date. Decided by the user on 2026-10-03, against a green segment with its own icon and a text in the list of M8 naming the assumption, and against a green ride with the boarding as no data. Asked for trams and applied to the whole public transport of the exception above. This departs also from M7, under which a segment is green only when every attribute relevant to the profile is known. The date of the timetable was part of the option the user chose; it was then dropped by the user on 2026-10-03, after the agent quoted M10, which asks every fact for its date, and the brief, which asks the team to state the freshness of every source: a public transport segment is not a fact of M10, since it has no votes and no status, so it shows its source and no date, and the freshness of the GTFS - the day each feed was published - goes into the description of the data sources and the presentation. Chosen against the day of `Last-Modified` of each feed shown on its segments and against a segment with neither source nor date.
- A public transport route always departs now, at the moment of the request in the Europe/Warsaw zone; the person chooses neither a departure nor an arrival time. Decided by the user on 2026-10-03, against an optional chosen departure time and against an arrival time as well.
- The person chooses the kind of route with a switch in the route form, walking or with public transport, and walking is the default; one route is computed at a time. Decided by the user on 2026-10-03, against computing both and offering two proposals and against the app choosing the faster one.
- When every way to the destination crosses a barrier from the profile or a matching geozone, the route stays the route with the fewest such barriers of M2, unchanged. Decided by the user on 2026-10-03, against the shortest route ignoring the barriers with their list and against a message with no route, after the agent stated that Valhalla excludes areas without a soft penalty, so this needs logic on the side of the project.
- The copy of the GTFS follows the copy of OpenStreetMap of M6: the three feeds are fetched before the demo and used as a whole or not at all, a fresh copy is triggered by the team by hand and nothing refreshes on a schedule, and when a fresh copy cannot be fetched or completed the last complete copy stays in use unchanged. Decided by the user on 2026-10-03, against the same rule with the day of download as the date and against a daily automatic refresh. The user chose `feed_version` as the date of the timetable; the agent then found that only `GTFS_KRK_T` carries a date there, and the user decided that the app shows no date of the timetable at all (the rule of the public transport segment above).
- When the route with public transport cannot be answered - no departure in time, or the public transport part of the engine not answering - while walking routes can, the app computes the walking route on its own and shows it with a plain statement that public transport was unavailable. Decided by the user on 2026-10-03, against a message with a button that switches to walking and against a message alone.
- TODO: how a route treats a stop or a trip the GTFS marks as not accessible (`2`) - left out, shown as a barrier, or something else - is not decided. Not blocking: no such value exists in the three feeds of 2026-10-03, and the copy is refreshed only by hand, so a new value cannot appear without the team seeing it.
- The new optional feature takes the number O9 and the specification says it is built first, before O1, so that the numbers O1 - O8 cited across the repository keep their meaning. Agent decision at C:40, without asking: renumbering would change references in documents other people edit in parallel, while the order is what the user decided.

## Notes on data, performance and security

- Personal data. The current location and the preferences of the profile travel to Valhalla inside the infrastructure of the project, which M2 allows; M2 also says the current location is not logged, so whatever Valhalla writes to its own logs about a request has to keep that rule. Not checked yet; it is a constraint for phase B, not a question of product behavior.
- Query volume. The route with the fewest barriers and the alternative of M2 may need more than one request to Valhalla per route request, and the PRD of `plans_finished/mvp/` limits a route request to 5 seconds. The spike measures it.
- Memory and disk. Valhalla, its tiles and the transit tiles share the server of the demo with the backend and the database, within 4 GB of free memory and 64 GB of free disk. The spike measures it.
- Source data. The GTFS copy is fetched by the team from a public server of the city before the demo; nothing about the person is sent there. The OpenStreetMap copy lives only in the database and the downloaded file is deleted after each run (`plans_finished/osm_data_source/` D-14), while Valhalla builds its tiles from a file; reconciling the two is for phase B.
- Licences. The terms of use of the GTFS of ZTP Kraków were not checked; the brief asks the team to state them for every source (`docs/hackathon/challenge_requirements.md`, section Data sources named in the brief). Valhalla is under the MIT licence, according to its repository, not checked in this interview.
