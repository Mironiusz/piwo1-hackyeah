## Decisions

D-1. Every member of the team who writes backend code runs their own PostgreSQL in a container of a project image, started with Docker Compose: Docker Desktop with the WSL 2 backend on Windows, Docker Engine with the Compose plugin on Linux. Decided by the user on 2026-10-03 in phase B, against the ready image `pgrouting/pgrouting:18-3.6-4.0` and against a native installation on each operating system. The ready image exists for amd64 only and is built on an image whose init script creates extensions outside the chain of revisions (F-9, F-10). A native installation needs a different procedure on each system and gives different versions on them: the Windows bundle carries PostGIS 3.6.2 (F-16), the PGDG packages on Linux 3.6.4 (F-8), and the native PostgreSQL on the machine of the agent's session has no PostGIS at all (F-6).

D-2. The environment is checked for Windows x64 and Linux x64, the machines on which the team members who write backend code run it, as stated by the user on 2026-10-03 in phase B. The base image and the PGDG packages also exist for arm64 (F-7, F-8), but macOS is not checked, and no step of this plan or of the work package of `plans/mvp/` covers it.

D-3. The project image is built from `postgres:18.6-trixie` and installs from the PGDG repository the base image already configures exactly `postgresql-18-postgis-3=3.6.4+dfsg-2.pgdg13+1` and `postgresql-18-pgrouting=4.0.1-1.pgdg13+1`, whose scripts packages come as dependencies (F-7, F-8). It adds nothing to `/docker-entrypoint-initdb.d` except the script of D-6. PostgreSQL 18 allows the builtin locale provider with the locale C.UTF-8 that `docs/standards/standard_database.md` requires (F-12, F-19). The image, the base image and the extension versions are the same for every member. Agent decision at C:40, without asking, for the exact pins: the version of an extension is recorded in the database when the extension is created, so two members on different builds would apply the same chain to different extension versions, and the PGDG index still holds older builds next to the newest (F-8).

D-4. The Compose file has one service, the database, built from the project image. The port 5432 of the container is published only on the loopback address 127.0.0.1 of the machine, at a host port that is an entry of `.env.local`, because it depends on the machine: a member may already run a native PostgreSQL on 5432 (F-6). The data lives in a named volume mounted at `/var/lib/postgresql`, the volume of the version 18 image (F-11). The Docker engine is release 28.0.0 or newer, which the README of the work package states. Agent decision at C:40, without asking: Docker publishes a port on every host address unless told otherwise, and older releases let the local network reach even a port published to localhost (F-25), so a database with a superuser account would be open to the network of the venue.

D-5. The cluster holds three login roles. The bootstrap superuser is the one the image creates at its first start from `POSTGRES_USER` and `POSTGRES_PASSWORD` (F-11), the account "the database server itself creates at installation" of the PRD; only the script of D-6 uses it. The schema owner is `LOGIN SUPERUSER` and owns the database; it applies the revisions, and its address is read only by `alembic/env.py` (F-20). The service account is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, owns no object, and gets its rights only from grants in revisions; since the database is created on PostgreSQL 18 and owned by the schema owner, the service account cannot create anything in the public schema without a grant (F-14). The names and passwords of the three roles and the name of the database are entries of the local environment files and none of them stands in the repository (F-20). Decided by the user on 2026-10-03 (`LOCAL_DATABASE_SHAPE.md`, question 3) for the two accounts and their roles; the attribute lists are an agent decision at C:40, without asking, spelling out "not a superuser and owns nothing" so that no other way to change the schema or the roles is left to the service account.

D-6. The script creating the database and the accounts is one shell script in `/docker-entrypoint-initdb.d` of the project image. The entrypoint runs it as the bootstrap superuser only when the data directory is empty (F-11), so it runs once, at the first start, and never on a later start. It creates exactly the schema owner and the service account of D-5 and the database with `CREATE DATABASE <name> OWNER <schema owner> TEMPLATE template0 ENCODING 'UTF8' LOCALE_PROVIDER builtin LOCALE 'C.UTF-8'` (F-12, F-13); it creates no extension, no schema object and no grant (F-18). The names and passwords reach it as environment variables of the container, interpolated by Compose from the local environment files. Recreating the database from scratch, for example after an applied revision was edited (F-18), is removing the named volume, which holds nothing else, and starting the service again. Agent decision at C:40, without asking: the init directory of the official image is the documented place for a one-time setup, it keeps the first setup to one start command, and it keeps every later start free of any change (F-18).

D-7. The first revision in the chain, applied by the schema owner, creates PostGIS with `CREATE EXTENSION postgis`; nothing outside the chain creates it (F-15). The revision is written by `plans/schema_revision/`. pgRouting stays available and is not created until `plans_finished/routing_engine/` chooses it; that choice then needs one new revision with `CREATE EXTENSION pgrouting`, not a rebuilt environment (F-8, F-22). Decided by the user on 2026-10-03 (`LOCAL_DATABASE_SHAPE.md`, questions 3 and 5).

D-8. The work package of `plans/mvp/` decides the file names and locations of the image definition, the Compose file and the script, the names of the environment entries with their records in `docs/standards/standard_config.md`, section Environment entries, the README instructions and the Alembic configuration, under `docs/standards/standard_naming.md` and `docs/standards/standard_config.md`, because they belong to the backend skeleton that Q-11 of `plans/mvp/MVP_PLAN.md` shapes. With the first critical test it also adds what `docs/standards/standard_tests.md` requires with it (F-21), and these critical tests against the local database: `lower('ŁÓDŹ')` returns `łódź` and text compares by bytes (F-19); after `alembic upgrade head` the extension postgis exists and pgrouting is listed in `pg_available_extensions`; with the service account a `CREATE TABLE` in the public schema and a `DROP` or `ALTER` of an object of the first revision are refused (`LOCAL_DATABASE_SHAPE.md`, scenario 5). Agent decision at C:40, without asking: naming these files here would guess the backend architecture, and the three tests prove the locale, the extensions and the rights by behavior.

D-9. The consequence for the hosted database is handed to the task `DEPLOYMENT` of `plans_finished/deployment/` as an input of its shape, without deciding it there (PRD FR-4). Its open question and its decisions stay unchanged.

D-10. The change stays within the scope of the PRD: the shapes of `plans_finished/fact_schema/` and `plans_finished/routing_engine/` get no input from this plan, and the constraint reaches them through D-7 of `plans/mvp/MVP_PLAN.md` and the registry entry. Decided by the user on 2026-10-03 in phase B, against adding an input to both shapes and against adding one to the shape of `plans_finished/fact_schema/` only.

D-11. Removing Q-4 from the risk of `plans/mvp/MVP_PLAN.md` on the order of the open questions also removes Q-3, which D-6 of that plan settled (F-1). Agent decision at C:40, without asking: the sentence is edited anyway, and leaving a settled question in it would keep the risk wrong.

- The answers behind the PRD and the choices of D-1 and D-2 were given by the user, who has not stated being the db person. The ruling of the db person is still to be confirmed, as in `plans_finished/fact_schema/`.
- No run of the environment happens in this initiative (PRD, Out of scope): the engine of Docker Desktop is not running on the machine of the agent's session (F-5). A wrong claim surfaces only in the work package of `plans/mvp/`; every claim of D-3 - D-6 rests on the published contents of the images, the packages and the documentation (F-7 - F-14).
- Building the image needs `deb.debian.org` and `apt.postgresql.org`, and pulling the base image needs Docker Hub. A public service already refused requests from the address of the venue (F-24), so the first build is done early, and a member whose build fails can take the built image from another member with `docker save` and `docker load`.
- The exact pins of D-3 fail the build once the PGDG index drops those builds. Within the hackathon this is unlikely, but a stranger building from the README weeks later may need to raise the pins to the builds the index then offers.
- Docker Desktop needs a paid subscription for professional use in larger organizations (F-17). A member working on a laptop of such an employer checks their licence before installing it; Docker Engine on Linux has no such condition.
- The PRD of `plans_finished/fact_schema/` does not mention creating PostGIS and still says it waits for Q-4 (F-23), and the user kept its shape out of this plan (D-10). If the first revision is written without `CREATE EXTENSION postgis`, the first critical test of D-8 fails; the human step of the rollout order tells the db person.
- pgRouting 4.0 is the only build PGDG offers for PostgreSQL 18 (F-8). If `plans_finished/routing_engine/` designs against an older pgRouting interface, it has to check its functions against 4.0 first.
- An environment that carries pgRouting carries a dependency the project never uses if `plans_finished/routing_engine/` chooses another engine.
- On the hosted demo the account that applies revisions is a superuser, and the server runs other services of its owner (F-4). Step 6 hands this over; it is not decided here.
- A member may run a native PostgreSQL on the same machine, as the machine of the agent's session has one (F-6). What happens when both servers want port 5432 was not checked; the host port of D-4 lets that member move the container to another port in `.env.local`, and the README of the work package says so.
