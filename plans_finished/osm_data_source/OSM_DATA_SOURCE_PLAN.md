# Plan: Choice of the source of OpenStreetMap data for the MVP

Document state: 2026-10-03, plan closed

## Goal

Decide where the MVP takes OpenStreetMap data for Kraków from, how the copy is fetched, cut, dated and refreshed by hand, and how a fresh copy is reconciled with the stored facts, as defined by `plans_finished/osm_data_source/OSM_DATA_SOURCE_PRD.md` (FR-1 - FR-12, AC-1 - AC-11). Hand the decision to `plans/mvp/` so that it settles `plans/mvp/MVP_PLAN.md` Q-2, together with the constraints it puts on Q-10 and Q-11 there and on `plans_finished/routing_engine/`, `plans_finished/demo_environment/`, `plans_finished/frontend_stack/` and `plans_finished/api_contract/`, and check the text of the rules of this initiative in version 3 of `docs/product/specification.md`, which `plans_finished/osm_barrier_mapping/` writes. No product code is written here: the import and the refresh are built as a work package of `plans/mvp/` (PRD, Out of scope).

## Decisions

D-1. The copy is taken from the Geofabrik extract of Małopolska, `https://download.geofabrik.de/europe/poland/malopolskie-latest.osm.pbf`. Decided by the user on 2026-10-03 in phase B, answering for the import person as in the shape, against the BBBike extract Cracow, which leaves out the east of Nowa Huta and is a week old (F-2), and against the public Overpass API, which did not answer the checks of F-1 and of the shape on the day of the first import. It is the only candidate checked that meets FR-1 - FR-4 (F-3, F-5 - F-8).

D-2. The file is read with pyosmium, the package `osmium` 4.3.1, which becomes the first runtime dependency of the project (F-13). It has wheels for Python 3.13 on Linux, Windows and macOS (F-12), so the server needs no system package, and the cut, the derivation of facts and the reconciliation stay in the Python code of the backend. Decided by the user on 2026-10-03 in phase B, against osmium-tool with osm2pgsql, which would add two system tools and a mapping in Lua. The measurements of F-7 - F-11 were made with it.

D-3. A run first asks for `malopolskie-latest.osm.pbf` without following the redirect and reads the dated file name from the `Location` header (F-3). It then downloads the dated `.osm.pbf` and the dated `.osm.pbf.md5` from the same directory, and accepts the file only when its MD5 sum equals the sum in the `.md5` file. Taking both under the dated name keeps a file and a sum of two different days from meeting, which the latest names could do when Geofabrik publishes between the two downloads. A `Location` that does not point to a file of the same directory named `malopolskie-` followed by six digits and `.osm.pbf` is a failed refresh. Agent decision at C:40, without asking.

D-4. The date of the copy (PRD FR-3) is the instant `osmosis_replication_timestamp` of the header of the accepted file, stored in UTC and shown as its calendar day in Europe/Warsaw, computed through an aware value in that zone (F-30). For the file of F-6, 2026-10-02T20:21:34Z is 22:21:34 on 2 October in Warsaw, so the app shows 2 October, the case of AC-3. A file whose header lacks this value, or whose value is not an instant, is a failed refresh; the day of the download is never used in its place. Agent decision at C:40, without asking: the header is part of the file whose sum was checked, so the date cannot belong to a different file, while the state file of F-6 is a separate request.

D-5. A refresh whose header instant equals the instant of the copy in use ends as an executed run with nothing changed and the cause "no newer copy", logged at INFO. A refresh whose header instant is earlier than that of the copy in use is a failed refresh. Agent decision at C:40, without asking: an equal state gives by D-10 exactly the state already in use, so the run saves the work; an earlier state would move the date the app shows backwards and run FR-8 on facts that OpenStreetMap still holds.

D-6. The copy covers the administrative boundary of Kraków, relation 449696, assembled anew from each accepted file (F-8). A node belongs to the copy when it lies inside the boundary. A way belongs to the copy when at least one of its nodes lies inside, and then it is kept whole with all its nodes, so that no way of the pedestrian network ends at the boundary in the middle of a segment. A relation belongs to the copy when at least one of its member ways does, without adding its other members (F-10). A file in which relation 449696 is missing or does not assemble into a closed area is a failed refresh. The area was decided by the user on 2026-10-03 in phase B, against the bounding rectangle of Kraków, which takes in parts of Wieliczka, Skawina and Zabierzów, and against the whole of Małopolska. The rules for nodes, ways and relations at the boundary are an agent decision at C:40, without asking: they follow from AC-1 and from F-10.

D-7. An OpenStreetMap element is identified by its type - node, way or relation - together with its OpenStreetMap identifier, and an OpenStreetMap fact by that element identity together with its fact type of the closed list. When OpenStreetMap splits, joins or recreates a way, nothing is matched by geometry: a part that keeps the old identifier keeps its facts (JOSM keeps it on the part with the most nodes, F-16), a part with a new identifier gets new OpenStreetMap facts without votes (PRD FR-10), and an identifier that disappears runs FR-7 or FR-8. This can leave a converted user fact next to an OpenStreetMap fact of the same barrier, which is accepted for the MVP. Decided by the user on 2026-10-03 in phase B, against matching by geometry, which FR-10 and `docs/product/specification.md` M3 forbid. It settles the open point the shape left in its section Domain rules and handed to Q-10 of the MVP plan as its second point (F-18).

D-8. The date of the last OpenStreetMap edit of a fact (PRD FR-2, AC-2) is the timestamp of the element the fact comes from, as it stands in the accepted file, shown as its calendar day in Europe/Warsaw. A fact from a node takes the timestamp of that node, a fact from a way the timestamp of that way. Every element of the file of F-7 has a timestamp, so an element without one in a later file is treated as a damaged file and the refresh fails, rather than producing a fact without a date. Agent decision at C:40, without asking: AC-2 forbids showing an OpenStreetMap fact without the date.

D-9. A refresh becomes visible as a whole or not at all (PRD FR-6, AC-5). The download, the sum, the header, the boundary and the cut are completed before anything is written. Then the copy, the reconciliation of D-10 and the date of the copy become visible in one database commit. Any failure before or during the commit leaves the copy in use, its facts, its routes and its date unchanged. Q-10 of the MVP plan decides how the copy is stored - writing it in one transaction or switching to a fully written one - under this constraint. Agent decision at C:40, without asking: it follows from FR-6.

D-10. Every refresh reconciles the fresh copy with the stored facts in this order, keyed by the identity of D-7 as the reconciliation key of `docs/standards/standard_idempotency.md` (F-28):

1. A fact of the fresh copy, derived from the tags by the rule of `plans_finished/osm_barrier_mapping/`, whose identity matches no stored fact becomes a new OpenStreetMap fact without votes, even where a user fact of the same type lies (PRD FR-10).
2. A fact whose identity matches a stored OpenStreetMap fact stays that fact, with its votes, and takes the date of the last edit and the attributes of the fresh copy.
3. A fact whose identity matches a fact converted by FR-7 or outdated by FR-8 becomes an OpenStreetMap fact again, with the source OpenStreetMap, the date of the last edit of the fresh copy, all its votes and the status those votes give a fact from OpenStreetMap by M4 (PRD FR-9).
4. A stored OpenStreetMap fact whose identity is missing from the fresh copy is compared by the sums of M4 weights - 1 for a logged-in vote, 0.5 for a vote without an account, each kept for as long as the fact exists (D-21). When confirmations outweigh denials, it becomes a user fact with all its votes, the source "user report", the date of its last confirmation and the status of a user fact by M4 (PRD FR-7). Otherwise it becomes outdated with the reason that it was removed in OpenStreetMap, leaves the map and the routes, and keeps its votes in its history (PRD FR-8).
5. Apart from points 3 and 4, a refresh never changes the status of a fact: an OpenStreetMap fact present in the fresh copy keeps the status its votes give it by M4. No refresh adds, removes or reweighs a vote.
6. Whether a fresh copy contradicts a converted fact (PRD FR-11) is not stored by the refresh. It is evaluated from the tags of the element in the copy in use by the contradiction rule of `plans_finished/osm_barrier_mapping/`, which is why a converted fact keeps its element identity.
7. Running the reconciliation twice on the same copy gives the same state. The final protection is a unique constraint on the identity of D-7 for every fact that came from OpenStreetMap, converted and outdated ones included, written with `INSERT ... ON CONFLICT`.

Agent decision at C:40, without asking: points 1 - 6 restate FR-7 - FR-11 as one ordered procedure over the identity the user chose, and point 7 follows from the standard.

D-11. Nothing triggers a refresh on a schedule (PRD FR-5). A refresh is an administrative forcing of the import, started by a member of the team and never by request handling (F-26), and the same run makes the first copy (PRD FR-4). Before the download it takes a lock in the database with a zero wait, and a second trigger while the lock is held ends at once as a skipped run logged at INFO (F-27). The form of the trigger - for example a command of the worker entry point - and the machine it runs on - the server of the demo, or a team machine writing to the database of the demo - are decided by Q-11 of the MVP plan together with Q-1 of `plans_finished/demo_environment/DEMO_ENVIRONMENT_PLAN.md`, using F-4, F-10 and F-11. Agent decision at C:40, without asking: the standards fix the lock and the kind of run, and the rest is the backend architecture Q-11 owns.

D-12.
