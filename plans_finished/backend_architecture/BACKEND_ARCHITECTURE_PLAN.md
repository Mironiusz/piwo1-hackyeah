## Decisions

D-1. Start of the backend process (item 1). The backend is started with `python -m api`. `api/__main__.py` holds `main()`, which calls `uvicorn.run` with the application factory `api.app.build_app`, `factory=True`, `workers=1`, `host` and `port` from the environment entries `API_BIND_HOST` and `API_PORT` read through `config/config.py`, `log_config=None` and `access_log=False`. `workers=1` stands in code, so the one process of F-13 cannot be lost to a command line. The bind host is an entry, not a constant, because `0.0.0.0` inside the container and `127.0.0.1` on a laptop differ between environments, and a constant `0.0.0.0` is a bandit finding of medium confidence (F-11). `log_config=None` keeps uvicorn from configuring a second logging mechanism next to `config/logging.py` (F-8), and `access_log=False` keeps the URL out of the log, which the request log of D-3 replaces (F-28). FastAPI and uvicorn become pinned runtime dependencies. Agent decision at C:40, without asking: it follows from F-11, F-12, F-13 and F-28.

D-2. Application factory and request handling. `api/app.py` holds `build_app() -> FastAPI`, which configures logging through `config/logging.py`, includes the routers of D-6, registers the middleware of `api/request_context.py` and the exception handlers of `api/errors.py`, and sets the lifespan of D-9. Every endpoint is a plain `def`, so FastAPI runs it in its thread pool, the blocking calls of the address search and of Valhalla run there as F-13 requires, and the locks of the graph and of the rate gate are `threading.Lock`. `api/request_context.py` takes or generates the request identifier through the entry points of `config/logging.py` and writes the one request log entry of F-28. `api/errors.py` turns the named exceptions of the rules layer into the codes and bodies of `docs/product/api_contract.md`. `api/session.py` reads `Authorization: Bearer`, calls `service/sessions.py` and sets the renewed `Session-Token`. Agent decision at C:40, without asking: it follows from F-3, F-8, F-13 and F-27.

D-3. Configuration and logging. `config/config.py` is the facade of F-5, `config/settings.py` holds the Pydantic model of the environment contract, `config/env_file.py` reads the environment file format, and `config/logging.py` holds the mechanism of F-8 with the root logger name `piwo1-hackyeah`, the name of the project in `pyproject.toml`. The entries this plan adds are `API_BIND_HOST`, `API_PORT`, `ROUTING_SERVICE_URL` and `ROUTING_DATA_DIR`; `ROUTING_DATA_DIR` is read only by the import run and is optional under F-7. The work package that writes the first code records them in `docs/standards/standard_config.md`, section Environment entries, with the database entries D-7 of the MVP plan names. Agent decision at C:40, without asking: the file names and the entries follow F-5, F-7 and F-8.

D-4. Database access. Every connection is opened by `data/engine.py`, the one place of F-10: a synchronous SQLAlchemy engine on psycopg 3 with the session zone pinned to UTC, built by `build_engine(statement_timeout_ms: int)`. The backend process uses a statement timeout of 5000 ms, the limit of a route (F-40); the import run uses the 60 minutes of its run timeout (F-15). Queries are constants named `<VERB>_<WHAT>_SQL` in the data layer. SQLAlchemy, psycopg and Pydantic become pinned runtime dependencies, with Alembic. The Alembic configuration is `alembic.ini` in the repository root, with `alembic/env.py`, which reads the address of the schema owner account (F-6), and the revisions in `alembic/versions/`. Agent decision at C:40, without asking: the standards already assume these libraries (F-10), and F-17 asks Q-11 for the database timeout.

D-5. Import and refresh run (item 2). The run is started by hand with `python -m worker import-osm` in a one-off container of the backend image on the server of the demo, never on a team machine. `worker/__main__.py` holds `main(argv: list[str]) -> int`, which parses the command, opens the run scope of `config/logging.py`, calls `service/osm_import.py` `apply_osm_import() -> OsmImportResult` and returns 0 for an executed or skipped run and 1 for a failed one. The run, in this order: takes the lock of F-15 through `data/locks.py`; downloads and cuts the copy (`data/geofabrik.py`); writes the network file and builds the routing data of D-6 with the Valhalla tools in the same container; writes the copy, its reconciliation and its date in one commit (`data/osm_copy.py`); switches the pointer of D-6; and deletes the downloaded file whatever the outcome. On the server the run reaches the database only inside the network of the demo, so the database publishes no port of the host, and the Valhalla tools and the routing data are where the routing service reads them. The other parts of the loading program of F-31 - the tile archive and the sample reports - are further commands of the same entry point, named by the work packages that build them. No periodic task exists, so no worker process runs on the server, and the registry of periodic tasks with its consistency test is created with the first periodic task (F-4). Agent decision at C:40, without asking, the user having withdrawn question 4 of the shape: the server keeps the database closed to the network outside the demo and keeps the routing data next to the service.

D-6. Routing data and the copy the service serves (item 3). The volume of `ROUTING_DATA_DIR` holds one directory per copy, `copies/<state_at>/`, named by the instant of F-25 as whole seconds since the epoch, with `network.osm.pbf` and `valhalla_tiles.tar`. The run sets the modification time of `valhalla_tiles.tar` to that instant before the commit and never changes the files of a directory after it. After the commit it writes the name of the directory into `current` through a temporary file and a rename. The routing service, at its start, reads `current`, writes the absolute path of that directory's `valhalla_tiles.tar` as `mjolnir.tile_extract` into its configuration and starts `valhalla_service`; while `current` does not exist it waits, reading it again every 5 seconds, and starts nothing. Every route request calls `GET /status` of the service through `data/valhalla.py` `fetch_served_copy_instant() -> int`, with the 2-second timeout of F-19, and compares `tileset_last_modified` with the instant of the copy in use read in its transaction; when they differ, or the call fails, the request ends with `routing_unavailable`. The path the service reads is fixed for its whole life, so `/status` reports the copy it loaded, which a fixed path behind a moving link would not (F-22, F-23). Old directories are not deleted; each takes about 60 MB, and the demo is deleted on 4 October 2026. The route work package builds the start script of the service in `valhalla/` with the configuration of F-19. Agent decision at C:40, without asking: F-22 - F-24 measured that this is the only reading of the served copy the service offers, and that it lies when the file changes under it.

D-7. Graph of the route with the fewest barriers (item 3). `service/route_graph.py` holds the graph as a cache of the process, keyed by the instant of the copy it was built from, with `build_route_graph_at_start() -> None` for the lifespan of D-9 and the function `resolve_fewest_barriers_path` for `service/route_planning.py`, whose parameters and result the route work package defines from `plans_finished/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-7; a rebuild holds a `threading.Lock`, as F-17 decides. The network is read by `data/route_network.py`. During a rebuild the old and the new graph exist together, about 1.3 GB. Agent decision at C:40, without asking: F-17 and F-19.

D-8. Transaction of a route request. A route request runs in one `REPEATABLE READ READ ONLY` transaction from its first read to its last, the calls to Valhalla and the check of `plans_finished/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-9 included, so every read of one route sees one snapshot and one copy, also when a refresh commits during it. Agent decision at C:40, without asking: the check after Valhalla answers reads the database again, and only one snapshot keeps it on the copy the request started with (PRD FR-4).

D-9. Start before the data (PRD FR-5). The lifespan of `build_app` calls `build_route_graph_at_start()`. When there is no copy in use, it logs that at INFO and the process starts without a graph; when the database refuses the read - unreachable, or without the schema before the revisions - it logs the error at WARNING and the process starts too. A route request whose read of the copy in use finds no copy, or is refused by the database, ends with `routing_unavailable`; a refusal is logged at ERROR without coordinates. Once the copy is loaded and the service serves it, the next route request builds the graph under D-7, so no restart of the backend is needed. Agent decision at C:40, without asking: PRD FR-5 and AC-5, with the order of F-31.

D-10. Placement on the server (item 4). The Compose project of the demo has four long-running services, one one-off container and one volume per kind of data:

- `proxy`, the reverse proxy of F-30, the only service that publishes a port of the host, the HTTP port; it serves the files of the frontend build and the tile archive, answering byte ranges (F-29), and passes `/api/` to `backend`;
- `backend`, the backend image, started with `python -m api` as one process on the internal port 8000;
- `database`, the PostgreSQL image of D-7 of the MVP plan, an instance of its own on the volume `database_data`, with no port of the host;
- `routing`, the Valhalla image of `valhalla/Dockerfile`, on the internal port 8002, with no port of the host, reading the volume `routing_data` without writing to it;
- the import of D-5, a one-off container of the backend image writing to `routing_data`, and no long-running worker.

The backend image is built on the image of `valhalla/Dockerfile` with Python 3.13 added, so the import has the Valhalla tools of D-6 and the worker stays an entry point of the same image as the programming interface (F-4, F-21). The tile archive lies on a volume the proxy reads and the loading command of the map work package writes. The software of the proxy, the way Python 3.13 enters the image, the file names of the Compose project and the commands are decided by the task `DEPLOYMENT_CONFIG` of `plans/deployment_config/`. Decided by the user on 2026-10-04 in phase B for the base image of the backend, against a slim Python image with the routing data built by a second container in a second step; the rest is an agent decision at C:40, without asking, from F-29 - F-31.

The sum is at most 10.1 GB of the 16 GB of the server. Agent decision at C:40, without asking: PRD FR-7; the measurement of the database and of the backend on the server belongs to the first deployment.

Agent decision at C:40, without asking: F-24 and D-5.

## Risks

- Parallel editing. Other sessions edit `plans_finished/mvp/MVP_PLAN.md` and the specification; a conflicting edit is merged on the current text, never overwritten.
- The `/status` call adds a fourth call to Valhalla to a route request, against the three calls of 2 seconds `plans_finished/valhalla_routing/VALHALLA_ROUTING_PLAN.md` D-10 counts within 5 seconds; it answers from a `stat`, but its time on the server is not measured.
- A change of the modification time of a tile extract, for example a copy of the volume that does not keep it, makes every route end with `routing_unavailable` until the run is repeated; it never lets a route mix two copies.
- The backend image depends on the Valhalla image, whose build took 11 min 33 s, and Python 3.13 has to be added to Ubuntu 24.04; `DEPLOYMENT_CONFIG` carries that cost.
- `worker/` hosts an administrative command, while `docs/standards/standard_naming.md` describes it as the layer that triggers periodic tasks; the command keeps the rule of `docs/standards/standard_worker.md` that the layer has no domain rule and calls only the rules layer, and `plans_finished/osm_data_source/OSM_DATA_SOURCE_PLAN.md` D-11 named this form.
- A route request holds a database connection while Valhalla answers (D-8), so concurrent routes are limited by the connection pool; the demo has few users at a time.
- The memory of the database and of the backend process is assumed, not measured (D-11).
- The hash is personal data kept without a limit if the demo outlives 4 October 2026.
